## 1. 本讲主线：减少等待，同时保住正确性

对应讲义页 2–3、38、48、62，PDF 第 3–4、89、106、171 页。

[LEC 8](LEC-8-Before-or-after-atomicity.md) 用两阶段锁（2PL）保证冲突可串行化：访问前先加锁，释放后不再取得新锁。但锁有管理成本，事务可能等待，还可能死锁。

本讲从三个方向继续优化：

```text
2PL：先协调冲突，再访问数据
  ↓ 能否先做计算，最后再检查？
OCC：私有执行 → 验证 → 提交或重试
  ↓ 能否让硬件代劳？
HTM / RTM：CPU 跟踪读写集合、检测冲突、提交或撤销
  ↓ 长时间只读事务还要频繁重试吗？
MVCC：保留旧版本，让读者使用一致快照
  ↓ 读快照已经正确，写事务也一定正确吗？
写写冲突检查 → 快照隔离 → write skew → 更强的验证
```

**贯穿本讲的问题是：哪些事务必须协调，什么时候协调，以及失败时让谁等待或重做。**

需要一直区分三个概念：

| 概念 | 解决的问题 | 本讲的提醒 |
| --- | --- | --- |
| Before-or-after atomicity | 并发操作能否解释为完整动作的某种先后执行？ | 需要明确可串行化的保证 |
| All-or-nothing atomicity | 操作失败时能否全部生效或全部撤销？ | 私有缓冲便于撤销，但崩溃恢复仍需额外机制 |
| Snapshot isolation（SI） | 每个事务是否读取一致快照，并避免并发写入同一记录？ | 仍可能发生 write skew，不等于可串行化 |

## 2. OCC：执行时乐观，提交前验证

对应讲义页 2–6，PDF 第 3–9 页。

**Optimistic concurrency control（乐观并发控制，OCC）**先假设冲突较少，让事务执行；在发布修改之前检查，这次执行能否安全提交。不满足条件就 abort（中止），丢弃本次结果，之后重新执行。

### 2.1 三个阶段

| 阶段 | 做什么 | 共享状态是否被修改？ |
| --- | --- | --- |
| Phase 1：本地执行 | 读取共享数据，记录读集合；把待写结果放入私有写集合 | 事务的数据修改尚未发布 |
| Phase 2：验证 | 检查读取依据是否仍然有效，是否存在冲突提交 | 不发布业务修改 |
| Phase 3：提交 | 验证成功则安装写集合；失败则中止 | 成功时发布修改 |

**“乐观”不表示不检查，而是把主要冲突检查推迟到提交阶段。**

### 2.2 Read set 与 write set

```text
read_set：本次执行依赖了哪些共享记录，以及读到的版本
write_set：本次执行准备写哪些记录，以及要写入的新值
```

例如初始 `A = 100, B = 100`，执行 `B = A + B`：

```text
read_set  = { A: 原版本 vA, B: 原版本 vB }
write_set = { B: 200 }

此时共享存储中的 B 仍然是 100。
只有提交成功，200 才会被发布。
```

写集合通常只保留该事务对每条记录的最终待写值。事务自己随后读取已经写过的记录时，应当读到自己的私有修改，即 **read your own writes**。

**补充理解：**可以把“私有数据值”和“用于验证的原始版本”分开保存：

```text
Read(tx, x):
    if x in tx.write_set:
        return tx.write_set[x]
    if x in tx.read_cache:
        return tx.read_cache[x]
    value, version = read_record_consistently(x)
    tx.read_cache[x] = value
    tx.read_set[x] = version
    return value

Write(tx, x, value):
    tx.write_set[x] = value
```

这里缓存重复读取是便于理解的一种实现。关键是：**私有写入不能把验证所需的原始共享版本覆盖掉。**

### 2.3 为什么读取也需要原子性？

执行阶段没有长期持锁，不代表可以读到撕裂的数据。例如实际状态从 `(value=100, version=7)` 更新为 `(110,8)`，不能把旧值 100 和新版本 8 错配起来。

读取接口必须取得一致的记录内容与版本；可以由原子记录访问、版本前后检查等协议实现。课件的“read 必须 atomic”是在要求这个基础保证。

**表述边界：**一次记录读取正确，不代表整个读集合已经是一个一致快照。普通 OCC 还要依赖提交验证，决定这些读取能否共同构成一次合法执行。

## 3. 验证与提交为什么必须协调为一个整体？

对应讲义页 6–8，PDF 第 8–18 页。

两个事务都执行：

```text
A += 1
B += 1
```

初始 `A = B = 1`。如果“检查通过”和“安装修改”之间没有保护，就可能发生：

| 步骤 | T1 | T2 | 共享 `(A,B)` |
| --- | --- | --- | --- |
| 1 | 读取 `(1,1)`，私有计算 `(2,2)` | | `(1,1)` |
| 2 | | 读取 `(1,1)`，私有计算 `(2,2)` | `(1,1)` |
| 3 | 验证通过 | | `(1,1)` |
| 4 | | 验证也通过 | `(1,1)` |
| 5 | 写入 `(2,2)` | | `(2,2)` |
| 6 | | 写入 `(2,2)` | `(2,2)` |

任意串行顺序都应得到 `(3,3)`，实际却只增加了一次。

问题不在于验证条件漏写，而在于：**检查结果只对检查当时成立，不能无条件授权之后的写入。**

课件先用一个临界区包住 Phase 2 与 Phase 3：

```text
取得提交阶段的保护
    检查所有读取依据
    若失败：中止
    若成功：安装所有待写结果
释放保护
```

后续可以把全局保护细化为逐记录的协议，但必须继续排除上述“两边都通过旧检查，然后都写入”的执行。

## 4. 检查值，还是检查版本？ABA 问题

对应讲义页 9–10，PDF 第 19–27 页。

### 4.1 两种检查并不等价

| 检查方式 | 保存什么 | 能检测到什么？ |
| --- | --- | --- |
| 比较值 | 当时读到的 value | 当前值与过去值不同 |
| 比较版本 | 当时读到的 version | 自读取之后是否发生了更新 |

若值经历 `1 → 2 → 1`，再次比较值会认为“没变化”，比较持续递增的版本则能发现它已经被改过。这就是 **ABA problem**：对象表面上回到原样，但更新历史已经不同。

### 4.2 课件中的三个事务

```text
T1：A += 1
T2：A += 1
T3：A = 1
初始：A = 1，version = 0
```

| 步骤 | 动作 | 共享 `(A, version)` |
| --- | --- | --- |
| 1 | T1 读取 A=1，保存版本 0，私有结果为 2 | `(1,0)` |
| 2 | T2 也读到 A=1，验证后提交 A=2 | `(2,1)` |
| 3 | T3 提交 A=1 | `(1,2)` |
| 4 | T1 开始验证 | 当前值仍为 1，但当前版本已为 2 |

只比较值会让 T1 通过；比较版本会中止 T1。

按 LEC 8 的冲突关系：

```text
T1.R(A) 在 T2.W(A) 之前：T1 → T2
T2.R(A) 在 T1.W(A) 之前：T2 → T1
```

若让 T1 提交，就形成冲突环，无法保留这些冲突关系并排成串行执行。

**表述边界：**这里不能仅凭“最终 A=2”证明错误；某些串行顺序同样能得到 2。该例说明，比较相同数值不足以证明“记录从未变化”，也不足以保证课件采用的冲突可串行化。若按视图等价分析，还必须保留读取来源，不能把 T1 读取初始版本与读取 T3 写回的 1 当成同一次读取。

版本机制本身也有前提：每次提交更新都必须推进版本；版本不能在仍有事务引用旧版本时被重用，否则版本号也可能出现 ABA。

## 5. OCC 的提交阶段：从全局锁到只锁写集合

对应讲义页 11–16，PDF 第 28–47 页。

### 5.1 方案一：全局锁

```text
ValidateAndCommit(tx):
    acquire(global_commit_lock)
    try:
        for x in tx.read_set:
            if current_version(x) != tx.read_set[x]:
                return ABORT
        for x, value in tx.write_set:
            publish_value_and_advance_version(x, value)
        return COMMIT
    finally:
        release(global_commit_lock)
```

所有提交者遵守同一把锁，T1 完成验证与安装后，T2 才能开始验证。第 3 节的双增量例子中，T2 会发现版本改变，丢弃旧结果；重新读取 `(2,2)` 后才能计算出 `(3,3)`。

**为什么还有并发？** 执行业务逻辑的 Phase 1 仍可并发。全局锁只覆盖验证和安装，通常比包住整个事务更短，但很大的读写集合仍会拉长这段临界区。

**补充理解：**Phase 1 的读者没有持有这把全局锁，因此可能读到一个正在安装中的组合。基础 OCC 可以在最终验证时拒绝这次执行；若要求连未提交事务都不能基于不一致数据运行，还需要更强的读取保护。不可撤销的输出应在提交成功后发布。

### 5.2 方案二：锁住读集合与写集合的并集

```text
按统一顺序锁住 read_set ∪ write_set
→ 验证原始读版本
→ 安装写集合
→ 释放全部锁
```

这样，没有共同访问记录的事务可以同时提交。

两个实现细节：

- **先去重，再排序。** 同一记录可能既在读集合也在写集合中。
- **按全局统一顺序取锁。** 只说“使用 2PL”仍不能排除死锁；排序才排除了循环等待。

### 5.3 错误优化：只锁写集合，只检查读版本

课件接着尝试减少读集合上的锁：

```text
锁住 write_set
→ 检查 read_set 的版本未变
→ 安装 write_set
```

这个版本仍然不正确。令初始 `A = B = 1`：

```text
T1：A = A + B       write_set = {A}
T2：B = B + A       write_set = {B}
```

| 步骤 | T1 | T2 |
| --- | --- | --- |
| 1 | 读取旧 A=1、B=1，准备 A=2 | 读取旧 A=1、B=1，准备 B=2 |
| 2 | 锁住 A | 锁住 B |
| 3 | 检查 B 版本未变，通过 | 检查 A 版本未变，通过 |
| 4 | 安装 A=2 | 安装 B=2 |

最终 `(A,B)=(2,2)`。串行 `T1 → T2` 应为 `(2,3)`；串行 `T2 → T1` 应为 `(3,2)`。

**写集合不相交，不代表没有依赖。** T1 读取了 T2 将要写的 B，T2 读取了 T1 将要写的 A。

### 5.4 改进：还要检查读取记录是否被其他事务锁住

课件的下一版是：

```text
ValidateAndCommit(tx):
    按统一顺序取得 tx.write_set 的全部锁
    try:
        for x, original_version in tx.read_set:
            version, owner = read_version_and_lock_state_consistently(x)
            if version != original_version:
                return ABORT
            if owner != NONE and owner != tx:
                return ABORT
        安装所有私有写入，并更新对应版本
        return COMMIT
    finally:
        释放本事务已经取得的全部锁
```

在上例中，T1 验证 B 时发现 B 已被 T2 锁住；T2 验证 A 时也可能发现 A 被 T1 锁住。协议会中止冲突事务，而不是让两者都凭旧版本通过。

两种检查各自覆盖一种情况：

| 检查 | 发现的风险 |
| --- | --- |
| 版本改变 | 别的事务已经发布过更新，当前计算依据过时 |
| 被其他事务锁住 | 别的事务正在准备或执行更新，即使版本暂时还没变化 |

**课件补全：**“被锁住就中止”要排除本事务自己持有的写锁，否则普通的 `A += 1` 也会被自己中止。版本、锁状态、数据发布还必须遵循一致的原子访问和内存可见性协议；不能把伪代码中的普通字段读取直接当成完整的并发实现。

**这一优化保留了 OCC 的特点：执行阶段不长期持锁，提交阶段才短暂保护写集合。**

## 6. 锁为什么有成本：CAS 与自旋锁

对应讲义页 17–22，PDF 第 48–53 页。

### 6.1 取得锁本身也需要原子性

下面的普通代码不能实现互斥：

```text
if flag == 0:
    flag = 1
    进入临界区
```

两个线程可能都先读到 0，然后都写入 1，同时进入临界区。锁需要把“检查”和“占用”做成一个不可插入的动作。

**Compare-and-swap / compare-and-exchange（CAS）**提供这种硬件原语。沿用课件“返回旧值”的接口：

```text
CAS(address, expected, desired):        # 整体由硬件原子执行
    old = *address
    if old == expected:
        *address = desired
    return old
```

这里的多行代码只用于描述语义，不是用普通读写实现 CAS 的方法。

### 6.2 最简单的 spin lock

```text
Lock(lock):
    while CAS(lock.flag, 0, 1) != 0:
        spin

Unlock(lock):
    atomic_store_release(lock.flag, 0)
```

成功把 0 改成 1 的线程得到锁，其余线程循环等待。真实实现中，取得锁需要相应的 acquire 语义，解锁需要 release 语义，以保证临界区的数据按正确顺序可见。

**表述边界：**“解锁可以不用 CAS”不等于“用任意普通变量写入即可”；还需要原子存储、内存顺序和语言层面的同步保证。自旋锁适合的等待时长也有限，长时间空转会占用 CPU。

### 6.3 OCC 为什么可能更便宜？

对一条只读记录，在没有重试的理想情形下：

| 方案 | 课件概括的主要操作 |
| --- | --- |
| OCC | 读取数据；验证版本和锁状态 |
| 2PL | 取得锁，通常含原子读改写；读取数据；释放锁 |

读取已缓存的数据通常比争夺并修改共享锁状态便宜。课件用 L1 访问约 1 ns、一次 mutex lock/unlock 约 17 ns 说明量级差异。

这些数值是课件引用的示意数据，不能当成当前所有 CPU、锁实现和竞争程度下的固定延迟。**需要记住的是同步有额外成本，而非某个恒定倍数。**

## 7. OCC 的代价：false abort、重试与活锁

对应讲义页 23–26，PDF 第 54–66 页。

### 7.1 False abort：本来存在串行解释，却仍被拒绝

初始 `A = B = 100`：

```text
T1：B = A + B
T2：A = A × 1.1
```

执行顺序：

```text
T1 读 A=100、B=100，私有计算 B=200
T2 读 A=100，提交 A=110
T1 验证 A，发现它已经变化，于是中止
```

但是，如果允许 T1 发布 B=200，整个结果可以解释为：

```text
串行 T1 → T2：
    T1 把 B 改成 200
    T2 把 A 改成 110
    最终 (A,B) = (110,200)
```

这里的数据依赖只有 `T1 → T2`，没有环。**存在合法串行顺序，不代表某个具体 OCC 验证器一定会接受。**

课件中的简单方案要求 T1 的读集合在验证时仍然有效；T2 先提交后，T1 就不能再沿用旧 A。它不能把这次较晚验证的 T1 放回 T2 之前，因此发生 **false abort（不必要的中止）**。

**表述边界：**这是课件所用验证规则的限制，不是所有 OCC 算法都只能采用同一种串行顺序。

### 7.2 读集合越大，执行越久，重试风险越高

只要读集合中的某条记录被更新，整个事务就可能重来：

```text
读取许多记录、执行很久
    ↓
更容易与其他事务的更新重叠
    ↓
提交时验证失败
    ↓
此前计算被丢弃，重试又增加系统负载
```

持续重试却不能完成事务，课件称为 livelock（活锁）。也可能出现系统总体仍有吞吐，但某个长事务一直失败的 starvation（饥饿）。

常见缓解思路包括退避、调整优先级、限制重试次数或回退到加锁路径；具体策略仍需保证进展，不能只写一个无限重试循环。

### 7.3 2PL 与 OCC 的性能取舍

| 情形 | 2PL 的主要代价 | OCC 的主要代价 |
| --- | --- | --- |
| 冲突少、事务短 | 仍需要取得和释放锁 | 验证通常便宜，很少浪费计算 |
| 冲突多 | 等待、持锁、死锁处理 | 频繁中止，重复执行已经做过的工作 |
| 事务长、读集合大 | 长期持锁容易阻塞别人 | 验证失败概率和重做成本可能很高 |

课件的趋势图展示 OCC 在低竞争时较好、竞争增加后可能低于 2PL。它说明工作负载会改变取舍，不是“所有系统在某个固定并发数必然交叉”的定律。

**“OCC 没有死锁”也需要限定：**执行阶段不持锁可以避免这一阶段的锁等待环；若提交阶段仍使用多把阻塞锁，就还需要统一取锁顺序等措施。

## 8. HTM / RTM：让 CPU 执行内存事务

对应讲义页 27–33，PDF 第 68–79 页。

**Hardware transactional memory（硬件事务内存，HTM）**让 CPU 把一段受支持的内存操作作为事务执行。课件以 Intel 的 **Restricted Transactional Memory（RTM）**为例。

### 8.1 三个基本操作

| 操作 | 含义 |
| --- | --- |
| `xbegin` / `_xbegin()` | 开始尝试事务执行 |
| `xend` / `_xend()` | 尝试提交事务 |
| `xabort` / `_xabort(...)` | 显式中止事务 |

```text
if _xbegin() == STARTED:
    执行需要保护的内存访问
    _xend()
else:
    执行失败后的处理路径
```

成功时，事务的内存修改整体生效；中止时，事务内的推测性修改被撤销，控制流转到回退路径。

### 8.2 普通写入也会与 RTM 区域冲突

```text
CPU 0：开始 RTM → 读 x=0 → ……
CPU 1：普通代码执行 x=1
CPU 0：检测到冲突，中止事务，进入回退路径
```

CPU 1 不需要也进入 RTM，硬件仍可检测它与事务读集合的冲突。课件的示例由事务中止让普通写入继续，不是让普通写入等待整个 RTM 区域完成。

**表述边界：**这不意味着随便把一小段代码放进 RTM，就能让整个应用免于竞争。业务动作的边界、普通访问与事务访问的关系、回退路径的同步，都仍需正确设计。

### 8.3 为什么不能无限重试？

RTM **不保证某次重试最终成功**。如果失败来自容量限制或不适合事务执行的操作，一直重做同一段代码也不会解决原因。

完整的使用思路是有限次尝试，然后回退：

```text
RunWithRTM():
    for attempt in bounded_attempts:
        if _xbegin() == STARTED:
            if fallback_lock.is_held():
                _xabort(EXPLICIT_ABORT_CODE)
            critical_work()
            _xend()
            return
        # 可以结合中止原因决定是否继续尝试

    acquire(fallback_lock)
    try:
        critical_work()
    finally:
        release(fallback_lock)
```

这里所有回退执行者使用同一把锁，RTM 路径也必须在访问受保护数据前读取它。

### 8.4 为什么 RTM 路径要检查回退锁？

否则，普通加锁路径以为自己在独占执行，RTM 路径却可能同时进入。

在 RTM 内读取锁状态有两重作用：

1. 锁已经被持有时，主动中止，避免和回退执行者重叠。
2. 读取后，锁所在缓存行进入事务读集合；若另一 CPU 随后取得这把锁，其更新会与事务冲突。

**快路径与回退路径必须共享同一套保护关系。** 仅在失败分支里调用一次 `lock.acquire()`，还不构成完整方案；回退分支还必须执行工作并释放锁。

## 9. RTM 为什么快，又为什么受限？

对应讲义页 34–38，PDF 第 80–89 页。

### 9.1 可以把它理解为硬件实现的乐观执行

课件用 OCC 来解释 RTM：

```text
读取 / 写入内存
    ↓
CPU 用缓存相关机制跟踪事务读写集合
    ↓
利用缓存一致性协议发现冲突
    ↓
提交推测性写入，或中止并撤销
```

示例中，CPU 0 已把 x 所在缓存行纳入读集合；CPU 1 为写入 x 请求独占权限，引发失效与冲突检测，CPU 0 的事务因此中止。

**补充理解：**跟踪通常以缓存行为单位。两个线程访问不同变量，但变量位于同一缓存行，也可能产生事务冲突。因此“逻辑上不是同一记录”不一定意味着硬件上没有竞争。

### 9.2 容量限制：读写集合不是无限大的

缓存等硬件跟踪资源有限，工作集过大可能导致 **capacity abort（容量中止）**。

课件引用的实验图中，写集合容量明显小于读集合容量，分别标注约 31 KB 与 4 MB。这是特定硬件和访问方式下的测量，不是 RTM 接口对所有处理器的保证。

要记住的关系是：

```text
读写集合变大 → 更容易超出跟踪能力 → 即使没有其他事务，也可能中止
```

### 9.3 外部事件：没有数据冲突，也不保证成功

中断等事件同样可能中止事务。事务执行越久，遇到这类事件的机会通常越大。

课件的实验图标注约 3.9 ms 的执行时长边界；它是该实验环境的现象，不能理解成“RTM 一律保证执行到 3.9 ms”或统一的架构时限。

### 9.4 硬件事务并非总比软件 OCC 快

课件比较了 HTM 与软件 OCC 系统 Silo：

- **SmallBank：**事务相对简单，HTM 在图示实验中吞吐较高。
- **TPC-C：**事务更复杂、工作集更大，HTM 在图示实验中的表现较差，软件 OCC 更有优势。

课件对 Silo 的评价处在其引用研究的背景中，不应读成当前系统的性能排名。

**HTM 的优势依赖于事务能否经常成功完成。** 它把很多跟踪工作放进硬件，但容量、外部事件、冲突和回退路径仍决定实际成本。

**与 LEC 7 的边界：**RTM 的 all-or-nothing 指运行期间内存事务的提交或撤销，不自动提供断电后的持久性，也不能替代磁盘日志、恢复或不可撤销外部操作的协调。

## 10. 把几讲连起来：事务与 ACID

对应讲义页 39–46，PDF 第 91–99 页。

事务是管理一组数据操作的抽象：程序用 `begin` 与 `commit` 标出需要一起保护的范围。数据可以是账户、库存、键值记录，也可以是 inode 和目录项。

例如扣库存与加入购物车：

```text
begin
    if item.count > 0:
        item.count -= 1
        cart.add(item)
commit
```

事务边界告诉系统：检查库存、扣减、加入购物车是一个业务动作。如果只保护其中一个写操作，仍可能破坏业务约束。

### 10.1 ACID 的四项保证

| 字母 | 名称 | 核心含义 | 对应机制或责任 |
| --- | --- | --- | --- |
| A | Atomicity，原子性 | 事务全部生效或全部撤销 | 日志、恢复、私有更新等 |
| C | Consistency，一致性 | 从满足应用约束的状态到另一个满足约束的状态 | 正确的事务逻辑、数据库约束等 |
| I | Isolation，隔离性 | 限制并发事务相互影响；本课程理想目标是可串行化 | 2PL、OCC、适当的多版本协议等 |
| D | Durability，持久性 | 已提交结果在系统承诺的故障模型下不会丢失 | 持久化日志、恢复等 |

**ACID 的 C 与 LEC 6 的复制一致性模型不是同一个概念。** 这里的 C 关注业务不变量，例如转账不改变账户总额。

### 10.2 原子性中的提交点

```text
提交之前：必须保留撤销能力
          ↓
       commit point
          ↓
提交之后：必须能够完成已经承诺的结果
```

这与 [LEC 7](LEC-7-All-or-nothing-atomicity.md) 的恢复日志相衔接。持久性不要求提交时所有主数据页都已经写回；若持久化的日志足以在崩溃后恢复结果，也可以满足相应承诺。

### 10.3 可串行化为什么有助于保证 C？

假设：初始状态满足业务约束，而且每个事务单独执行时都能保持这些约束。

```text
一致状态 C0
  → T1 → 一致状态 C1
  → T2 → 一致状态 C2
  → ……
  → Tn → 一致状态 Cn
```

若并发执行等价于某个这样的串行顺序，就可以复用单线程正确性的推理。

但事务系统不会自动修复业务代码：转账扣两倍的钱却只加一倍，即使完全串行也会出错。反过来，如果采用比可串行化更弱的隔离级别，“每个事务单独正确”也未必足以保证并发正确。

## 11. MVCC 的动机：让长时间读者继续读旧快照

对应讲义页 48–51，PDF 第 106–122 页。

### 11.1 只读事务为什么被普通 OCC 中止？

```text
T1：读取 A、B，准备返回 A+B
T2：更新 A、B
```

如果 T1 已经读到了更新前完整的 A、B，但在验证之前 T2 提交，OCC 会发现读集合变化，使 T1 中止。

然而，T1 读到的结果本来可以解释为“先执行 T1，再执行 T2”。如果可以让它始终读取同一个旧快照，就不一定需要重做。

更棘手的情形是：T1 先读旧 A，T2 更新 A、B，T1 再读取 B。单版本存储可能只剩新 B，T1 就得到旧 A 与新 B 的混合。

### 11.2 保留多个版本

**Multi-version concurrency control（多版本并发控制，MVCC）**保留记录的历史版本，写入时增加新版本，读者按同一个快照规则选择版本。

```text
A 的版本链：A@12 → A@7 → A@0
B 的版本链：B@15 → B@4 → B@0

若事务读取时间戳为 10 的快照：
    读取 A@7
    读取 B@4
```

**一致快照不要求所有记录的版本号相同。** 它要求每条记录都取“同一个快照边界之前，最近一次可见的更新”。

新事务可以读新版本，旧事务仍可读旧版本。后来的更新不需要覆盖并破坏旧事务的读取依据。

**表述边界：**MVCC 是一类机制，不是某个固定隔离级别的同义词。是否可串行化，还要看读写冲突、版本可见性与提交验证的具体规则。

## 12. 用时间戳选择快照：start time 与 commit time

对应讲义页 51–53，PDF 第 121–125 页。

### 12.1 两个时间戳的职责

| 记号 | 含义 | 用途 |
| --- | --- | --- |
| `T.sts` | Start timestamp，事务开始时取得 | 决定事务读取哪个快照 |
| `T.cts` | Commit timestamp，为本次提交分配 | 标记本事务产生的新版本 |
| `X(i).cts` | 记录 X 的某个版本的提交时间戳 | 判断该版本能否被某个快照读取 |

读取规则：

```text
在所有 X(i).cts <= T.sts 的可见版本中，
选择 X(i).cts 最大的那个版本。
```

它是“不晚于开始时间的最新版本”，不是单纯按时间差选“最近”的版本；比 `T.sts` 更新的版本不能读。

### 12.2 用全局计数器生成时间戳

课件使用原子的 **fetch-and-add（FAA）**分配单调递增序号。这里为便于阅读，把生成下一个序号记作 `next_timestamp()`。

```text
事务开始：T.sts = next_timestamp()
准备发布：T.cts = next_timestamp()
```

这是逻辑时间，不需要等于时钟的真实日期或纳秒数。

**课件校正：**“先结束的事务具有更小的开始时间戳”对重叠事务并不成立。一个后开始的短事务可能先提交。能保证的是时间戳按其分配操作排序；若 T1 已完成、T2 才开始，则 T1 的提交时间戳早于 T2 的开始时间戳。

此外，**取得提交时间戳不等于所有新版本已安装完成**。下面的 partial snapshot 问题正来自这个间隙。

## 13. 第一个陷阱：有版本号，仍可能读到半个快照

对应讲义页 53–56，PDF 第 124–142 页。

### 13.1 不完整方案

初始只有 `A@0、B@0`。T2 要把 A 改成 3、B 改成 2，并为整个事务分配 `cts=1`：

```text
T2：取得 cts=1 → 安装 B@1 → …… → 安装 A@1
```

如果 T1 在中途取得 `sts=2`，而读者不检查记录是否正在提交：

| 步骤 | T2 | T1 |
| --- | --- | --- |
| 1 | 取得 cts=1 | |
| 2 | 安装 B@1，A@1 尚未安装 | |
| 3 | | 开始，取得 sts=2 |
| 4 | | 读取 A：目前只找到 A@0 |
| 5 | | 读取 B：找到符合 `cts <= 2` 的 B@1 |
| 6 | 安装 A@1 | |

T1 得到 `(A@0, B@1)`，既不是 T2 之前的状态，也不是 T2 之后的状态。

**版本过滤只能在已经存在的版本中选择，不能凭空读到还没安装的 A@1。** 因此多版本存储仍需要处理多记录提交的可见性。

### 13.2 课件方案：先锁齐写集合，再分配提交时间戳

```text
Commit(tx):
    按统一顺序取得写集合的全部锁
    commit_ts = next_timestamp()
    for x, value in tx.write_set:
        为 x 安装版本 (commit_ts, value)
        release(x)

Get(tx, x):
    等待 x 不处于写入锁定状态
    安全遍历 x 的版本链
    返回其中 cts <= tx.sts 的最新版本
```

这是本节解释快照可见性的中间方案，**还没有加入后文的写冲突验证**。也假设安装阶段能够完成，不在已经发布部分新版本后任意中止。

回到上例：

```text
T2：锁住 A、B → cts=1 → 安装 B@1，释放 B → 安装 A@1，释放 A
T1：                         sts=2 → 读 A 时等待 → 读 A@1、B@1
```

未安装完的 A 仍被锁住，T1 不会直接退回 A@0。B 即使已经释放，其新版本也已存在。等 T1 完成读取，两个结果就都来自 T2 之后的快照。

**课件表述补全：**不是“安装期间所有写记录始终都被锁住”；示例允许已安装的记录提前解锁。真正重要的是：分配 `cts` 之前已经锁齐，某条记录的新版本尚未安装时，不能先释放它的锁。

### 13.3 为什么不能先分配 cts，再去取锁？

若反过来：

```text
T2 先取得 cts=1，但还没有锁住 A
T1 取得 sts=2，见 A 未锁，直接读到 A@0
T2 再锁 A、B，安装 A@1、B@1
T1 后来读到 B@1
```

混合快照重新出现。

正确顺序使得：**凡是时间戳已经落入读者快照范围、却尚未安装完成的写入，都能通过已持有的锁挡住过早读取。**

若写事务是在读者开始之后才取得提交时间戳，那么其新版本满足 `cts > reader.sts`，读者本来就应跳过它。

### 13.4 “读者不持锁”不等于“永不等待”

这个方案中的读者不长期占有记录锁，但可能等正在安装版本的写者。版本链也必须支持安全的并发遍历和发布，不能把可变容器上的普通遍历当成天然线程安全。

**补充理解：**实际 MVCC 系统还可以通过事务提交状态等机制控制可见性；课件的等待锁方案是帮助理解原子发布要求的一种设计。

## 14. 第二个陷阱：一致快照仍会丢失更新

对应讲义页 57–59，PDF 第 143–157 页。

### 14.1 给每次写入新版本，并不能让旧计算自动正确

初始 `A@0 = 0`，两个事务都执行 `A += 1`：

| 事务 | 开始时间 | 读取 | 私有结果 | 准备安装的版本 |
| --- | --- | --- | --- | --- |
| T1 | `sts=1` | `A@0 = 0` | 1 | `A@3 = 1` |
| T2 | `sts=2` | `A@0 = 0` | 1 | `A@4 = 1` |

虽然两个写入可以依次取得锁，最终版本链仍可能是：

```text
A@4=1 → A@3=1 → A@0=0
```

最新值是 1，串行执行两个加一应该得到 2。

**只把安装步骤串行化不够；T2 的计算结果早已基于过时的 A@0 产生。**

### 14.2 提交前检查写写冲突

在持有写集合锁的情况下，对每个待写记录 X 检查：

```text
if latest_committed_version(X).cts > T.sts:
    abort T
```

这表示：T 开始后，另一个事务已经更新了 T 也想写的记录。

在例子中，T1 安装了 `A@3`；T2 提交时发现 `3 > 2`，于是中止。它重新开始后读到 1，再计算 2，才不会覆盖掉 T1 的增量。

**课件补全：**检查范围是本事务的写集合，不是“系统里任何记录在我开始后更新过，就全部中止”。检查与安装之间也必须继续持有相应保护，避免另一个写者插入。

### 14.3 当前方案的完整流程

```text
Begin:
    T.sts = next_timestamp()

Read(X):
    若 X 已在本事务的私有写集合中，返回私有值
    否则按前述可见性协议读取最新的 X(i).cts <= T.sts

Write(X, value):
    只更新私有写集合

Commit:
    1. 按统一顺序取得写集合的全部锁
    2. 对写集合中每条记录检查 latest.cts <= T.sts
       若失败，释放已持有的锁并中止
    3. 分配 T.cts
    4. 给写集合的所有记录安装带 T.cts 的新版本
    5. 释放锁，完成提交
```

这里把锁保留到全部安装完成，便于表达；课件前面的可见性方案也允许一条记录安装好后再释放该记录的锁。

这套规则已经防止刚才的并发写覆盖，**但还没有得到完整的可串行化保证**。

## 15. 第三个陷阱：write skew 与快照隔离

对应讲义页 60–61，PDF 第 159–170 页。

### 15.1 写不同记录，也能破坏跨记录约束

课件中的结构是：

```text
T1：读取旧 X，写 Y
T2：读取旧 Y，写 X
```

两个事务使用各自的一致快照，写集合分别为 `{Y}` 与 `{X}`，所以前一节的写写冲突检查可能全部通过。

但依赖关系要求：

```text
T1 读到了 T2 更新之前的 X：T1 → T2
T2 读到了 T1 更新之前的 Y：T2 → T1
```

出现环，无法安排成满足这些读取关系的串行顺序。这种异常称为 **write skew（写偏斜）**。

这里按“读到旧版本，相应写者应排在其后”的版本依赖画边；不能忽略版本，机械地把所有物理读写时刻套进单版本分析。

### 15.2 具体应用：至少留一人值班

**补充示例：**令 `X=1` 表示甲值班，`Y=1` 表示乙值班。业务约束是：

```text
X + Y >= 1
```

初始 `X=Y=1`，两人同时申请下班：

```text
T1（乙下班）：
    if X == 1:
        Y = 0

T2（甲下班）：
    if Y == 1:
        X = 0
```

两者都从快照里看到对方在岗，于是各自把自己的状态改成 0。写集合不相交，都可能提交，最终 `X=Y=0`，无人值班。

串行执行则不会如此：

| 串行顺序 | 结果 |
| --- | --- |
| T1 → T2 | T1 使 Y=0，T2 随后发现乙不在岗，保持 X=1 |
| T2 → T1 | T2 使 X=0，T1 随后发现甲不在岗，保持 Y=1 |

**每次读取都来自完整快照、每个事务单独都正确、没有写同一记录，三者同时成立仍不足以保证并发业务正确。**

### 15.3 Snapshot isolation 到底保证了什么？

课件把当前“按开始时快照读取 + 检查写写冲突”的方案称为 **snapshot isolation（快照隔离，SI）**。

| 检查项 | 这里的 SI |
| --- | --- |
| 一个事务是否按固定快照读取？ | 是 |
| 是否允许读取另一个事务未完成发布的部分更新？ | 正确的可见性协议会阻止 |
| 两个重叠事务是否能无条件更新同一记录？ | 不能，需要写写冲突检查 |
| 写集合不相交的事务是否一定安全？ | 不一定，可能 write skew |
| 是否等价于 serializability？ | 否 |

**MVCC 与 SI 不可画等号。** MVCC 是多版本机制；SI 是采用特定读写规则得到的一种隔离级别。多版本机制也可以用于实现更强的隔离。

## 16. 修复 write skew：读写事务仍要验证读取依据

对应讲义页 61–62，PDF 第 170–171 页。

课件给出的直接修复方向：

```text
只读事务：读取一致快照，避免普通 OCC 的读集合末尾验证

读写事务：除写写冲突外，还检查 read_set 中的读取依据
          验证与发布继续按 OCC 所需的协议协调
```

回到值班例子，如果 T1 已修改 Y，那么 T2 提交时验证自己读过的 Y，就能发现它已经不再是原先的版本，从而中止。

还必须考虑两者同时验证的情形：如果两边都检查完旧版本，再各自安装，错误仍会出现。因此，**“增加读集合验证”必须连同第 5 节中的提交保护一起理解**，例如使用正确的全局提交临界区，或版本与锁状态检查协议。

**表述边界：**“只读事务永不 abort”在这里指：正常执行模型中，不因后来写者让旧快照过时而发生这种验证中止。它不是对故障、资源不足、取消或历史版本不可用的普遍保证。也不能因此推出所有 SI 读写事务可串行化。

**补充理解：**保留历史版本会增加存储与回收成本。只要仍有活跃事务可能读取某个旧版本，就不能随意回收它；长时间读者虽然减少了重试，却可能延缓版本清理。

## 17. 并发控制方法对照

对应讲义页 26、38、47–48、61–62。

| 方法 | 执行阶段 | 冲突如何处理 | 主要优势 | 主要限制 |
| --- | --- | --- | --- | --- |
| 2PL | 访问前取得锁，遵守增长/收缩阶段 | 等待，或中止某个事务解除冲突 | 在协议前提下保证冲突可串行化 | 锁成本、等待、死锁 |
| 单版本 OCC | 私有执行，记录读写集合 | 提交时验证，失败则重做 | 冲突少时避免长时间持锁 | false abort、重复计算、饥饿 |
| HTM / RTM | CPU 跟踪事务内存访问 | 硬件检测冲突并中止 | 符合条件的小事务可降低软件管理成本 | 容量、外部事件、必须有回退路径 |
| MVCC + SI | 读取开始时快照，缓冲写入 | 写集合冲突时中止 | 只读事务不因新版本出现而重新验证 | write skew，历史版本管理 |
| MVCC + 可串行化协议 | 使用多版本，并协调必要的数据依赖 | 验证、锁或其他依赖控制 | 保留多版本读取优势，同时提供更强隔离 | 仍有额外协调成本 |

这些方法不是完全互斥的选项：OCC 的提交阶段可以用锁，RTM 可以回退到锁，多版本也可以与 OCC 或 2PL 结合。

### 17.1 复习时抓住的八条规则

1. **OCC 的执行结果先放在私有空间。** 验证通过之前不能把业务修改当成已提交结果发布。
2. **验证和安装必须共同协调。** 不能在检查通过后留下无保护的写入窗口。
3. **相同值不代表同一版本。** ABA 的关键是更新历史被数值比较掩盖。
4. **只锁写集合时，还要处理读写依赖。** 只看版本未变，可能漏掉正在准备写入的事务。
5. **RTM 不保证成功或持久化。** 有限次重试、正确回退、故障恢复分别有自己的职责。
6. **快照需要统一的可见性边界。** 多版本和时间戳不能自动防止半个提交被读到。
7. **写写冲突检查防不住 write skew。** 业务约束可能跨越不同记录。
8. **MVCC 是机制，可串行化是保证。** 判断正确性必须检查完整协议，而不能只看技术名字。

### 17.2 做本讲调度题的顺序

```text
① 写出初始值、各事务的读集合和写集合。
② 区分私有写入与真正发布到共享存储的写入。
③ OCC：检查读取版本、写锁拥有者、验证与安装能否被插入。
④ MVCC：标出 sts / cts，逐次确定读到哪个版本。
⑤ 检查是否存在尚未安装完、却已落入读者快照的更新。
⑥ 检查写集合是否有 latest.cts > sts 的记录。
⑦ 即使写集合不相交，也要画出旧版本读取产生的数据依赖。
⑧ 找串行解释，并核对应用不变量，而不是只看最终数值。
```

## 18. 复习自测

1. **OCC 为什么先把写入放在私有缓冲区？**  
   便于在验证失败时直接丢弃结果，也避免把未经验证的业务修改提前暴露为已提交数据。

2. **Phase 1 不持锁，是否意味着每次读取可以不管原子性？**  
   不可以。至少要取得一致的记录值和版本，避免数据撕裂或值与版本错配。

3. **两个事务都验证成功，是否足以证明都能提交？**  
   不足以；若验证与安装没有共同保护，两者可能都基于旧状态通过检查。

4. **`A: 1 → 2 → 1` 后，比较值与比较版本有什么不同？**  
   比较值可能通过，持续更新的版本会暴露中间发生过的修改。

5. **OCC 在提交阶段用了全局锁，为什么仍可能比全事务加锁更有并发性？**  
   本地读取与计算仍能并发，锁只覆盖验证和安装阶段。

6. **只锁 write set，再验证 read set 的版本，为什么不够？**  
   别的事务可能已经锁住并准备写入某个读取记录，只是尚未推进版本；两者会同时通过旧检查。

7. **验证时发现记录被锁，一定要中止吗？**  
   要区分锁拥有者。自己为写集合持有的锁不构成这类冲突，其他事务持有的锁才需要按协议处理。

8. **所有事务在提交时都遵守 2PL，是否自动没有死锁？**  
   不自动。还需要统一取锁顺序、无等待策略等进展机制。

9. **False abort 是否意味着允许了错误结果？**  
   不是。它是保守地拒绝了本来可以找到合法串行解释的执行，损失主要是性能。

10. **为什么长时间只读事务对单版本 OCC 不友好？**  
    读集合大、执行时间长，更容易在验证前遇到记录更新，导致大量读取工作重做。

11. **一个普通非事务写入，能让另一个 CPU 的 RTM 事务中止吗？**  
    能。硬件可以检测普通访问与事务读写集合的冲突。

12. **RTM 没有数据冲突，是否就一定能成功？**  
    不一定。容量限制、中断等原因仍可能导致中止，所以不能依赖无限重试。

13. **为什么 RTM 快路径要读取回退锁？**  
    既能发现已有回退执行者，也能让之后的取锁更新与 RTM 的读集合发生冲突。

14. **RTM 提交成功，是否等于数据库事务已持久化？**  
    不等于。内存事务的原子提交不自动提供断电恢复能力。

15. **ACID 的 C 能否自动修复写错的转账代码？**  
    不能。应用逻辑和约束必须正确，隔离性只是帮助组合这些正确的单事务操作。

16. **快照时间为 10，X 有版本 0、7、12，读取哪个？**  
    在版本可见性协议成立时读取 7，即不大于 10 的最大版本；不能读取 12。

17. **同一快照中，A 的版本为 7、B 的版本为 4，是否一定不一致？**  
    不是。只要两者都是同一快照边界之前各自最新的可见版本，就可以属于一致快照。

18. **为什么安装了一半新版本时，版本过滤本身还不够？**  
    缺失的新版本无法被过滤器选中，读者可能对某条记录选旧版本、对另一条选新版本。

19. **课件的 MVCC 协议为什么先锁齐写集合，再取得 cts？**  
    保证已经属于读者快照范围、但尚未完成安装的更新，会被记录锁挡住，而不是被读者遗漏。

20. **两个事务都读 A=0，分别安装 A@3=1、A@4=1，有什么问题？**  
    两次加一的一个效果丢失了。后提交者应发现该记录的新版本晚于自己的开始时间并中止。

21. **写集合不相交，是否就能安全提交？**  
    不一定。两个事务可能分别读取对方要写的记录，形成 write skew。

22. **如何修复值班例子中的 write skew？**  
    让读写事务也验证读取依据，并正确协调验证与安装；或者采用能保护相应业务依赖的可串行化协议。

23. **“MVCC 只读事务不需要验证”能否推出整个系统可串行化？**  
    不能。还需要分析读写事务之间的依赖、写冲突检查以及版本发布协议。

24. **多版本为什么不能永久免费保留？**  
    历史版本占用空间，需要安全回收；长时间活跃读者可能继续需要很老的版本。
