## 1. 本讲主线：多个副本，如何表现得像同一个系统？

对应讲义页 21、39–41、90，PDF 第 59、134–136、264 页。

上一讲讨论文件如何跨机器存储；这一讲进一步问：**当多个用户并发读写、网络传输有延迟时，用户究竟允许看到哪些结果？**

以聊天系统为例：

- **State，状态：**聊天记录列表。
- **Update / write，更新：**追加消息、上传文件、发送引用。
- **Read，读取：**观察当前聊天记录。
- **Replica，副本：**手机、平板或服务器上的一份状态。

同样的消息，可能在不同设备上以不同顺序出现；用户甚至先看到“请看这个文件”，随后才收到文件。这不是简单的“数据有没有传到”，还涉及更新的顺序和可见性。

**Consistency model（一致性模型）是系统与应用之间的约定：哪些观察结果允许出现，哪些不允许出现。**

它描述外部行为，而不是指定内部必须使用什么架构。多台服务器也可以对外表现为一个逻辑副本；只有一台服务器，也需要正确处理并发操作。

```text
复制和缓存提高性能、可用性
          ↓
各处收到更新的时间、顺序可能不同
          ↓
定义允许观察到的行为：一致性模型
          ↓
选择同步、排序、冲突处理和读写协议
```

## 2. 从 NFS、GFS、3FS 回到一致性问题

对应讲义页 2–20，PDF 第 3–58 页。

### 2.1 NFS：缓存也是一种复制

本讲延续早期 NFS 的教学模型：服务器保存文件，客户端通过 RPC 访问，并缓存文件内容。

服务器上的文件和客户端缓存是多份副本，可能暂时不同：

```text
初始：服务器 f = v1

客户端 A：open → write(v2)，修改暂存在本地
客户端 B：open → read，可能仍得到 v1

客户端 A：close，完成写回
客户端 B：之后重新 open，验证缓存 → read，得到 v2
```

这就是 **close-to-open consistency，关闭到打开的一致性**。它围绕写者关闭、读者随后打开的边界提供保证，不承诺每次 `write()` 后所有读者立即看到修改。

早期 NFS 的无状态设计、文件句柄、客户端 cursor 等，可回看 [LEC 5 笔记](LEC-5-Distributed-File-System.md)。这里“没有 open RPC”是所讨论版本的设定，不能推广到所有 NFS 版本。

### 2.2 GFS：写入顺序相同，仍要检查读取路径

同一 chunk 的多个副本若按网络到达顺序执行，可能出现：

| 副本 | 应用顺序 | 最终值 |
| --- | --- | --- |
| R1 | `write(A)` → `write(B)` | B |
| R2 | `write(A)` → `write(B)` | B |
| R3 | `write(B)` → `write(A)` | A |

GFS 让 primary 决定修改顺序，其他副本按这个顺序执行。课件强调，正常成功的写要等相关副本完成并回复；某个副本报错会导致写失败。

但**写失败不等于所有已执行修改自动撤销**。例如两个副本已经是 B，另一个仍是 A；客户端从不同副本读取，可能得到不同数据。

本讲第 20 页的重点是：**只讨论写入排序不足以确定整个系统的一致性，还要讨论读从哪里取值，以及部分失败时如何处理。**

### 2.3 3FS：用工作负载解释设计取舍

本讲前半段补充 3FS，承接上一讲：

| 场景或变化 | 设计及原因 |
| --- | --- |
| 训练随机读取大量样本、checkpoint 突发写入 | 使用 SSD 和高速 RDMA 网络支撑数据访问 |
| GPU 与存储需求分别增长 | 存算分离，计算节点和存储节点分别扩展 |
| 高速网络降低数据位置对调度的限制 | Locality-oblivious：不必把任务安排到数据所在机器附近 |
| 大量小文件与客户端增加元数据压力 | 多个无状态 meta service，共享 FoundationDB 事务 KV 存储 |
| 大量只读打开，跟踪所有 fd 成本高 | 只记录写打开的 file session |
| FUSE 复制和共享队列锁成为瓶颈 | Native API 通过共享内存缓冲区与请求环处理数据 I/O |

事务 KV 存储的例子是重命名：把 inode 7 的目录项从 `/x/a.txt` 移到 `/y/a.txt`，删除旧目录项和建立新目录项在同一个事务中完成。

```text
begin
  clear DENT|2|a.txt
  set   DENT|5|a.txt → inode 7
commit
```

课件用这个简化例子说明“两个修改都生效，或者都不生效”，以及并发冲突后的重试。不要把它当成完整的重命名实现。

只跟踪写打开，是为了降低海量只读打开的成本，同时协调删除与并发写入，避免留下难以回收的 chunk。FUSE 仍需要内核中的 FUSE 模块；用户态实现减少的是另写专用内核文件系统的负担。

**联系本讲：**事务、复制、缓存和打开文件状态都在规定并发操作如何相互影响，但它们不是同一种保证。元数据使用事务，也不意味着所有文件数据读写自动具有相同语义。

## 3. ChatAPP：集中式方案为什么简单，又为什么不够？

对应讲义页 22–29，PDF 第 60–86 页。

### 3.1 最直接的实现

服务器保存一份聊天列表：

```text
update(msg)：通过 RPC 把 msg 追加到服务器列表尾部
read()：通过 RPC 读取服务器上的列表
```

如果服务器串行处理操作，而且每个用户等待上一个 RPC 的确认后才发下一个，那么同一用户的操作顺序容易保留：

```text
上传文件 → 等待 ack → 发送引用 → 等待 ack

服务器列表：[文件, 引用]
```

这里没有保证不同用户并发请求的“点击顺序”。不同请求的网络延迟可能不同，服务器收到的顺序也可能不同。

### 3.2 四个代价

| 代价 | 原因 |
| --- | --- |
| 更新慢 | 每次操作都等待远端确认，网络往返进入关键路径 |
| 读取慢 | 课件的朴素实现每次传回全部历史，历史越长传输越多 |
| 无法离线读取 | 本地没有可用历史，断网后无法访问服务器 |
| 服务器故障时停摆 | 唯一状态持有者不可用，所有用户受影响 |

“每次读取整个历史”是这个朴素方案的选择，可以用分页等方式优化；不要把它理解为集中式设计必然具有的性质。

## 4. 复制和缓存：把等待从前台移到后台

对应讲义页 30–38，PDF 第 87–131 页。

### 4.1 写入需要多少副本确认？

| 策略 | 返回速度 | 主要问题 |
| --- | --- | --- |
| 只更新本地，立即返回 | 快，前台无需网络 RTT | 其他副本尚未更新；本地副本丢失时可能丢数据 |
| 等所有副本完成 | 受最慢副本限制 | 一个副本故障就可能阻塞写入 |
| 等部分副本确认，其余后台追赶 | 减少前台等待 | 必须规定哪些副本可读、故障后如何恢复 |

**补充理解：**“返回成功”意味着什么必须单独规定。已显示在本地、已复制到其他机器、已持久化，是不同阶段。

### 4.2 读本地副本

本地读取速度快，还可以离线工作，但可能读到旧数据。周期同步或推送可缩短落后时间；课件中的“每 10 秒同步”是例子，不是最终一致性规定的时限。

### 4.3 同步不只是复制字节

同步至少要处理两类问题：

1. **乱序：**文件先发送但体积大、传输慢，引用消息先到。
2. **并发更新：**两个副本从相同状态出发，各自追加一条消息。

```text
公共前缀：[你好, 谢谢]

R1 本地更新后：[你好, 谢谢, 好的]
R2 本地更新后：[你好, 谢谢, 收到]
```

双方都包含有效的新更新，不能简单把某个副本判为“过时”，再用另一个整体覆盖。

即使合并时保留两条消息，也要决定“好的”和“收到”谁在前。无论选哪个，至少一个用户可能看到原本显示的位置发生变化。

**复制解决数据有几份；一致性模型规定这些副本对外可以呈现什么差异。**

## 5. 最终一致性：允许暂时不同，但要求最终收敛

对应讲义页 42–47，PDF 第 137–150 页。

### 5.1 定义与条件

**Eventual consistency（最终一致性）：如果停止产生新更新，并且更新最终能传播到相关副本，那么经过足够时间，各副本会收敛，读取会得到一致的最终结果。**

课件采用的实现还要求：持有同一组更新的副本，通过确定性的处理得到相同状态。

这里有三个关键词：

- **暂时不同是允许的：**某个副本可以尚未收到更新。
- **最终传播是前提：**永久失联的副本无法凭空知道新数据。
- **没有固定时限：**定义本身不承诺 1 秒或 10 秒内完成同步。

这一基本定义可对照 Werner Vogels 的 [Eventually Consistent — Revisited](https://www.allthingsdistributed.com/2008/12/eventually_consistent.html)。

对于并发写入，“最终结果”由系统的合并规则定义；不能简单理解成真实时间最后发生的那次写一定胜出。

### 5.2 课件中的实现路线

```text
前台：本地写入 → 本地返回
后台：传播更新 → 去重与合并 → 确定顺序 → 重建一致状态
读取：返回本地当前状态
```

这让网络不必进入每一次前台读写，但应用要接受暂时不一致。

**补充理解：**最终一致性本身不自动保证读到自己刚写的内容，也不自动保证“读过新值后再也不会读到旧值”。这些需要额外的会话保证或协议设计。

### 5.3 相同更新集合，为什么还可能得到不同状态？

假设两个副本按到达顺序追加：

```text
R1：先本地 X，再收到 Y → [X, Y]
R2：先本地 Y，再收到 X → [Y, X]
```

两边更新集合都是 `{X, Y}`，列表却不同，因为追加操作的效果依赖顺序。

课件给出的方案是记录操作日志：

1. 交换更新，最终拿到相同的操作集合。
2. 按相同的确定性规则排序。
3. 从相同初始状态重新执行操作。

```text
到达日志不同 → 排序后的日志相同 → 确定性重放 → 状态相同
```

**补充理解：**用至少一次 RPC 传播时，应给每个更新稳定且唯一的 ID，以便去重；否则重试可能让同一消息追加两次。排序重放也只是本讲的教学实现，不是所有最终一致系统的唯一实现方式。重放普通状态修改和重复执行转账、发邮件等外部副作用不能混为一谈。

## 6. 排序键：确定性只是第一步

对应讲义页 48–54，PDF 第 151–165 页。

### 6.1 只用物理时间为什么不够？

若两条更新的 `getTimeOfDay()` 返回相同数值，排序键无法区分它们。即使用稳定排序保留输入顺序，各副本的输入顺序不同，结果仍可能不同。

课件提出用字典序比较：

```text
key = (physical_time, node_id)
```

先比时间，相同时再比节点编号。

**补充理解：**这解决了不同节点之间的时间碰撞；同一节点在一个时间刻度内生成多条更新时，仍可能重复。完整实现还需本地序号等唯一性机制，例如 `(physical_time, node_id, local_seq)`。

### 6.2 排出了同一个顺序，也可能不合理

课件示例：

```text
R1 上传文件：时间戳 1755419200.123
R2 收到文件，然后发送引用：时间戳 1755419199.987
```

R2 的时钟落后，因此按物理时间排序得到：

```text
[引用文件, 文件本身]
```

所有副本可以一致地排错顺序。问题不是“有没有全序”，而是这个顺序有没有保留事件间的依赖。

| 排序方式 | 能解决什么 | 仍有什么问题 |
| --- | --- | --- |
| 各自按到达顺序 | 本地处理简单 | 不同副本顺序不同 |
| 只按物理时间 | 大致反映时间 | 时间戳碰撞、时钟不同步 |
| 物理时间 + 唯一平局处理 | 同一集合得到确定顺序 | 仍可能把结果排在原因之前 |
| 节点 ID 优先 | 也能构造确定顺序 | 按机器编号排序缺乏应用上的因果含义 |

此外，实际墙上时钟还可能被校时调整；不能默认它总是严格单调递增。

## 7. 因果关系：happens-before 是偏序

对应讲义页 55–57，PDF 第 166–171 页。

用 `a → b` 表示 a happens-before b。它由以下规则生成：

1. **同一进程内顺序：**若 a 在 b 之前执行，则 `a → b`。
2. **消息关系：**发送一条消息发生在接收这条消息之前。
3. **传递性：**若 `a → b` 且 `b → c`，则 `a → c`。

本讲简化为每个节点内有明确的顺序；多线程节点需要把相应同步关系纳入建模。

```text
R1：上传文件 a ─────发送─────┐
                           ↓
R2：                    收到文件 b → 引用文件 c

所以：a → b → c，进而 a → c
```

若既没有 `a → b`，也没有 `b → a`，就称两个事件**因果并发**，记为 `a ∥ b`。

因果并发不要求物理上发生在同一瞬间；它表示在建模的进程顺序和消息链中，两者之间没有因果路径。因此 happens-before 是偏序，不强迫所有事件都可比较。定义与逻辑时钟的关系见 [Lamport 1978 年论文](https://lamport.azurewebsites.net/pubs/time-clocks.pdf)。

## 8. Lamport clock：用一个整数保留因果先后

对应讲义页 57–60，PDF 第 171–178 页。

### 8.1 要保证的性质

每个事件 e 带一个逻辑时间 `L(e)`，满足：

```text
a → b  ⇒  L(a) < L(b)
```

它不需要表示几点几分，只需要满足这个顺序约束。

### 8.2 标准事件计数算法

每个进程维护整数 `L`，初始为 0：

```text
本地事件或发送消息：
    L = L + 1
    用 L 标记事件；发送时把 L 放入消息

收到带时间戳 T 的消息：
    L = max(L, T) + 1
    用新的 L 标记接收事件
```

课件写作接收时 `T = max(T, T_received + 1)`，并要求本地时钟随时间或事件推进。这里统一采用“每次事件递增，接收先取最大再加一”的写法，使每个事件的时间戳严格增长。

### 8.3 文件与引用的例子

沿用课件数值，文件事件已经带时间戳 10，R2 当前时钟为 9：

| 步骤 | R2 时钟 | 解释 |
| --- | --- | --- |
| 收到文件，附带 `T = 10` | `max(9, 10) + 1 = 11` | 接收发生在文件事件之后 |
| 本地创建引用消息 | `11 + 1 = 12` | 引用发生在接收之后 |

```text
文件：(10, R1)
引用：(12, R2)
```

使用 `(Lamport 时间, 节点 ID)` 的字典序，可以把因果偏序扩展为确定性全序。同一进程每个事件严格递增，节点 ID 再解决不同进程的平局。

### 8.4 最重要的限制：不能反向推理

```text
a → b  ⇒  L(a) < L(b)       正确
L(a) < L(b)  ⇒  a → b       错误
```

两个互不通信的节点也可能分别生成时间戳 3 和 7。不能据此断言：

- 事件 3 在物理时间上更早。
- 两个节点一定通信过。
- 事件 3 导致事件 7。

对应课件第 59 页：仅凭时间戳，前两项推断都不成立。若额外知道事件 a 的消息在 b 之前已被接收，则可以通过消息和本地顺序推出 `a → b`；若只知道“后来某时刻同步过”，则不够。

### 8.5 排序正确，不等于读取时已经满足因果可见性

**补充理解：**Lamport 时间戳保证拿到两个事件后，能把原因排在结果前面；它不会自动让缺失的原因先到达。

某个副本可能先收到引用，尚未收到文件。如果立即展示引用，用户仍然可能看见不存在的文件。要提供因果一致的可见性，还需要识别依赖，在依赖到齐前延迟展示或应用更新。

**时钟记录顺序信息；协议决定何时让更新可见。**

## 9. “接龙”问题：为什么任意全序不够？

对应讲义页 61–65、69，PDF 第 179–188、199 页。

普通聊天可以容忍稍后调整消息位置，但“第一个报名的人有奖金”不能轻易接受已经确认的名次被改写。

```text
原列表已有 17 人

Alice 离线追加自己 → 本地显示第 18 名
Bob   离线追加自己 → 本地显示第 18 名
```

Lamport 时间戳加节点 ID 可以强行决定一个次序，但这不证明排在前面的人物理上更早点击，也不能消除之前已经展示的冲突结果。

课件提出两条路径：

| 路径 | 做法 | 代价 |
| --- | --- | --- |
| 显式识别并发冲突 | 不凭时间戳伪造因果关系，把不可比较的更新交给应用 | 应用需要合并、仲裁或要求重试 |
| 使用更强的一致性模型 | 在返回正式结果前，确定符合模型的操作顺序 | 增加协调与等待，某些故障下无法继续完成操作 |

第一条路径需要能表达“不可比较”的时间戳，因此引入向量时钟。

## 10. Vector clock：识别因果关系与并发

对应讲义页 66–68，PDF 第 189–198 页。

### 10.1 数据结构与更新规则

有 n 个进程，就用长度为 n 的向量。进程 i 保存 `V_i`：自己的分量记录本地事件进度，其他分量记录已知的对应进程进度。

```text
初始：所有分量为 0

进程 i 发生本地事件或发送消息：
    V_i[i] += 1
    事件附带当前向量；发送时一并携带

进程 i 收到向量 M：
    对所有 k：V_i[k] = max(V_i[k], M[k])
    V_i[i] += 1
```

这里把接收本身也计为事件。向量的合并是逐分量取最大值，不是相加，也不是直接覆盖。

### 10.2 比较规则

定义：

```text
A ≤ B：对所有 k，都有 A[k] ≤ B[k]
A < B：A ≤ B，并且至少一个分量严格小于
```

对于按上述标准算法标记、通信关系完整纳入模型的事件：

```text
a → b  ⇔  V(a) < V(b)
```

如果 `V(a)` 与 `V(b)` 一部分分量大、一部分分量小，二者不可比较，表示因果并发。

**不能按数组的字典序判断因果关系。** 字典序会把 `[1, 0]` 和 `[0, 1]` 排出先后，但向量时钟恰好要保留它们的不可比较性。

### 10.3 课件计算例子

两个副本初始都是 `[0, 0]`：

| 事件 | 向量 | 原因 |
| --- | --- | --- |
| R1 创建 X | `[1, 0]` | R1 的分量加一 |
| R2 独立创建 Y | `[0, 1]` | R2 的分量加一 |
| R1 收到带 `[0, 1]` 的 Y | `[2, 1]` | 先合并成 `[1, 1]`，再将自己的分量加一 |
| R1 随后创建 `ref(Y)` | `[3, 1]` | R1 的分量再次加一 |

得到：

```text
X = [1, 0] 与 Y = [0, 1]：不可比较，X ∥ Y
Y = [0, 1] < ref(Y) = [3, 1]：Y → ref(Y)
X = [1, 0] < ref(Y) = [3, 1]：X → ref(Y)
```

最后一条来自 R1 的本地顺序，不要求引用内容一定提及 X。Happens-before 描述可能的因果影响，不只描述消息的文字引用。

### 10.4 向量时钟能做什么，不能做什么？

| 能做 | 不能自动完成 |
| --- | --- |
| 区分“发生在之前”和“因果并发” | 判定两个并发报名谁物理上先点击 |
| 发现需要应用处理的并发版本 | 自动选择业务上正确的冲突处理方式 |
| 合并已知因果历史 | 自动完成复制、可靠传输或线性一致读写 |

**补充理解：**向量长度随参与者数量增加，动态节点成员也增加管理成本。它的信息更丰富，但不像 Lamport 标量时间戳那样紧凑。

## 11. Strict consistency：按真实发起时间排序为什么困难？

对应讲义页 70–77，PDF 第 200–223 页。

课件希望“先点击报名的人先排队”，把**按操作的全局真实发起时间（issue time）排序**称为 strict consistency，严格一致性。

即使使用单个服务器，也会遇到：

```text
Alice：先发 A ────────────────→ 服务器后收到 A
Bob：      后发 B ───→          服务器先收到 B
```

服务器按到达顺序处理得到 B、A，与发起顺序相反。

### 11.1 给请求加物理时间戳？

不同设备时钟可能存在偏差，时间戳不一定准确反映全局真实顺序。

### 11.2 假设时钟完全同步，是否就够了？

仍然不够。服务器收到时间戳 7 的 B 时，不知道是否还有时间戳 5 的 A 正在网络中：

- A 可能延迟很大。
- A 可能丢包，需要重传。
- 服务器不知道还有多少更早请求尚未到达。

**在没有通信延迟上界、又要求按绝对发起时间排序的设定下，服务器无法仅靠等待一个有限时长来确认没有更早请求。**

**表述边界：**本节沿用课件的 strict consistency 教学表述。关键结论依赖时钟和网络假设，不应脱离假设记成“任何系统都绝对无法实现更严格的时间语义”。

## 12. Linearizability：保留“完成后才发起”的真实时间顺序

对应讲义页 78–82，PDF 第 224–233 页。

### 12.1 定义

**Linearizability（线性一致性，也称可线性化）要求每次操作看起来都在调用开始与返回之间的某个瞬间生效。** 这个瞬间称为 linearization point，线性化点。

所有操作必须能放进一个符合对象语义的串行顺序，并保留：

```text
若 A 已经返回，B 才开始调用，则串行顺序必须 A 在 B 前。
```

定义可对照 [Herlihy 与 Wing 的原论文](https://www.cs.cmu.edu/~wing/publications/HerlihyWing90.pdf)。

```text
操作 A：|---调用---●---返回---|
操作 B：                         |---调用---●---返回---|

● 是逻辑生效点；这里 A 必须在 B 前。
```

这里约束的是真实时间中的先后关系，不要求客户端持有完美同步的物理时钟。

### 12.2 重叠操作可以选择顺序

```text
A：|-------------|
B：     |-------------|
```

A、B 的执行区间重叠，真实时间约束本身不强制谁先；只要能够解释所有返回结果，系统可以选择 A、B，也可以选择 B、A。

因此，**线性一致性不等于按点击时间排序**。Alice 先发起，Bob 后发起，只要两个操作重叠，Bob 仍可能排在前面。

### 12.3 读操作也必须放进同一条顺序

对一个初始值为 0 的寄存器 x，假设没有其他写入：

| 历史 | 是否允许 | 原因 |
| --- | --- | --- |
| `write(x,1)` 返回后，才调用 `read(x)`，返回 0 | 不允许 | 读必须排在已完成的写之后 |
| `read(x)` 与 `write(x,1)` 重叠，读返回 0 | 可以 | 可把读排在写之前 |
| 两者重叠，读返回 1 | 可以 | 可把写排在读之前 |
| 先一次读返回 1，完成后再读却返回 0 | 不允许 | 没有其他写时，无法解释为合法串行顺序 |

后面两次读即使来自不同客户端，线性一致性仍要求保留它们的完成到发起关系。

### 12.4 一个判断方法

1. 标出每个操作的调用和返回区间。
2. 给不重叠操作加边：先返回的操作必须排在后发起的操作前面。
3. 根据读结果加约束：寄存器读必须返回串行顺序中最近一次写的值。
4. 检查能否找到满足所有约束的串行顺序。

**补充理解：**线性一致的是具体操作。两个独立 API 调用 `read()`、`write()` 各自线性一致，不代表两者组合成的“先检查再占位”是原子的。接龙若要保证唯一名次，可以把“追加并返回名次”设计成一个原子操作，或使用条件更新等机制。

## 13. Primary-backup：如何实现线性一致的读写？

对应讲义页 82–86，PDF 第 233–254 页。

### 13.1 由 primary 确定顺序

本讲方案为每个对象指定一个 primary，读写都交给它；发到 backup 的请求转给 primary。

```text
客户端 ──读/写──→ Primary
                    │
                    ├──按序传播写入──→ Backup 1
                    └──按序传播写入──→ Backup 2
```

课件用 **one writer rule** 概括这一设计：由一个排序者决定读写顺序。

**表述边界：**这里的“一个”针对相应对象或分区，不要求整个系统只能有一台写服务器；单个 primary 也是本讲选用的实现方式，不是线性一致性定义要求的唯一算法。

### 13.2 课件中的写入路径

忽略故障切换，使用固定 primary 和副本集合：

1. 客户端把写操作交给 primary。
2. Primary 确定写入序号并发给 backups。
3. Backups 按序应用，完成后回复 ack。
4. Primary 收到所需确认，完成本地更新，再回复客户端成功。
5. 读由 primary 按与写入相容的串行顺序执行。

课件采用等待所有 backup 的简化版本。不能在未规定提交、故障恢复等机制时，直接把它替换为“随便收到一个 ack 就返回”。

### 13.3 为什么还要序号？

Primary 发出的顺序不等于 backup 收到的顺序：

```text
Primary 发出：write(x,1) → write(x,2)
Backup 收到：write(x,2) → write(x,1)
```

若直接应用，primary 最终是 2，backup 却是 1。

解决方法是为每次修改分配递增序号：

```text
(seq=1, write(x,1))
(seq=2, write(x,2))

Backup 先收到 seq=2：暂存并等待
收到且完成 seq=1 后：再应用 seq=2
```

**序号指定顺序，接收方按序执行才真正落实顺序。** 缺失消息仍需重传或日志补齐，单有序号不会让数据自动到达。

### 13.4 代价与尚未解决的问题

| 问题 | 影响 |
| --- | --- |
| 所有操作集中到 primary | primary 可能成为吞吐瓶颈 |
| 写入等待 backup 确认 | 增加网络等待 |
| primary 故障 | 没有故障切换协议时，系统停止服务 |
| 等待所有 backup，而某个 backup 故障 | 写入无法完成 |

**补充理解：**完整的容错实现还必须保证新 primary 不丢失已确认写入、旧 primary 不能继续独立提供冲突结果。复制几份数据并不自动解决这些问题；后续共识与故障恢复课程会进一步讨论。

## 14. 为什么直接读 backup 会破坏线性一致性？

对应讲义页 87，PDF 第 255–261 页。

初始 `x = 1`。沿用课件时序，primary 等 backup ack 后才更新自己的本地状态：

```text
1. Primary 收到 write(x,2)，把更新发给 Backup。
2. Backup 应用更新，x = 2；Primary 此时仍为 x = 1。
3. 读 R1 从 Backup 得到 2，并返回。
4. R1 返回后才开始读 R2；R2 从 Primary 本地得到 1。
5. Primary 收到 ack，更新 x = 2，写操作返回。
```

为什么写还没返回，也能证明这个历史不线性一致？

```text
R1 返回 2    ⇒ write(x,2) 必须排在 R1 前
R1 完成后 R2 才开始 ⇒ R1 必须排在 R2 前

所以必须：write(x,2) → R1 → R2
但 R2 返回 1，与这个顺序矛盾。
```

**读到一个尚未返回的写并不一定违规；先读到新值、随后又读到旧值，才使这个例子无法线性化。**

这也说明强一致读不能只靠“写已经排好了序”。若要从副本读取，必须增加相应同步、版本验证或其他能证明读取安全的机制。

## 15. Sequential consistency 与 linearizability 的区别

对应讲义页 87–88，PDF 第 255–262 页。

**Sequential consistency（顺序一致性）：存在一个合法的全局串行顺序，并且保持每个进程自己的程序顺序。**

它不额外要求保留不同进程之间所有真实时间上的“先完成、后发起”关系。

| 比较项 | 顺序一致性 | 线性一致性 |
| --- | --- | --- |
| 能否解释为合法串行执行 | 必须 | 必须 |
| 是否保持各进程的程序顺序 | 必须 | 必须 |
| 是否保持跨进程的真实时间先后 | 不作这一额外要求 | 必须 |

对上一节的两个读，如果它们属于不同客户端，且没有其他程序顺序约束，可以解释成：

```text
读旧值 R2 → write(x,2) → 读新值 R1
```

这个解释不符合原来的跨客户端真实时间顺序，所以不线性一致；但它可以满足顺序一致性的要求。

**表述边界：**课件用这个例子引出顺序一致性，但不能据此推导“主备复制 + 任意本地读”自动实现顺序一致性。

例如同一个客户端先从新副本读到 2，再从旧副本读到 1，而且没有其他写入，那么其程序顺序要求 `R1 → R2`，上述重排便不成立。因此，实际实现仍需维护会话和读写顺序等约束。

## 16. 把本讲的模型放在一起

对应讲义页 40–41、60、69、80、88–90。

| 模型 | 核心承诺 | 仍可能出现什么 |
| --- | --- | --- |
| 最终一致性 | 停止更新、传播完成后收敛 | 传播期间读旧值、消息重排；其他保证需另加 |
| 因果一致性 | 可见性尊重因果依赖 | 并发更新不必有统一的全局顺序 |
| 顺序一致性 | 一个合法全局串行顺序，保留各进程程序顺序 | 跨进程的真实时间先后不一定保留 |
| 线性一致性 | 合法串行顺序，同时保留不重叠操作的真实时间顺序 | 重叠操作未必按点击顺序排序 |
| 严格一致性（本讲表述） | 按全局真实发起时间排序 | 在本讲网络与时钟假设下，难以实际提供 |

课件用一条光谱表达“约束越多，实现可用的优化越少”的直觉。**补充理解：**不要把所有模型机械理解成一条包含所有属性的严格强弱链；例如因果顺序约束与最终收敛是不同维度，具体系统可以组合保证。

模型较弱通常给本地读写、异步复制更多空间，但不意味着任何弱一致实现都一定比强一致实现更快。实际表现仍取决于工作负载、网络、协议和故障状态。

同样，模型本身不等于可用性承诺：最终一致性允许某些本地操作在断网时继续，但数据丢失、磁盘故障、没有可达副本等问题不会因此消失。

### 16.1 三种顺序信息不要混用

| 机制 | 记录或决定什么 | 不能据此声称什么 |
| --- | --- | --- |
| Lamport clock | 用标量时间戳保留因果先后，可加平局规则构造全序 | 数字小就一定是原因，或物理时间更早 |
| Vector clock | 用偏序区分因果关系与并发 | 自动选出并发竞争的业务赢家 |
| Primary sequence number | 指定相应复制日志中的执行顺序 | 自动解决读一致性、丢包或故障切换 |

## 17. 复习自测

1. **一致性模型主要规定什么？**  
   规定操作的可见性和表面顺序，即用户允许观察到哪些结果；不直接规定必须使用几台服务器。

2. **缓存为什么也会产生一致性问题？**  
   缓存就是状态的另一份副本，不同副本收到更新的时间和顺序可能不同。

3. **所有副本都收到 X、Y，为什么仍可能不一致？**  
   如果操作不交换，`X → Y` 和 `Y → X` 会产生不同状态，需要一致的排序或其他收敛机制。

4. **最终一致性是否意味着“最多 10 秒同步完成”？**  
   否。固定时限需要额外约定，定义本身只要求相应条件下最终收敛。

5. **为什么物理时间加节点 ID 仍不能保证因果顺序？**  
   节点 ID 只解决平局，不解决设备时钟偏差；收到文件后发出的引用仍可能带更小的物理时间。

6. **本地 Lamport 时钟为 8，收到时间戳 12，接收事件和下一个本地事件各是多少？**  
   接收为 `max(8,12)+1 = 13`，下一个事件为 14。

7. **`L(a)=3`、`L(b)=7`，能否推出 `a → b`？**  
   不能。两者可能因果并发；标量时间戳丢失了区分这些情况的信息。

8. **使用 Lamport 时钟，是否能立即展示每个刚收到的更新而保持因果一致？**  
   不能。收到结果时，其依赖可能尚未到达，还需要依赖追踪和可见性控制。

9. **`[2,1,0]` 与 `[2,3,0]` 谁在前？**  
   前者逐分量不大于后者，且第二分量更小，因此前者在因果上发生于后者之前。

10. **`[2,1,0]` 与 `[1,2,0]` 谁在前？**  
    不可比较，表示因果并发；不能用字典序替代向量比较。

11. **R2 当前 `[2,1,0]`，收到 `[1,4,2]`，更新后是多少？**  
    假设 R2 对应第二分量，逐分量最大值为 `[2,4,2]`，接收事件再增加自己的分量，得到 `[2,5,2]`。

12. **为什么向量时钟也不能决定两个并发报名谁先点击？**  
    它记录因果信息，能告诉应用两个事件并发；没有记录足以确定真实点击先后的全局物理时间。

13. **单服务器为什么不自动实现课件中的严格一致性？**  
    请求到达顺序可能与发起顺序不同；加时间戳后仍可能不知道更早请求是否尚在途中。

14. **线性一致性是否保证先发起的写先完成或先执行？**  
    不保证。重叠操作可按任一符合返回结果的顺序排列；明确约束的是完成到发起的顺序。

15. **写操作尚未返回，读到新值是否一定违反线性一致性？**  
    否。写可以已在调用区间内生效，只是响应尚未到达；但后续操作仍须能放进同一个合法顺序。

16. **Primary 已经排序，backup 为什么还要检查序号？**  
    网络可能乱序；backup 需要等待前序操作完成，不能按消息到达顺序直接应用。

17. **主备复制时，直接读本地副本为什么可能不线性一致？**  
    不同副本应用进度不同，可能先读到新值，随后另一次不重叠的读又得到旧值。

18. **这个本地读方案是否必然顺序一致？**  
    否。还要保持每个进程的程序顺序；同一进程在副本间切换后读值倒退，可能连顺序一致性也不满足。

19. **线性一致的 read 和 write 能否直接保证“先检查空位，再报名”没有竞争？**  
    不能。两次调用之间可能插入别人的操作，需要原子报名、条件更新或适当的事务语义。

20. **分析一个复制系统时，应先问哪些问题？**  
    写在哪里排序、什么时候确认成功、读从哪里取值、依赖未到齐时是否可见、并发冲突如何处理，以及故障后哪些已确认结果必须保留。
