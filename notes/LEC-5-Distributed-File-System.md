## 1. 本讲主线：文件系统加上 RPC，就够了吗？

对应讲义页 1–3、65，PDF 第 2–7、205 页。

前几讲已经具备两个基础：

- 单机文件系统：把路径、文件描述符和文件内偏移转换为数据块访问。
- RPC：把本地调用形式转换为远端请求，并处理编码、超时和重试。

最直接的想法是把 `open/read/write/close` 全部改成 RPC。但网络延迟、部分故障、多客户端缓存和多副本，会改变原本的设计前提。

**分布式文件系统的核心，是根据工作负载决定：状态放在哪里、数据如何定位、修改何时可见，以及故障后如何继续工作。**

| 案例 | 主要场景 | 本讲重点 |
| --- | --- | --- |
| NFS | 工作站访问远程共享文件 | 透明接口、无状态服务器、文件句柄、客户端缓存 |
| GFS | 大文件、顺序读取、追加写入 | 单 master、大 chunk、多副本、读写路径分离 |
| HDFS | Hadoop 的大规模数据处理 | 与 GFS 相似的元数据和数据分离架构 |
| 3FS | AI 数据准备、随机读样本、写 checkpoint | 事务元数据、计算 chunk 位置、存算分离、绕过 FUSE 数据路径瓶颈 |

### 1.1 访问透明性不等于本地语义完全不变

显式访问需要用户主动连接远程资源，例如通过 FTP 下载文件；透明访问则尽量让应用继续使用熟悉的文件接口。

```text
应用：open / read / write
          ↓
客户端文件系统实现
          ↓ RPC / 网络
远程文件服务
          ↓
服务器上的存储设备
```

NFS 可以把远程目录挂载到本地目录树中。GFS 则使用自己的客户端库，不能把两者都理解为无需修改应用的 POSIX 文件系统。

## 2. NFS：本地文件接口如何映射到远程操作？

对应讲义页 4–8、14、20，PDF 第 9–26、44–53、68–77 页。

### 2.1 设计目标

NFS（Network File System）由 Sun 在 1980 年代面向工作站设计，强调：

- 客户端和服务器可以运行不同硬件、操作系统和底层文件系统。
- 通过挂载实现访问透明性，也支持无盘工作站。
- 用简单的服务端状态模型降低故障恢复成本。
- 用缓存、较大传输单位和预读提高性能。

课件的 UDP 与重试属于早期设计背景，不能理解为所有版本的 NFS 都只使用 UDP。

### 2.2 `mount`：把远程目录接入本地命名空间

课件示例：

```sh
mount 192.168.1.100:/users/paul /home/paul
```

服务器导出 `/users/paul`，客户端把它挂在 `/home/paul`。概念流程为：

1. 客户端请求访问服务器导出的目录。
2. 服务器返回该目录的 **file handle，文件句柄，简称 `fh`**。
3. 客户端通过 VFS/vnode 等内核抽象接入挂载点。
4. 后续访问挂载目录时，由 NFS 客户端把文件操作转换为远程请求。

**补充理解：**`fh` 是服务器可解释、客户端通常视为不透明标识的对象身份，不应直接理解为文件路径字符串。

### 2.3 文件 API 与 NFS RPC 并非一一对应

| 应用看到的操作 | 课件中的 NFS 操作 | 变化 |
| --- | --- | --- |
| `OPEN(path, mode)` | 逐级 `LOOKUP(dirfh, name)` 等 | 客户端建立本地打开状态 |
| `READ(fd, buf, n)` | `READ(fh, offset, count)` | 显式携带文件身份和偏移 |
| `WRITE(fd, buf, n)` | `WRITE(fh, offset, count, data)` | 显式携带偏移和数据 |
| `SEEK(fd, offset)` | 无独立 RPC | 修改客户端保存的 cursor |
| `CLOSE(fd)` | 无独立 `CLOSE` RPC | 释放本地状态，必要时完成写回 |
| `STAT(path)` | 路径解析后 `GETATTR(fh)` | 根据句柄取属性 |
| `MKDIR(path)` | `MKDIR(dirfh, name, attr)` | 用父目录句柄和名字定位 |
| `UNLINK(path)` | `REMOVE(dirfh, name)` | 删除目录项 |
| `RENAME(from, to)` | `RENAME(dirfh, name, tofh, toname)` | 显式指出源、目标父目录 |

表中的 `OPEN → LOOKUP` 是普通已存在文件的简化流程。创建、截断、权限检查和缓存验证还可能需要其他操作。

**版本边界：**“没有 `OPEN/CLOSE` RPC”适用于这里的 NFS v2/v3 模型。NFSv4 引入了 `OPEN`、`CLOSE` 及相关状态，也支持组合多个操作的 `COMPOUND` RPC。参见 [RFC 7530 §1.4.2、§1.4.4](https://www.rfc-editor.org/rfc/rfc7530.html#section-1.4.4)。

### 2.4 一次打开与读取

忽略缓存命中和错误处理：

```text
应用                     NFS 客户端                    NFS 服务器
 | open("f")                  |                            |
 |--------------------------->| LOOKUP(dirfh, "f")          |
 |                            |--------------------------->|
 |                            |<---------------------------|
 |                            |          fh, attrs         |
 |<---------------------------|                            |
 | fd                         | 保存 fd → fh，cursor = 0   |
 |                            |                            |
 | read(fd, buf, n)            |                            |
 |--------------------------->| READ(fh, 0, n)              |
 |                            |--------------------------->|
 |                            |<---------------------------|
 |<---------------------------|          data, attrs       |
 | data                       | 按实际读取量推进 cursor    |
```

应用使用的 `fd` 属于客户端进程；服务器处理的是 `fh`，不需要理解客户端的 `fd = 3`。

## 3. 为什么早期 NFS 不在服务器上保存打开文件表？

对应讲义页 9–13，PDF 第 27–43 页。

### 3.1 直接远程化 `open()` 会引入什么状态？

若服务器像本地内核一样保存打开状态，它需要类似这样的表：

| 客户端 | fd | 文件 | cursor |
| --- | --- | --- | --- |
| A | 3 | f | 0 |
| B | 3 | g | 4096 |
| C | 3 | h | 128 |

这会带来三个问题：

1. **规模：**状态量随各客户端打开文件数的总和增长。
2. **服务器崩溃：**内存表丢失后，客户端发来的 `READ(3, ...)` 无法被正确解释。
3. **客户端崩溃：**客户端可能永远不发送 `CLOSE`，服务器需要发现并清理遗留状态。

### 3.2 把 cursor 留在客户端，让每次请求自包含

NFS 采用：

```text
客户端保存：fd → fh、cursor、打开方式等
请求携带：fh、offset、count，以及操作所需的其他信息
服务器保存：文件数据和元数据
```

例如 `READ(fh_f, 4096, 1024)` 已经说明读哪个文件、从哪里读、读多少。只要文件及句柄仍然有效，服务器重启后不必恢复原来的每客户端打开表，就能解释请求。

**无状态不等于没有任何状态，而是不依赖前一次调用留下的客户端会话上下文来解释当前请求。** 文件内容、inode 和目录显然仍需保存。

课件第 13 页用“请求携带完整上下文”的 API 类比这一思想。类比重点是状态责任的转移：服务器少记会话，客户端就要保存并携带更多信息。

### 3.3 无状态不自动解决重复执行

请求超时后，客户端可以重试，但服务器可能已经执行了第一次请求。

```text
客户端发请求 → 服务器完成操作 → 响应丢失
客户端超时重试 → 同一操作可能再次执行
```

课件沿用上一讲的方案：请求带 `xid`，服务器保留 **reply cache（回复缓存）**，识别重复调用并返回已有结果。

这是无状态设计中的“软状态”：它改善重试行为，但不能把有限的内存缓存当成跨崩溃、永不失效的 exactly-once 保证。无状态、幂等和至多一次，是三个不同概念。

## 4. File handle：为什么不能用路径或单独的 inode number？

对应讲义页 15–19，PDF 第 54–67 页。

### 4.1 路径会随重命名改变

课件时序：

```text
客户端 1：打开 dir1/f，得到 fd
客户端 2：把 dir1 改名为 dir2
客户端 2：把另一个目录 dir3 改名为 dir1
客户端 1：继续 read(fd)
```

原 fd 应继续指向原文件，也就是现在的 `dir2/f`。如果每次读都重新解释字符串 `dir1/f`，就可能访问另一个文件。

**路径表示“按名字如何找到对象”，打开后的引用表示“此前找到的那个对象”。** 二者不能混用。

### 4.2 inode number 可能被回收复用

只使用 inode number 也有问题：

| 时刻 | 操作 | 服务器状态 |
| --- | --- | --- |
| 1 | 客户端 B 打开旧文件 `f` | `inode = 7, generation = 1` |
| 2 | 客户端 A 删除 `f` | 课件无状态模型下旧 inode 可被释放 |
| 3 | A 创建新的 `f` | 复用 inode 7，`generation = 2` |
| 4 | B 用旧句柄读取 | 应拒绝旧身份，不能读到新文件 |

解决办法是在句柄中加入 **generation number（代数）**：inode number 被分配给新的文件对象时，代数改变。

### 4.3 句柄标识文件的某一次生命期

教学上可把句柄理解为：

```text
fh ≈ (文件系统标识, inode number, generation number, ...)
```

服务器检查 `(7, 1)` 与当前 `(7, 2)` 不匹配，就返回旧句柄失效的错误，而不是读取新文件。实际句柄编码由服务器实现决定，并非协议要求客户端按这个结构解析。

| 标识方式 | 能处理什么 | 主要问题 |
| --- | --- | --- |
| 路径名 | 找到当前名字对应的对象 | 重命名后可能指向别的对象 |
| inode number | 不随重命名改变 | 编号复用后可能误认新对象 |
| inode number + generation | 区分同一编号的不同生命期 | 能拒绝旧引用，但不自动保留旧文件 |

### 4.4 检测失效不等于保留 UNIX 的删除语义

本地 UNIX 文件系统通常允许：文件名删除后，已有 fd 继续读旧文件，直到最后的存活引用释放。

课件中的无状态 NFS 模型不知道其他客户端是否仍打开该文件，因此可能回收旧文件，让后续访问得到 stale file handle。

**generation 解决的是“别误读新文件”，不是“让被删除的旧文件继续存活”。** 这是第 18 页明确指出的语义取舍；不要把简化案例当成所有 NFS 版本、所有客户端实现的完整删除行为。

## 5. NFS 缓存：性能提升为什么带来一致性问题？

对应讲义页 21–24，PDF 第 78–89 页。

### 5.1 缓存的不只是文件内容

| 客户端缓存 | 用途 | 可能过时的内容 |
| --- | --- | --- |
| 文件数据块 | 减少远程 `READ` | 其他客户端写入的新数据 |
| 属性 | 减少 `GETATTR` | 大小、修改时间等 |
| 路径绑定、目录信息 | 减少 `LOOKUP/READDIR` | 新建、删除、重命名后的名字关系 |

服务器也可以利用本地文件系统的 buffer cache。远程访问是否更慢，取决于网络、服务器存储和双方缓存命中情况，不能仅凭“远程”判断。

### 5.2 Close-to-open consistency：关闭到打开的一致性

课件的核心策略是：

- **写者关闭时：**把尚未发送的修改写回服务器。
- **读者打开时：**验证属性，例如比较服务器修改时间和缓存记录；发现变化后失效旧缓存。

```text
初始：服务器 f = v1

客户端 A：open → write(v2)，暂存本地缓存
客户端 B：open → read，仍可能读到 v1

客户端 A：close，完成写回，服务器 f = v2
客户端 B：之后重新 open，验证缓存 → read，看到 v2
```

这里假设写回和后续验证成功，且没有新的并发修改。**关键边界是写者关闭后、读者重新打开；不是每次 `write()` 后所有客户端立即看到新数据。**

一个长期保持打开状态的读者，不能仅凭 close-to-open 的名字就推断自己每次读取都是最新的。

### 5.3 验证、失效与超时

课件介绍用文件修改时间验证缓存，并在一定时间后强制失效。验证越频繁，越容易发现变化，但也会增加远程操作。

| 策略方向 | 好处 | 代价 |
| --- | --- | --- |
| 更频繁验证 | 缩短读到旧内容的窗口 | 更多 RPC、更高延迟 |
| 更长时间复用缓存 | 降低网络与服务器开销 | 可能更久看不到其他客户端修改 |

课件中的文件 3 秒、目录 30 秒，是所介绍策略的示例值，不是所有部署都必须遵守的常量。单靠定期验证，也不能推导出任意并发读写都具有严格的全局顺序。

### 5.4 其他读优化

- **较大传输单位：**一次 RPC 传更多数据，摊薄往返和处理开销；课件举 8 KB 的历史示例。
- **Read-ahead，预读：**在顺序访问中提前请求后续块，让网络和磁盘访问与应用计算重叠。

**补充理解：**预读依赖访问可预测性。随机读取时，错误预读可能浪费带宽和缓存空间。

## 6. NFS 的后续演进

对应讲义页 25–26，PDF 第 90–91 页。

课件列举 NFSv3 的 64 位文件大小、TCP、大块传输和 `COMMIT`，以及 NFSv4 更丰富的状态、缓存管理、统一导出命名空间、ACL 和组合 RPC。

**补充理解：**NFSv3 的 `WRITE` 可以使用不同稳定性级别；未稳定写入的数据需要后续 `COMMIT` 等处理。因此应区分：应用缓冲、客户端缓存、服务器收到数据、数据进入稳定存储。参见 [RFC 1813 的 WRITE 与 COMMIT](https://www.rfc-editor.org/rfc/rfc1813.html#section-3.3.7)。

学习本讲时，不要把三个结论混在一起：

1. 本地 `close()` 不普遍等于持久化保证。
2. NFS 客户端的关闭流程可能触发远程写回。
3. 早期 NFS 没有独立 `CLOSE` RPC，并不意味着关闭时绝无网络通信。

## 7. GFS：先改变工作负载假设，再改变架构

对应讲义页 27–30，PDF 第 93–96 页。

GFS（Google File System）面向大规模数据密集型应用，课件强调以下假设：

| 假设 | 推动的设计选择 |
| --- | --- |
| 多 GB 大文件常见 | 使用大 chunk，降低管理数量 |
| 大量顺序、流式读取 | 追求总体吞吐，减少频繁元数据查询 |
| 追加常见，文件内部随机覆盖较少 | 提供面向追加的接口 |
| 服务器和磁盘故障是常态 | 自动发现故障，保存副本并恢复副本数 |
| 应用可以与文件系统共同设计 | 使用专用客户端库，不强求完整 POSIX 语义 |

课件列出 `create/delete/open/close/read/write`，以及 `snapshot/append`。重点是**按应用需要设计接口**，不必逐项复制传统文件系统 API。

**课件校正：**第 30、64 页把 GFS 描述为不支持 `rename`，这一绝对说法不宜照记。经典论文 §4.4.1 明确描述通过重命名回原名来恢复隐藏的已删除文件。可确定的结论是 GFS 不提供完整标准 POSIX 接口，不能据此概括为完全没有重命名能力。参见 [GFS 原论文](https://storage.googleapis.com/gweb-research2023-media/pubtools/4446.pdf)。

## 8. GFS 架构：一个 master，多个 chunkserver

对应讲义页 31–38，PDF 第 97–114 页。

### 8.1 元数据与文件数据分开

```text
                      元数据请求
应用 + GFS client ----------------------> Master
        |                                 |
        | 直接读写文件数据                | 管理 chunk、副本和租约
        v                                 v
   Chunkserver 1     Chunkserver 2     Chunkserver 3 ...
       本地磁盘          本地磁盘          本地磁盘
```

| 组件 | 职责 |
| --- | --- |
| Master | 管理命名空间、文件到 chunk 的映射、chunk 副本位置等元数据 |
| Chunkserver | 把 chunk 存在本地磁盘，服务实际数据读写 |
| Client library | 计算 chunk 索引、查询和缓存元数据、直接访问 chunkserver |

Master 不转发正常读写的数据字节，因此大文件的数据吞吐不必集中经过 master。但元数据请求和内存容量仍可能成为瓶颈。

### 8.2 Chunk 与副本

课件采用经典参数：

- Chunk 大小：64 MB。
- Chunk handle：master 分配的全局唯一 64 位编号。
- 副本数：默认 3 份，可根据需要调整。
- 存储形式：chunk 在 chunkserver 的本地 Linux 文件系统中作为文件保存。
- 完整性检查：每个 64 KB 数据段有一个 32 位 checksum。

**副本和 checksum 解决不同问题：**副本提供冗余；checksum 帮助发现内容损坏。仅保存多个副本，不代表能自动判断哪份数据正确。

### 8.3 为什么选择大 chunk？

1. **元数据更少：**同样大小的文件需要更少的 chunk 映射。
2. **查询 master 更少：**连续访问较大范围时，常落在已知 chunk 中。
3. **更容易复用连接：**连续请求可以发往同一 chunkserver。

**补充推导：**明确按二进制单位计算，一个 1 TiB 文件用 64 MiB chunk：

$$
N=\frac{2^{40}}{2^{26}}=2^{14}=16{,}384
$$

若改用 4 KiB 管理单位，则需要 $2^{28}=268{,}435{,}456$ 个单位，是前者的 16,384 倍。这里比较的是逻辑单位数量，不是具体元数据字节数。

三副本下，1 TiB 有效数据大致需要 3 TiB 副本数据空间，尚未计入其他开销。

课件第 34 页把 3 次 1 MB 读取画成“小 chunk 需要 3 次握手、大 chunk 需要 1 次”。它假设前者访问不同服务器、后者留在同一服务器；**TCP 握手并不是每跨一个 chunk 就必然发生**，也取决于副本位置和连接是否已经建立。

**补充理解：**大 chunk 也有取舍：小而热门的文件可能集中在少数服务器上形成热点，需要增加副本等措施。

### 8.4 哪些 master 元数据要持久保存？

| 信息 | 课件中的保存方式 | 原因 |
| --- | --- | --- |
| 命名空间、文件到 chunk 的映射 | 内存中服务，并以 operation log 等方式持久保存 | 不能仅从物理副本位置推回完整名字关系 |
| Chunk 当前在哪些服务器上 | 内存中维护；启动时询问 chunkserver，之后通过 heartbeat 更新 | 实际持有 chunk 的服务器是位置事实来源 |

所以“元数据在内存中”不等于“重启后全丢失”，“位置表不写日志”也不等于“所有元数据都不写日志”。

### 8.5 GFS 缓存的是什么？

课件说客户端不缓存文件数据，但缓存 chunk 位置等元数据。Chunkserver 不额外建立一套 GFS 数据缓存，而是利用底层操作系统的 buffer cache。

不要把这句话扩大为“系统任何地方都不缓冲数据”：写入协议还会暂存待写数据，操作系统也有自己的缓存。

## 9. GFS 读取：先问位置，再直接取数据

对应讲义页 39，PDF 第 115–128 页。

设文件偏移为 $o$，chunk 大小为 $C$：

$$
\text{chunk index}=\left\lfloor\frac{o}{C}\right\rfloor,
\qquad
\text{offset in chunk}=o\bmod C
$$

一次未命中元数据缓存的读取：

1. Client 根据文件偏移计算 chunk index。
2. 向 master 发送文件名和 chunk index。
3. Master 返回 chunk handle 与副本所在服务器。
4. Client 缓存映射，选择一个副本。
5. Client 直接向 chunkserver 请求指定 chunk 内的字节范围。
6. Chunkserver 返回数据，数据不经过 master。

后续访问同一 chunk 时，若缓存仍有效，就可以跳过 master。

**补充例子：**按 64 MiB chunk 计算，文件偏移 130 MiB 对应 chunk index 2、chunk 内偏移 2 MiB。若读取跨越 chunk 边界，客户端需要拆分请求。

## 10. GFS 写入：数据传播与写入排序分开

对应讲义页 40–43，PDF 第 129–155 页。

### 10.1 副本收到相同数据，为什么仍可能不一致？

假设 A、B 覆盖同一个位置，各副本都收到两个请求，但执行顺序不同：

| 副本 | 执行顺序 | 最终内容 |
| --- | --- | --- |
| 1 | A → B | B |
| 2 | A → B | B |
| 3 | B → A | A |

网络发送顺序不能自动成为所有副本的共同执行顺序。

GFS 为一个 chunk 选择一个 **primary（主副本）**，由它统一决定修改顺序，其他副本作为 secondaries 跟随执行。

### 10.2 Master 与 primary 不是同一个角色

- **Master：**管理整个文件系统的元数据，并向某个副本授予租约。
- **Primary：**在租约有效期内，为相应 chunk 的修改排序。

不同 chunk 的 primary 可以位于不同 chunkserver。课件的租约初始期限为 60 秒，可通过 heartbeat 等过程续租；它不是客户端某次写调用的超时时间。

### 10.3 阶段一：传数据，先暂存

Client 先取得 primary 和 secondaries 的位置，再把数据沿服务器链传播：

```text
Client → Secondary 1 → Primary → Secondary 2
             暂存         暂存          暂存
```

图中的顺序只是例子。数据流可按网络条件组织，不要求先到 primary。此时服务器收到的是待写数据，尚不能把“已暂存”当成“已按顺序修改文件”。

### 10.4 阶段二：发写命令，统一顺序

待副本确认收到数据后：

1. Client 向 primary 发出写入请求，引用先前发送的数据。
2. Primary 为修改分配序号，决定并发修改的先后顺序。
3. Primary 执行本地修改，并把请求及顺序发给 secondaries。
4. Secondaries 按指定顺序执行，向 primary 返回结果。
5. Primary 汇总后回复 client。

```text
数据流：Client → 一个副本 → 下一个副本 → ...
控制流：Client → Primary → 各 Secondary
响应流：各 Secondary → Primary → Client
```

**分离的原因：**大数据传输追求带宽利用率，控制消息负责统一执行顺序；两者不必经过相同拓扑。

### 10.5 序号、版本号、租约分别解决什么？

| 机制 | 回答的问题 |
| --- | --- |
| 修改序号 | 当前 primary 安排的修改按什么顺序执行？ |
| Chunk version number | 这个副本是否已过时，是否错过更新？ |
| Lease，租约 | 这一段时间内，谁有权为该 chunk 排序？ |

课件用版本号识别落后副本，避免把它当成有效的新副本继续使用。它与 NFS generation number 都涉及版本，但对象和用途不同：后者区分 inode 的不同生命期。

### 10.6 两个重要边界

**补充理解：**这里的“两阶段”是先传数据、再发有序写命令，并不是数据库事务的 two-phase commit（2PC）。部分副本写入失败时，不会自动回滚所有已完成修改；不能据此推导出任意写入都全有或全无。

GFS 原论文还区分普通写与 record append：普通写指定偏移，record append 由系统选择位置，并提供原子记录的至少一次追加，重试可能产生重复记录。副本排序也不等于跨 chunk 的整次应用写入具有原子性。参见 [GFS 原论文 §2.7、§3.1、§3.3](https://storage.googleapis.com/gweb-research2023-media/pubtools/4446.pdf)。

## 11. HDFS：用另一组名字理解相似架构

对应讲义页 44–48，PDF 第 156–160 页。

HDFS（Hadoop Distributed File System）是受 GFS 思想启发的开源分布式文件系统，强调普通硬件上的容错、大文件和高吞吐。

| GFS 中的角色或结构 | HDFS 中的对应概念 |
| --- | --- |
| Master | NameNode |
| Chunkserver | DataNode |
| Chunk | Block |
| 元数据 checkpoint | FsImage |
| Operation log | EditLog |

核心关系仍然是：

```text
NameNode：文件名 → block 列表；block → DataNode 位置
DataNode：保存 block 副本，处理实际数据读写
```

FsImage 保存文件系统元数据检查点，EditLog 记录之后的元数据修改。不要因为图中画了 block 位置表，就认为当前所有副本位置都必须原样写入镜像。

**版本边界：**课件图采用 64 MB block，不能把它当成 HDFS 的固定块大小。Apache 文档给出的典型值是 128 MB，块大小与副本数可以配置。HDFS 是独立系统，不能把 GFS 的 primary/lease 写协议直接套用到 HDFS。参见 [Apache HDFS Architecture](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)。

课件第 44 页的 Google 集群数量、容量和吞吐是历史案例背景，不代表当前部署规模。

## 12. 3FS：AI 工作负载如何改变文件系统设计？

对应讲义页 49–51，PDF 第 162–170 页。

3FS（Fire-Flyer File System）面向训练与推理中的共享文件访问。

| 环节 | 课件中的访问特征 |
| --- | --- |
| 数据准备 | 读写大量中间文件 |
| Dataloader | 随机读取训练样本，读取大小可从 KB 到 MB |
| Checkpoint | 突发的大量写入 |
| 推理 KVCache | 高带宽读取 |

课件举出每节点超过 10 GiB/s 的 checkpoint 写入、峰值 40 GiB/s 的 KVCache 读取需求。这些是所讨论场景的数据，不应当作任意 3FS 部署的性能保证。

### 12.1 硬件变化改变瓶颈

课件把早期 GFS 的磁盘、100 Mbps 网络，与 3FS 场景中的 NVMe SSD、双 200 Gbps RDMA 网络对照。

**补充推导：**按标称链路带宽相加，$2\times200\text{ Gbps}/100\text{ Mbps}=4000$。这只是带宽规格之比，不等于端到端性能提高 4000 倍。

当存储和网络都很快时，频繁查询元数据、内存复制、线程竞争和内核路径开销就更容易成为限制。

### 12.2 四类角色

| 角色 | 主要职责 |
| --- | --- |
| Cluster manager | 维护集群成员和配置，接收 heartbeat |
| Meta service | 处理命名空间和元数据操作 |
| Storage service | 保存分布在多个节点上的 chunk 副本，处理数据 I/O |
| Client | 提供文件接口，根据元数据访问 storage service |

它保留了 GFS 的“大方向”：元数据与数据路径分离、文件分块、多副本；也保留了 NFS 的熟悉文件接口，并选择让元数据服务本身无状态。

## 13. 3FS 元数据：无状态服务背后的事务 KV store

对应讲义页 52–54，PDF 第 171–178 页。

### 13.1 把状态放到 FoundationDB

```text
Client → 任意 Meta service → FoundationDB
              无状态          保存共享元数据
```

课件将 inode 和目录项表示成键值对：

```text
INOD|7          → inode 7 的属性、文件布局等
DENT|2|a.txt    → inode 7
```

其中 `DENT|2|a.txt` 表示“inode 2 对应的目录中，名字 a.txt 指向哪个 inode”。这些键只是课件的简化表示。

服务进程故障后，另一个 meta service 可以依靠共享数据库继续处理请求，不必依赖故障进程中唯一的一份元数据。

### 13.2 用事务实现多条元数据更新

把 `/x/a.txt` 移到 `/y/a.txt`，假设 `/x` 为 inode 2、`/y` 为 inode 5，目标名尚不存在：

```text
begin transaction
    读取并检查源目录项、目标目录项等
    删除 DENT|2|a.txt
    设置 DENT|5|a.txt → inode 7
commit
```

事务使这些修改一起生效或都不生效。若另一个服务并发执行 `unlink /x/a.txt`，冲突检测与重试可以避免两个服务各自按过时信息完成修改。

**补充理解：**完整 `rename` 还需处理权限、目标覆盖、目录约束和相关元数据；上面的两个目录项更新只是说明事务的作用。

### 13.3 无状态没有消除复杂性，而是改变了承担者

GFS 单 master 把元数据和协调逻辑集中起来，设计简单，但有请求处理能力和内存容量限制。3FS 可以部署多个 meta service，把共享状态和并发控制交给事务数据库。

因此：

- Meta service 可以无状态，整个文件系统仍然有状态。
- 增加 meta service 有助于扩展请求处理，但数据库仍有容量、吞吐和冲突开销。
- 事务元数据不自动让所有文件数据读写也成为同一个数据库事务。

## 14. 3FS 为什么只跟踪以写模式打开的文件？

对应讲义页 55–56，PDF 第 179–182 页。

训练启动时，许多 worker 会打开大量样本文件。如果每个只读打开都在服务端记录 session，元数据服务和数据库需要处理大量额外状态。

课件中的取舍是：

| 打开方式 | 是否记录文件 session | 删除时的含义 |
| --- | --- | --- |
| 只读 | 不记录 | 不承诺因只读 fd 仍存活而保留旧文件 |
| 写模式 | 记录 | 有活跃写 session 时延迟删除，等待 session 结束 |

为什么写入需要特殊对待？如果删除与继续写入并发发生，写者可能再生成已经失去元数据引用的 chunk，造成垃圾数据难以回收。记录写 session 有助于协调文件删除与写入生命期。

课件截图还说明：系统需要检查客户端存活情况，清理离线客户端留下的写 session。这里再次出现了“保留状态就需要处理崩溃清理”的成本。

**与 NFS 的联系：**两者都牺牲了一部分“打开后删除仍可继续访问”的本地语义，但侧重点不同：早期 NFS 强调简单恢复，3FS 强调减少海量只读打开的成本。

## 15. 3FS 如何通过文件布局计算 chunk 位置？

对应讲义页 57–58，PDF 第 183–195 页。

### 15.1 从“查每个 chunk”改成“先取布局，再计算”

GFS 用大 chunk 和客户端缓存减少位置查询，但随机访问大量 chunk 仍可能产生许多元数据请求。

3FS 在打开文件时取得布局信息，之后由客户端计算 chunk 身份和所属 replication chain（复制链）。课件简化公式为：

```text
chunk_index = file_offset // chunk_size
offset_in_chunk = file_offset % chunk_size
chunk_id = (inode_id, chunk_index)
chain = chains[chunk_index % stripe]
```

这里 `stripe` 表示布局中使用的链数，`chains` 是该文件布局已经确定的有序链列表。`inode_id + chunk_index` 应理解为组合/拼接身份，不能直接按普通整数加法理解，否则不同二元组可能相撞。

### 15.2 一个计算例子

假设 inode 为 7，布局为 `chains = [A, B, C]`、`stripe = 3`：

| Chunk index | Chunk ID | 复制链 |
| --- | --- | --- |
| 0 | `(7, 0)` | A |
| 1 | `(7, 1)` | B |
| 2 | `(7, 2)` | C |
| 3 | `(7, 3)` | A |
| 4 | `(7, 4)` | B |

因此读 chunk 3、4 时，客户端可以根据已缓存布局分别访问 A、B，无需为每个 chunk 再问一次 meta service。

**边界：**“自己计算位置”不代表完全不需要元数据或集群配置。客户端仍需先拿到文件布局，并知道链对应哪些存储节点；故障和成员变化也需要处理。

## 16. 3FS 的存算分离与 locality-oblivious

对应讲义页 59–60，PDF 第 196–199 页。

早期 GFS + MapReduce 将计算尽量安排在数据所在机器附近，因为网络带宽稀缺，搬动大数据代价高。

3FS 场景采用：

- **Disaggregated，存算分离：**GPU 计算节点与存储节点是不同机器。
- **Locality-oblivious：**应用不需要为了数据位置把任务安排在相应存储机器附近。
- **高速 RDMA 网络：**支撑计算节点远程访问存储，降低物理位置对任务调度的影响。

```text
GPU 节点    GPU 节点    GPU 节点
     \         |         /
        高速 RDMA 网络
     /         |         \
存储节点    存储节点    存储节点
```

这使 GPU 资源和存储容量、带宽可以分别扩展。

**补充理解：**locality-oblivious 是应用与调度层的设计选择，不是说网络拓扑、拥塞和副本放置从此没有性能影响。课件的“任意客户端以全速访问任意 SSD”依赖其网络和负载条件。

## 17. FUSE 与 native API：兼容性和性能如何兼顾？

对应讲义页 61–63，PDF 第 200–203 页。

### 17.1 FUSE 提供熟悉的文件访问方式

FUSE（Filesystem in Userspace）把文件系统操作交给用户态进程实现：

```text
应用 read()
    ↓
内核 VFS / FUSE 模块
    ↓ 请求队列、跨边界数据传递
用户态 3FS FUSE daemon
    ↓ 网络访问
Storage service
```

应用可以使用熟悉的文件 API；开发者不必把自己的完整文件系统客户端写进内核。

**表述边界：**FUSE 本身仍使用内核模块。课件“无需内核模块”的意思是无需另写一个专用文件系统内核实现，不是整个路径完全没有内核组件。

### 17.2 快硬件让软件开销变得突出

课件指出两类瓶颈：

1. 用户态和内核态之间传递数据带来的内存复制与延迟。
2. 共享请求队列上的锁竞争，使增加线程数不再带来等比例吞吐增长。

课件引用约 400K 次 4 KiB 读取/秒的测试结果。这属于所测 FUSE 路径和环境，不能当成所有 FUSE 实现的理论上限。

### 17.3 Native API：元数据走 FUSE，数据走共享内存

性能敏感应用仍可通过 `open()` 取得 fd，再注册给 native API。实际数据 I/O 使用：

| 结构 | 作用 |
| --- | --- |
| Iov | 应用与客户端共享的数据缓冲区 |
| Ior | 共享请求环，应用提交请求，客户端处理并完成请求 |

```text
元数据：应用 open/close/stat → FUSE → 元数据服务

数据：  应用 ↔ 共享内存 Iov / Ior ↔ 3FS daemon ↔ RDMA ↔ 存储服务
```

设计借鉴 `io_uring` 的异步请求环思想，使批量数据 I/O 避开通常的 FUSE 内核请求队列及相应复制路径。这里的“零拷贝”针对指定共享缓冲区和数据路径，不表示应用的任意内存操作都没有复制成本。

第 13–17 节以课件正文和其中的设计文档截图为主；布局、写 session 与 native API 的原始说明可对照 [3FS Design Notes](https://github.com/deepseek-ai/3FS/blob/main/docs/design_notes.md)。

## 18. 把三个案例放在一起

对应讲义页 64–65，PDF 第 204–205 页。

| 维度 | 早期 NFS 模型 | 经典 GFS | 本讲 3FS |
| --- | --- | --- | --- |
| 主要负载 | 远程共享文件 | 大文件、流式读、追加 | 大量文件、随机读、突发写 |
| 应用接口 | 挂载后使用文件 API | 专用客户端库 | FUSE + native API |
| 元数据 | 文件服务器管理 | 单 master 内存管理，关键状态持久化 | 无状态 meta service + 事务 KV store |
| 对象定位 | `LOOKUP` 得到 fh | 向 master 查询 chunk 位置并缓存 | 打开时取布局，计算 chunk ID 和复制链 |
| 打开状态 | cursor 等保留在客户端 | 不照搬本地 POSIX 接口 | 只跟踪写模式的文件 session |
| 缓存重点 | 数据、属性、路径绑定 | 客户端主要缓存元数据 | 缓存布局，减少数据路径上的元数据请求 |
| 一致性重点 | 缓存验证、close-to-open | Primary 排序、租约、版本 | 事务元数据，协调写 session 与删除 |
| 扩展方法 | 减少远程操作和服务端会话状态 | 分块、多副本、数据绕过 master | 分布式元数据、布局计算、高速独立存储 |

“NFS 不复制数据”只是在本讲基础架构中的设定，不能推导出所有 NFS 部署都没有冗余后端；同样，GFS 的单 master 设计也不意味着持久元数据可以只有一份无保护的内存副本。

可以用四个问题分析任何类似系统：

1. **身份：**名字变化、编号复用以后，如何确认仍是原对象？
2. **状态：**进程崩溃以后，谁保存恢复所需的信息？
3. **可见性：**一次写入后，其他客户端何时、通过什么机制看到它？
4. **路径：**大数据经过谁，哪些步骤需要串行，瓶颈会在哪里？

## 19. 复习自测

1. **为什么不能把所有本地文件 API 直接换成同名 RPC？**  
   本地打开状态、偏移、对象生命期和共享缓存语义，在跨机器后会遇到延迟、崩溃、重试及并发访问问题，需要重新分配责任。

2. **NFS 的 fd、fh、cursor 分别在哪里使用？**  
   fd 是客户端进程的打开引用；fh 标识服务器上的文件对象；cursor 由客户端维护，并转换成 RPC 中的显式 offset。

3. **NFS 无状态为什么仍能有 reply cache？**  
   无状态主要指不依赖每客户端打开会话解释请求。回复缓存是改善重复请求处理的软状态，不是完整的打开文件表。

4. **为什么 file handle 不能直接是路径？**  
   重命名后路径可能指向另一个对象，旧 fd 应继续指向原来打开的文件。

5. **为什么只用 inode number 不够？**  
   编号可被回收复用，需要 generation 区分对象的不同生命期。

6. **加入 generation 后，删除的旧文件还能一直读吗？**  
   不一定。它只能阻止旧句柄误指向新文件，不能替代旧对象生命期管理。

7. **Close-to-open 是否保证每次 read 都看到别人的最新 write？**  
   否。它围绕写者关闭时的写回和读者随后打开时的验证提供可见性，不是每次读写的全局即时同步。

8. **“没有 CLOSE RPC”是否表示 close 不会发网络请求？**  
   否。关闭可能需要完成脏数据写回；而且 NFSv4 本身就有 CLOSE 操作。

9. **GFS 的 master 为什么不必承载全部数据吞吐？**  
   Client 只向它查询元数据，文件数据直接在 client 与 chunkserver 之间传输。

10. **Master 内存中有 chunk 位置表，为什么不一定持久记录它？**  
    可以从持有实际 chunk 的服务器重新收集位置，再通过 heartbeat 更新；命名空间等关键映射仍需持久保存。

11. **三个副本都收到 A、B 两次写，为什么还需要 primary？**  
    到达和执行顺序可能不同。Primary 统一排序，使正常完成的相应修改按一致顺序应用。

12. **Master、primary、chunk version、修改序号分别是什么？**  
    Master 管元数据与租约；primary 为某个 chunk 排序；version 用于识别过时副本；修改序号指定修改执行顺序。

13. **GFS 的“两阶段写入”是否就是 2PC？**  
    不是。它分离数据传播与有序执行，不承诺失败时自动回滚全部副本。

14. **HDFS 中 master 和 chunkserver 对应什么？**  
    分别对应 NameNode 和 DataNode；名称对应不意味着所有协议细节相同。

15. **3FS 的 meta service 无状态，文件元数据保存在哪里？**  
    保存在 FoundationDB 等共享事务存储中；无状态只描述服务进程承担的会话与持久状态责任。

16. **3FS 为什么不跟踪所有只读打开，却跟踪写打开？**  
    减少海量训练样本打开带来的元数据成本，同时避免删除和持续写入并发造成难以回收的 chunk。

17. **布局链为 `[A, B, C]`，chunk 7 应访问哪条链？**  
    按课件简化公式，`7 % 3 = 1`，选择 B；chunk ID 还要包含 inode ID。

18. **Locality-oblivious 是否等于不需要知道存储位置？**  
    否。客户端仍需定位数据；它主要表示任务调度不必为了数据位置而靠近相应存储节点。

19. **3FS native API 绕过的是什么？**  
    主要是通常的 FUSE 数据 I/O 队列和复制路径；元数据操作仍可经过 FUSE，数据通过共享缓冲区和请求环提交。
