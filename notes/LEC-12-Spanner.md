## 1. 本讲主线：把一个电商网站扩展到全球

对应讲义页 2–13、42，PDF 第 3–21、101 页。

前几讲分别解决了存储、通信、并发、故障和复制。本讲用 Spanner 展示：**这些机制怎样组合，才能让跨机器、跨分片的事务仍然具有清晰的一致性语义。**

```text
一台机器上的电商网站
    ↓ 数据要持久保存
文件系统 + 日志
    ↓ 一台机器装不下
分片（sharding）
    ↓ 一笔订单要更新不同分片
2PC：共同提交或共同中止
    ↓ 机器故障是常态
复制 + Paxos：保住每个分片的历史
    ↓ 多个应用服务器并发处理订单
2PL：隔离相互冲突的事务
    ↓ 只读查询多、扫描时间长
MVCC：按统一时间戳读取快照
    ↓ 分片散布全球，不能每次都找一个全局计数器
TrueTime + commit wait：让时间戳顺序符合真实时间先后
```

### 1.1 每个机制各自负责什么？

| 需求 | 机制 | 对应前置内容 |
| --- | --- | --- |
| 在故障后恢复本地数据 | 文件系统、持久化日志 | LEC 2–3、[LEC 7](LEC-7-All-or-nothing-atomicity.md) |
| 数据超过单机容量 | 哈希／范围分片 | [LEC 1.1](LEC-1.1-Scaling.md) |
| 跨机器请求 | RPC | [LEC 4](LEC-4-Remote-procedure-call.md) |
| 多个分片共同提交 | 2PC | [LEC 10](LEC-10-Multi-site-Atomicity-and-Replication.md) |
| 同一分片的多个副本维护一致历史 | Paxos 等复制协议 | [LEC 11](LEC-11-Paxos-and-Raft.md) |
| 并发事务不破坏隔离性 | 2PL 等并发控制 | [LEC 8](LEC-8-Before-or-after-atomicity.md) |
| 只读事务不长期占用读锁 | MVCC | [LEC 9](LEC-9-More-on-before-or-after-atomicity.md) |
| 跨地域时间戳符合真实时间顺序 | TrueTime + commit wait | 本讲重点 |

**三种不同的协调不能混为一谈：2PL 管并发访问，2PC 管跨分片提交，Paxos 管分片内复制。**

### 1.2 扩展前端，不会消除数据竞争

前端若不保存必须绑定某台机器的会话状态，就可以通过负载均衡增加应用服务器。但两个服务器仍可能同时读到 `stock = 1`，各卖出一件，再各写回 `stock = 0`。

结果是数据库显示库存为 0，却已经卖出两件。复制会忠实复制这个错误结果，2PC 也可以把这个错误事务原子地提交；必须另外处理并发隔离。

同样，**sharding 与 replication 是两条轴**：前者让不同机器保存不同的数据，后者让多台机器保存同一逻辑数据的副本。

## 2. Spanner 的课堂模型：每个分片一个复制组

对应讲义页 14–15，PDF 第 23–26 页。

课件将数据简化为 Stock 与 Order 两个分片，每个分片由一个 Paxos group 复制。

```text
                         Client / 应用程序
                          /            \
                         /              \
        Stock 分片的 Paxos group       Order 分片的 Paxos group
        leader + followers             leader + followers
        库存数据、锁、事务状态           订单数据、锁、事务状态
                    \                    /
                     \---- 跨组 2PC ----/
```

| 角色 | 职责 |
| --- | --- |
| Client | 执行业务逻辑、读取数据、缓存待写值、发起提交 |
| Participant leader | 管理本分片的锁，代表该分片参与事务 |
| Coordinator leader | 本次事务中选出的协调者，决定全局提交／中止 |
| Paxos followers | 复制本组日志，在合法切换后帮助恢复状态 |

Coordinator 通常选自参与者中的一个分片 leader，因而可以复用该组的复制机制；不需要为每个事务另设一台没有副本的协调机器。

**表述边界：**“稳定 leader 主要是 Paxos 的性能优化”不能理解成 Spanner 可以让多个节点随意各自管理同一分片的锁。Paxos 本身能容忍多个 proposer 竞争；上层事务服务仍必须保证 leader 权限、锁和恢复状态的一致衔接。

## 3. 读写事务的执行阶段：读时加锁，写先缓存

对应讲义页 16，PDF 第 27–31 页。

以一笔订单为例：

```text
tx.begin()
    stock = READ(stock)
    orders = READ(orders)
    BUFFER_WRITE(stock, stock - 1)
    BUFFER_WRITE(orders, orders + 1)
tx.end()
```

这只是说明两个分片参与事务；实际业务还需要在事务内检查库存是否足够。

### 3.1 读请求去 leader，读取最新值

读写事务读取某条记录时：

1. 请求到达该分片的 leader。
2. 取得相应读锁；若与其他事务冲突，则按并发控制规则等待或中止。
3. 读取最新的合法值并返回客户端。
4. 在事务结束前继续保留必要的锁，保护刚才的读取依据。

课件采用事务结束时统一释放锁的模型。这里的读锁防止“读完后，别人先修改，自己却继续按旧值计算”的问题。

### 3.2 写先放在客户端的 write set

在执行阶段，待写入的值先缓存在客户端，不立刻覆盖数据库：

```text
T.wset = {
    stock  -> old_stock - 1,
    orders -> old_orders + 1
}
```

这样，提交前中止时不需要撤销已经覆盖的数据值，也可以推迟取得写锁，缩短写锁持有时间。中止仍然需要清理事务状态、释放已有锁。

### 3.3 为什么执行阶段的读锁不必每次都复制？

课件说明：读锁先只保存在 leader 上。若事务尚未形成持久承诺，leader 故障后，可以中止该次执行，让客户端重试。

**表述边界：**这依赖于旧事务不能绕过失效的 leader 状态继续提交。尤其不能把它推广为“所有锁和事务状态都可以在切主时丢掉”：进入 PREPARED 之后，参与者已经作出承诺，必须能恢复相应状态。参见第 5 节。

## 4. 读写事务的提交阶段：2PC 建在 Paxos 之上

对应讲义页 17，PDF 第 32–42 页。

先忽略 TrueTime 的时间戳和等待；第 12 节再将它们接入完整流程。

### 4.1 Client 发起提交

`tx.end()` 时，客户端把各分片需要的写集合发给相应 participant leader，并告知选定的 coordinator。

这些请求可以并行发送。由客户端直接把写数据交给参与者，可以避免先把全部数据送到协调者，再跨广域网转发一遍。

### 4.2 非协调者参与组：取得写锁，再持久化 PREPARED

每个非协调者 leader：

```text
取得本分片所需的写锁
    ↓
通过本组 Paxos 记录 prepare 及恢复事务所需的信息
    ↓
记录可靠确立后，向 coordinator 报告准备成功
```

这个顺序保证：即使回复 YES 后当前 leader 故障，新 leader 仍能恢复“已经承诺参与”的状态。

**PREPARED 不等于 COMMITTED。** 此时不能随意释放保护资源，也不能独自决定中止。

### 4.3 协调者参与组：省去单独的 prepare 记录

协调者本身也要取得本分片的写锁，但可以省去独立的 prepare 轮次，把自己的更新相关信息与全局决定一起记录。

“跳过 prepare”省去的是一轮独立的准备日志，不是省去本地并发控制、可恢复性检查或对其他参与者的等待。

### 4.4 收齐成功答复后，复制全局决定

协调者收齐其他参与者的准备成功答复后，通过自身 Paxos group 可靠记录全局 COMMIT 决定。

```text
所有参与者具备提交条件
    + 协调者组可靠保存 COMMIT 决定
    → 故障恢复必须继续这个提交结果
```

在本节简化模型里，这时可以通知客户端成功；完整 Spanner 还要满足 commit wait，不能只完成日志复制就直接对外确认。

### 4.5 各参与者获知结果，完成应用并解锁

协调者把最终结果通知参与者。参与者通过自己的 Paxos group 记录结果，应用更新，再释放锁。

课件把这些后续工作移出客户端成功响应的关键路径。因此客户端收到成功，不要求每个 follower 此时已经应用完数据。

**为什么仍然原子？** 全局结果已经可靠确立；尚未完成的分片通过锁和后文的快照安全条件阻止不合法的读取，恢复后继续执行同一决定。系统不允许读取者把“某分片已应用、另一分片未应用”拼成半个事务。

## 5. 故障恢复：先判断已经作出了什么承诺

对应讲义页 16–17，PDF 第 27–42 页；结合 LEC 10 的 2PC 恢复规则。

| 故障时所处阶段 | 可以怎样处理？ | 不能做什么？ |
| --- | --- | --- |
| 尚在读取、缓存写入，未形成准备承诺 | 使失效的执行中止，重新读取并重试 | 用已经失去保护的旧读值直接继续提交 |
| 参与者已可靠记录 PREPARED | 恢复准备状态，向协调者查询／等待结果 | 仅凭超时单方面 ABORT |
| 协调者尚未作出可靠的最终决定 | 按恢复协议确认历史，再作出合法决定 | 因为本机没看到 COMMIT 就断言全局没提交 |
| COMMIT 已在协调者组可靠确立 | 恢复 COMMIT，重发通知，继续完成 | 因切主、回复丢失而改成 ABORT |
| 参与者已获知 COMMIT，但尚未应用完 | 根据日志继续应用，完成后解锁 | 暴露半个事务的结果 |
| 某个必需复制组不能形成 quorum | 等待恢复，相关事务可能阻塞 | 把“副本数量多”当作必然可用 |

### 5.1 “提交消息失败，事务就中止”必须加条件

讲义页 17 的一处动画写到：commit 消息失败，例如发生 leader change，就中止事务。

**课件校正：**必须区分“已确认中止”和“调用者没收到成功”。如果全局 COMMIT 已经可靠确立，通知丢失或切主不能撤销决定；客户端暂时不知道结果，不代表数据库没有提交。这也与 [LEC 10 的 2PC 规则](LEC-10-Multi-site-Atomicity-and-Replication.md)一致。

实际接口也区分事务中止与结果未知，参见 [Spanner Commit RPC 的错误语义](https://docs.cloud.google.com/spanner/docs/reference/rpc/google.spanner.v1#google.spanner.v1.Spanner.Commit)。

### 5.2 Paxos 改善 2PC 的恢复能力，但没有消灭阻塞

协调者状态保存在复制组里，单台协调机器故障时，满足接管条件的新 leader 可以继续处理。参与者的准备状态也可由自己的复制组恢复。

但如果关键复制组整体不可达，或不能形成 quorum，事务仍可能等待。**容忍某些故障与任何故障下都继续服务，是不同的保证。**

## 6. 性能分析：11 个消息延迟从哪里来？

对应讲义页 18–20，PDF 第 43–45 页。

设一次单向消息传递的延迟为 `d`，一次 RTT 为 `2d`。课件假设稳定 leader 的 Multi-Paxos 正常路径约需一次 RTT。

| 关键路径步骤 | 单向消息延迟数 |
| --- | ---: |
| 两次串行读取，各为 client 到 leader 的往返 | 4 |
| Client 并行向各参与者发送提交请求 | 1 |
| 非协调者组复制 prepare | 2 |
| 参与者向协调者报告 YES | 1 |
| 协调者组复制 COMMIT | 2 |
| 协调者回复 client | 1 |
| **合计** | **11** |

```text
两次读取：4d
提交路径：d + 2d + d + 2d + d = 7d
总计：11d
```

参与者随后记录最终结果、应用数据的阶段，不计入这一示意模型的响应关键路径；它仍有通信和存储成本。

### 6.1 跨地域时，复制 RTT 可能主导延迟

课件给出两种数量级示意：

- 同数据中心，若 `d ≈ 0.25 ms`，则 `11d ≈ 2.75 ms`，约为 3 ms。
- 若关键路径上的两轮 Paxos 各需跨地域 RTT 150 ms，仅它们就约为 300 ms。

它们是特定拓扑下的估算，未统一纳入锁等待、磁盘、排队、重试和 TrueTime 等成本。

课件还引用历史实验：1、10、200 个 2PC 参与者对应平均提交延迟约 14.6、22.8、122.5 ms。该实验的客户端与各 zone 网络距离小于 1 ms，不能把它当成上面跨洋示例的实测值，更不能当成今天产品的延迟承诺。

### 6.2 “像一台永不故障的机器”是语义抽象

课件用这句话强调：应用不需要自行拼接每个副本、分片的状态。

**表述边界：**它不表示没有中止、没有超时、无限容量或无限容错。可串行化描述观察到的事务结果；容量与可用性仍受资源、quorum 和网络条件约束。

## 7. 为什么只读事务要换一条路径？

对应讲义页 21–25，PDF 第 46–57 页。

订单列表、报表、审计等只读事务可能访问许多记录和分片，持续较长时间。若一路持有读锁，写事务就可能长时间等待读者。

Spanner 的课堂组合是：

```text
读写事务：2PL 保护读取依据和写入冲突
          提交时安装带时间戳的新版本

只读事务：选定一个快照时间戳
          所有读取都使用这个快照，不取得事务读锁
```

这里“读写事务中的读”仍然走加锁路径，不能把口号“MVCC for reads”理解为系统里所有 READ 都不加锁。

### 7.1 多版本的基本规则

记：

| 记号 | 含义 |
| --- | --- |
| `T.cts` | 读写事务的提交时间戳，commit timestamp |
| `T.sts` | 只读事务选择的快照时间戳；课件称 start timestamp |
| `X_i.cts` | 记录 X 的第 i 个已提交版本的时间戳 |

读取规则为：

```text
READ(X, T.sts)
    = 时间戳最大的、满足 X_i.cts ≤ T.sts 的已提交版本 X_i
```

例如：

| 版本时间戳 | X | Y |
| --- | ---: | ---: |
| 8 | 80 | 50 |
| 10 | 100 | 50 |
| 12 | 200 | 50 |

只读事务选 `sts = 11`，即使实际执行读取时版本 12 已经提交，仍然读取 `X = 100`、`Y = 50`。

“每次提交留下整个数据库快照”是逻辑视角。实现可以只保存修改记录的新版本；不需要每次复制整个数据库。

### 7.2 读写事务提交时安装新版本

在暂时省略 2PC 与复制的示意模型里：

```text
读取：取得读锁，读取最新合法版本
计算：写入客户端缓冲区
提交：取得所有必要写锁
      分配与串行化顺序相容的 cts
      把 write set 安装为带同一 cts 的新版本
      完成提交，再释放锁
```

MVCC 解决旧版本如何保留与选择；时间戳分配、事务可见性和并发控制还必须配合，才能获得可串行化的整体执行。不能把任意 MVCC 实现都等同于可串行化。

### 7.3 两处容易误读的“无锁”表述

讲义页 21 写到获取读锁“需要 Paxos”，但讲义页 16 又明确说执行阶段的读锁只在 leader 上。

**课件校正：**本讲模型里，每次读写事务的 READ 并不都触发一轮 Paxos。只读路径优化的直接动机是减少锁管理、冲突和长期持锁，不能把“每个读锁一轮共识”作为统一成本模型。

此外，**不取得事务读锁，不等于任何时候都立即返回**。副本是否已经具备完整快照，是另一个条件，见第 13 节。

## 8. 时间戳方案一：全局计数器

对应讲义页 26–27，PDF 第 58–63 页。

单机上，可以用一个原子递增计数器编号事务提交，读者获取一个快照边界。

```text
分配提交编号：cts = NEXT_TIMESTAMP()
只读事务开始：sts = READ_SAFE_SNAPSHOT_TIMESTAMP()
```

关键是给所有相关操作一个共同的比较尺度。

### 8.1 分配编号不等于发布完整快照

课件用 `FAA(global_time)` 简写分配过程，但这不是完整的提交实现：

- 要先规定 FAA 返回递增前的值还是递增后的值，不能在例题中混用。
- 一个编号已分配，不代表对应事务的全部版本都已安装。
- 读者选中某个时间戳后，必须确保该时间戳下应出现的事务不会被遗漏。

**补充理解：**这与 LEC 9 的“只分配 cts，仍可能读到半个快照”是同一个问题。全局计数器提供顺序，还需要发布／等待协议把编号与可见性接起来。

### 8.2 为什么全球系统不愿每次都访问它？

如果每个事务都向一台 timestamp server 请求编号或最新边界：

1. 远端数据中心增加一次跨地域通信，开始读取前就可能先等待一次跨洋 RTT。
2. 所有事务汇聚到同一个服务，形成吞吐量与可用性的集中点。

把 timestamp server 复制起来可以改善单点故障，但仍需要协调其状态，不能免费消除延迟和集中分配成本。

### 8.3 唯一编号是教学方案，不是 Spanner 时间戳的普遍承诺

讲义页 26 用“唯一且递增”介绍全局计数器模型。需要记住的是与冲突、串行化和真实时间相容的顺序要求。

**表述边界：**Spanner 的提交时间戳并不保证全局唯一；写入互不重叠字段的事务可能得到相同时间戳。不能把它直接当作任意事务的唯一 ID。参见 [Spanner 提交时间戳说明](https://docs.cloud.google.com/spanner/docs/commit-timestamp)。

## 9. 时间戳方案二：缓存旧时间，快照一致但可能不新鲜

对应讲义页 28–31，PDF 第 64–77 页。

每个数据中心可以缓存全局计数器的值，后台周期更新。只读事务从附近缓存取 `sts`，避免每次跨地域查询。

假设事务把 A、B 一起更新到时间戳 3，另一个数据中心仍缓存着 0：

```text
已提交历史：
    t=0: A0, B0
    t=1: A1, B1
    t=3: A3, B3

只读事务使用缓存 sts=0：
    READ(A) → A0
    READ(B) → B0
```

这可以是一个完整的旧快照，不是 `A3 + B0` 这种混合状态。前提是旧版本仍被保留，而且快照读取本身正确。

### 9.1 一致的旧快照，仍可能不符合用户观察

课件的付款例子：

| 顺序 | 事件 |
| --- | --- |
| 1 | 订单原来为 UNPAID |
| 2 | T1 把订单改为 PAID，以 `cts = 6` 提交并返回成功 |
| 3 | 用户看到付款成功后刷新页面，启动 T2 |
| 4 | T2 使用当地旧缓存 `sts = 5` |
| 5 | T2 返回 UNPAID |

T2 读到了合法旧快照，却违反“已经付款成功，再刷新应当看到付款”的实时顺序要求。

### 9.2 区分三个层次

| 性质 | 要求 |
| --- | --- |
| 一致快照 | 同一事务的多次读取来自同一个完整逻辑时刻 |
| 可串行化 | 整体效果可以由某个事务串行顺序解释 |
| 外部一致性／严格可串行化 | 可串行化，并且串行顺序尊重非重叠事务的真实时间先后 |

在付款例子里，把读取排在付款之前可以解释它读到 UNPAID，所以单凭可串行化还不足以排除这种观察；但这与用户已经观察到的先后顺序不符。

**外部一致性：若 T1 已完成，T2 才开始，那么串行解释必须把 T1 放在 T2 前面。** 对并发重叠事务，不额外强制一个仅由开始时间决定的先后关系。

课件用“T2 必须看到 T1 的写入”作直观解释。更准确地说，T2 不能读取排在 T1 之前的状态；如果后来又有合法写入覆盖了同一记录，T2 可以看到那个更新的值。[官方外部一致性说明](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency)也区分了事务顺序与单对象操作的一致性。

## 10. 时间戳方案三：TrueTime 返回区间

对应讲义页 32–34，PDF 第 78–80 页。

直接使用不同机器的普通物理时钟会出问题：A 的时钟快，先完成的事务可能得到 120；B 的时钟慢，后来才开始的事务却得到 115。版本比较就可能把新事务排到旧事务之前。

Spanner 的办法是显式表示时钟不确定性：

```text
TT.now() → [earliest, latest] = [L, U]

保证：L ≤ 调用时的真实时间 ≤ U
```

课件先用一个 time server 的时间作为共同参照，后面再解释如何用多台 timemaster 和高精度时间源实现。

### 10.1 误差界不是“平均很准”

假设一次同步后经过 30 秒，本机最大漂移为每秒 200 微秒，则这段时间新增的单侧不确定性为：

```text
30 × 200 μs = 6000 μs = 6 ms
```

若同步时没有其他误差，可以写成“本地估计时间 ±6 ms”，总区间宽度为 12 ms。实际还要加入同步通信及时间源本身的不确定性。

平均误差小不能替代有效的误差上界。后面的正确性推导要求真实时间确实位于区间内；如果区间失真，就不能继续引用该证明。

### 10.2 两个端点分别能证明什么？

| 信息 | 能推出什么？ |
| --- | --- |
| 当前 `L > t` | 时间戳 t 肯定已经过去 |
| 当前 `U < t` | 时间戳 t 肯定还没到 |
| `L ≤ t ≤ U` | 仅凭当前区间无法判断 t 是否已经过去 |

区间中点是估计值，不具有“肯定在前／后”的保证。TrueTime 的价值在于把这个未知范围交给事务协议处理。

## 11. Commit wait：让提交时间戳先成为过去

对应讲义页 35、38，PDF 第 81–87、97 页。

这是本讲最重要的推导。

### 11.1 课堂简化规则

读写事务 W 决定尝试提交时，取得区间 `[L1, U1]`，选择：

```text
W.cts = U1
```

此时 `U1` 可能还在真实时间的未来，不能立刻向外宣布完成。必须等待，直到能够确定真实时间已经超过 `U1`。

随后开始的只读事务 R 取得 `[L2, U2]`，选择：

```text
R.sts = U2
```

注意：R 的快照时间戳取自开始后的 TrueTime 调用，不等于它物理上开始执行的精确时刻。

### 11.2 等待条件要看新的下界

正确条件为：

```text
TT.after(W.cts)
等价于用新的区间检查：TT.now().earliest > W.cts
```

教学伪代码：

```text
cts = TT.now().latest       // 先选定，之后保持不变
可靠记录事务提交决定

while TT.now().earliest <= cts:
    等待

满足事务协议的其余条件后，允许结果对外可见并回复成功
```

每次检查时，比较的是**当前下界**与**先前选定的 cts**。不能在循环里不断把 cts 更新成新的上界，也不能用 `当前上界 > cts` 代替：上界越过了，只能说明“可能已经过去”。

### 11.3 为什么能保证后来的读取包含此前提交？

设 `r1` 是 W 对外完成时的真实时间，`r2` 是之后 R 获取读时间戳时的真实时间。

```text
W.cts = U1

commit wait：       U1 < r1
W 完成后 R 才开始： r1 < r2
TrueTime 区间保证： r2 ≤ U2
R.sts = U2

因此：W.cts = U1 < r1 < r2 ≤ U2 = R.sts
```

所以 R 的快照边界在 W 的提交时间戳之后。配合正确的版本读取和副本就绪条件，R 不会漏掉 W 应有的效果。

**这里用的是“W 已对外完成后，R 才开始”，不是“W 刚决定要提交时，任意并发读都必须看到它”。**

### 11.4 如果不等，会怎样？

构造一个所有区间都合法的例子，单位为毫秒：

```text
真实时间 100：W 取得 [90, 110]，选择 cts=110。
真实时间 101：若 W 不等待，就向用户返回成功。
真实时间 102：用户开始 R；R 取得 [100, 104]，选择 sts=104。

W 已完成在先，但 R.sts=104 < W.cts=110。
按版本规则，R 仍会排除 W 的写入。
```

这里没有任何时钟违反自己的误差界。出错原因是：**W 过早宣布一个仍在未来的时间戳已经完成。**

### 11.5 为什么只读事务不能直接用 L2？

假设 W 的 `cts=110`，已完成等待并返回。稍后的 R 在真实时间 112 取得 `[100, 120]`。

- 选 `sts=100`，会遗漏 W。
- 选 `sts=120`，满足“至少包含开始前已经完成的事务”的时间戳要求。

使用 U2 可能增加读取等待，但单独选择 L2 不能给出相同的新鲜度保证。

## 12. 把 TrueTime 接回完整的提交流程

对应讲义页 17、24、35、38，PDF 第 32–42、52–55、81–87、97 页。

前半讲的 2PC/Paxos 负责提交决定可靠且一致，后半讲的 TrueTime 负责时间戳顺序与真实时间相容。

### 12.1 事务时间戳还要满足本地历史约束

**补充理解：**完整流程的提交时间戳 `s` 还受参与者 prepare 时间戳及组内历史约束，不能机械地总令 `s = 某次 TT.now().latest`。可以把它理解为选择满足所有约束的时间戳，再等待 `TT.after(s)`。[Spanner 原论文 §4.2.1](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf)

```text
s ≥ 各参与者 prepare 时间戳的最大值
s > 协调者 leader 此前已分配的时间戳
s > 协调者接收提交请求时所取的 TrueTime 上界
```

```text
各参与组：取得锁，可靠记录准备状态
    ↓
协调者：收集准备结果，为整个事务选择合法的 s
    ↓
协调者组：通过 Paxos 可靠记录 COMMIT(s)
    +
commit wait：确定真实时间已经超过 s
    ↓
向客户端回复，向参与者通知结果
    ↓
参与者记录结果，以同一个 s 安装新版本，然后释放锁
```

所有参与分片采用同一个事务提交时间戳，才可以在快照边界上把整笔事务一起纳入或排除。

### 12.2 区分三个“提交”事件

| 事件 | 意义 |
| --- | --- |
| 提交决定可靠确立 | 恢复不能再把 COMMIT 改成 ABORT |
| Commit wait 满足 | 选定的提交时间戳已经肯定属于过去 |
| 某个副本应用完成 | 该副本本地状态已经反映相应写入 |

讲义页 38 的“等待期间事务未提交”应理解为：还不能按该规则对外完成／暴露提交效果。不能据此推断已经可靠记录的 COMMIT 仍可撤销。

### 12.3 等待并不必然全部叠加在网络延迟之后

课堂用“等待约一个区间宽度”说明成本。实际实现可将 commit wait 与 Paxos 通信重叠；只有尚未满足的等待部分会继续拖延响应。[Spanner 原论文 §4.2.1](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf)

因此不应把所有路径都写成固定的：

```text
11 × 单向延迟 + 完整的一次误差窗口
```

实际延迟取决于何时选定 s、日志复制何时完成、此时 TrueTime 下界推进到了哪里，以及是否还有锁等待。

## 13. 有了正确时间戳，副本就能立刻回答吗？

对应讲义页 22–25、35，PDF 第 47–57、81–87 页；本节补齐课堂模型省略的读取前提。

**不能。时间戳说明应该读哪个快照，不能证明该副本已经拥有这个快照。**

### 13.1 同一时间戳仍可能被落后副本错误解释

例如事务 W 在时间戳 20 同时更新 X、Y：

```text
X 所在副本：已经应用 W，拥有 X@20。
Y 所在副本：还未应用 W，只拥有 Y@10。

读者选择 sts=25。
若仅在“本机现有版本”里取最大 cts≤25：
    X → X@20
    Y → Y@10
就可能读到半个 W。
```

MVCC 版本过滤条件本身不够。Y 所在副本必须先确定：时间戳不超过 25 的相关提交已经完整反映，且不会再补来一个应纳入快照的未决事务。

### 13.2 Safe time：快照是否已经可安全提供

**补充理解：**Spanner 用 `t_safe` 标记副本可安全提供读取的时间戳边界。读取 `sts` 要求 `sts ≤ t_safe`；复制落后和未决的准备事务都可能阻碍其推进。读者因此可能等待，但不需要取得事务读锁。[Spanner 原论文 §4.1.3–4.1.4](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf)

```text
选定 sts
    ↓
各读取位置确认可以安全提供 sts 的快照
    ↓
返回最大 cts≤sts 的已提交版本
```

由此可以同时理解两件事：

- 写事务成功响应时，不必等待所有副本都应用完。
- 后来的强一致读取也不能随意从一个落后副本返回旧值。

**TrueTime 解决时间边界，2PC/Paxos 和快照就绪条件解决这个边界内的事务是否完整。**

## 14. TrueTime 的区间怎样从同步 RPC 算出来？

对应讲义页 36–37，PDF 第 88–96 页。

同步在后台进行，事务读取本机已经维护的区间，不需要每个事务都向 timemaster 发 RPC。

### 14.1 先定义三个可测时间

| 记号 | 使用哪个时钟？ | 含义 |
| --- | --- | --- |
| `t_begin` | 客户端时钟 | 发出同步请求 |
| `t_srv` | 时间服务器时钟 | 服务器处理请求时采样的时间 |
| `t_end` | 客户端时钟 | 收到同步回复 |
| `T` | 客户端时钟 | 此后调用 TrueTime 的当前时间，`T ≥ t_end` |
| `T_s` | 时间服务器时钟 | 希望估计的、与当前 T 对应的服务器时间 |

```text
服务器：                 t_srv ---------------------- T_s
                         ↑     \
客户端：      t_begin ---/------ t_end --------------- T
```

服务器采样事件发生在客户端发送和接收之间，但不知道它在往返区间内的精确位置，也不假设两个方向延迟相等。

### 14.2 先忽略时钟速率差异

从服务器采样到现在，经过的时间至少为 `T - t_end`，至多为 `T - t_begin`，所以：

```text
t_srv + (T - t_end) ≤ T_s ≤ t_srv + (T - t_begin)

L = t_srv + T - t_end
U = t_srv + T - t_begin
```

这时区间宽度是：

```text
U - L = t_end - t_begin = 同步 RPC 的 RTT
```

即使时间服务器极其准确，也无法仅靠这三个时间戳知道服务器采样点在 RTT 中的精确位置。

### 14.3 再加入漂移界

为避免符号混淆，本笔记用 `ρ` 表示课件公式里的时钟漂移率。按“每单位客户端时间对应的服务器时间增量在 `[1-ρ, 1+ρ]`”这一速率约定，有：

```text
L = t_srv + (T - t_end)   × (1 - ρ)
U = t_srv + (T - t_begin) × (1 + ρ)

L ≤ T_s ≤ U
```

这里假设用于测量经过时间的本地时钟连续推进，服务器参考本身没有另加的不确定性。更完整实现还要把时间源误差等因素计入。

**为什么下界减、上界加？** 求下界时选择“采样尽可能晚、此后走得尽可能慢”；求上界时选择“采样尽可能早、此后走得尽可能快”。

### 14.4 展开宽度：网络延迟和同步间隔分别贡献多少？

令：

```text
RTT = t_end - t_begin
age = T - t_end
```

则由上式直接推出：

```text
U - L
    = RTT + ρ × (2T - t_begin - t_end)
    = RTT × (1 + ρ) + 2ρ × age
```

因此：

- 同步 RPC 越慢，初始区间越宽。
- 距离上次同步越久，累积漂移使区间越宽。
- 更小的漂移界能减慢区间扩张，但不会自动消除网络带来的不确定性。

### 14.5 一个完整计算例子

以下为自拟例题，所有时间数值单位为毫秒：

```text
t_begin = 1000
t_end   = 1004
t_srv   = 5002
T       = 1104
ρ       = 200 μs/s = 0.0002
```

客户端与服务器的读数可以有偏移；这里并没有要求两个时钟数值相等。

```text
L = 5002 + (1104 - 1004) × 0.9998
  = 5101.98

U = 5002 + (1104 - 1000) × 1.0002
  = 5106.0208

U - L = 4.0408 ms
```

也可以用展开式复核：

```text
RTT × (1 + ρ) + 2ρ × age
    = 4 × 1.0002 + 2 × 0.0002 × 100
    = 4.0408 ms
```

## 15. 误差窗口、等待时间与多台 timemaster

对应讲义页 38–41，PDF 第 97–100 页。

### 15.1 “等待一个窗口宽度”的直觉与边界

若当前只知道真实时间在 `[L, U]` 内，并选择 `cts=U`，最保守情况是真实时间还在 L 附近，需要等它走过大约 `U-L` 的距离。

讲义页 38 给出带漂移修正的 `(U-L)(1+ε)`。适合记住的关系是：**不确定性越大，保证 cts 已经过去所需的等待通常越长。**

**表述边界：**固定睡眠公式依赖速率误差的定义。在上一节的精确速率约定下，用本地经过时间 D 保证服务器至少前进宽度 W，需要 `(1-ρ)D ≥ W`，即 `D ≥ W/(1-ρ)`；`W(1+ρ)` 只是一阶近似。协议判断应以 `TT.after(cts)` 为准，避免把近似等待公式当作严格证明。

### 15.2 漂移率、半宽、全宽是不同量

| 量 | 本笔记记号 | 单位 |
| --- | --- | --- |
| 时钟速率偏差上界 | `ρ` | 无量纲，例如 `200 μs/s = 0.0002` |
| TrueTime 区间全宽 | `U-L` | 时间，例如 ms |
| TrueTime 区间半宽 | `(U-L)/2` | 时间，例如 ms |

课件推导中的 ε 是漂移率；引用原论文的 TrueTime 误差图时，图里的 ε 表示时间不确定性的半宽。做题时要先看定义和单位，不能看到同一个希腊字母就直接代入。

### 15.3 多台 timemaster 减少单一来源的影响

课件从单台时间服务器模型推进到：每个数据中心部署多个 timemaster，本机后台向本地及其他数据中心的多个时间源同步。

时间源包括 GPS 和原子钟。两种来源的故障模式不同，组合起来可以减少对单一来源的依赖。普通服务器通过同步和保守漂移界维护自己的区间，不需要每台业务机器都配一台原子钟。

课件提到采用 Marzullo 算法的变体，但未展开算法细节。这里应掌握的是“用多个有界时间估计维持可信区间”，不需要把它记成简单对时间读数取平均。

### 15.4 高精度硬件不能消除网络不确定性

讲义页 41 展示了 timemaster 维护停机时，不确定性出现尖峰的历史测量。时间源不可用、同步变慢或间隔变长，都可能使区间扩大，继而增加等待成本。

只要误差区间仍有效，系统可以用更多等待维持原来的正确性要求；区间扩大不必然意味着已经返回错误数据。

**课件校正：**该页把 `t_srv - t_begin` 近似看成单向网络延迟。但二者来自不同机器的时钟，若偏移未知，直接相减不能得到单向延迟。前一节的推导只使用同一客户端时钟上的差值和请求／回复的因果顺序。

图中的高精度原子钟照片用于展示时间源概念，不能据此推断所有 Spanner 机器使用该型号或具备相同单机精度。

## 16. 把各种保证接成一条链

对应讲义页 42，PDF 第 101 页。

| 机制 | 直接解决的问题 | 单独使用时仍缺什么？ |
| --- | --- | --- |
| Sharding | 数据容量与负载分散 | 跨分片事务语义 |
| Paxos | 一组副本可靠维护同一历史 | 跨组共同提交与业务事务隔离 |
| 2PC | 参与分片共同提交／中止 | 并发事务的串行化，以及故障时的进展条件 |
| 2PL | 保护读写依赖、控制冲突 | 长只读事务的低干扰执行 |
| MVCC | 保留版本、按时间戳读取快照 | 时间戳正确性与快照完整性 |
| TrueTime | 给出真实时间的可信区间 | 事务决定、复制和并发控制 |
| Commit wait | 使提交时间戳在对外完成前肯定过去 | 副本已经完整应用所需快照的保证 |
| Safe time | 判断副本能否回答指定时间戳的读取 | 选择符合请求语义的快照时间戳 |

### 16.1 复习时抓住的十二条规则

1. **分片与复制分别解决容量和冗余。** 一个分片可以有多个副本。
2. **2PL、2PC、Paxos 分工不同。** 三者的阶段和投票不能互相替代。
3. **读写事务读取时取得锁，写入先缓冲。** 提交阶段再取得必要写锁。
4. **YES 必须有可恢复的承诺支撑。** PREPARED 不能因超时自行撤销。
5. **可靠 COMMIT 不能因回复丢失而中止。** 结果未知与已中止不同。
6. **同一事务的更新共享提交时间戳。** 快照要把整笔事务一起纳入或排除。
7. **一致快照可以很旧。** 外部一致性还要求尊重已完成事务的真实时间顺序。
8. **TrueTime 返回区间，正确性依赖区间覆盖真实时间。** 平均准确度不能替代误差界。
9. **选择 cts 后，等待新的下界越过它。** 不是等待新的上界越过它。
10. **只读快照用同一个 sts。** 每次 READ 重新取当前时间会破坏固定快照。
11. **无锁不等于无等待。** 副本落后或未决事务可能阻碍快照读取。
12. **先辨认量纲再代公式。** 漂移率、区间半宽、区间全宽不能混用。

### 16.2 做本讲时序题的顺序

```text
① 标出分片与副本组，确认哪些是 2PC 参与者、谁是 coordinator。
② 标出读锁、写锁、PREPARED、可靠 COMMIT、应用和解锁时刻。
③ 计算关键路径时，把单向延迟、RTT 和可并行步骤分开。
④ 给每个事务标明 cts 或 sts；同一事务读取始终使用同一 sts。
⑤ 区分真实时间、机器本地时间、事务时间戳这三种数值。
⑥ 写出每个 TrueTime 区间，并检查它确实覆盖对应真实时间。
⑦ 写出 commit-wait 条件：当前 L > 已选定的 cts。
⑧ 检查“前一事务完成 → 后一事务开始”的真实时间边。
⑨ 用时间戳不等式判断版本是否应出现，再检查副本是否能安全回答。
⑩ 遇到故障，先判断持久承诺能否恢复，再区分安全性与进展性。
```

## 17. 复习自测

1. **为什么每个分片都用 Paxos，还需要 2PC？**  
   Paxos 统一一组副本的历史；一笔事务更新多个分片时，仍需协调各组共同提交或中止。

2. **为什么用了 2PC，还可能出现超卖？**  
   原子提交不等于并发隔离。两个事务仍可能读取同一旧库存，再提交基于旧值的更新。

3. **执行阶段为什么把写入缓存在 client？**  
   避免提前覆盖数据，并推迟取得写锁；提交前中止时无需撤销已经写入主数据的新值。

4. **协调者省略自己的 prepare，是否意味着不用加写锁？**  
   不是。它仍要保护本分片的读写，只是省略独立的准备日志轮次。

5. **参与者报告 YES 前为什么要经过本组 Paxos？**  
   让准备承诺在允许的 leader 故障后仍可恢复，不能只记在易失的单机状态里。

6. **协调者已可靠记录 COMMIT，回复丢了，可以 ABORT 吗？**  
   不可以。客户端暂时不知道结果，恢复仍必须继续提交。

7. **11 个消息延迟是不是所有 Spanner 事务的固定成本？**  
   不是。它对应两次串行读取、特定多组提交路径和稳定 leader 的课堂模型。

8. **只读事务的每次 READ 都读当前最新值，是否等价于 MVCC 快照？**  
   不等价。事务中间可能有提交，必须用统一的 sts 才能固定同一个快照。

9. **`sts=11`，X 有时间戳 8、10、12 的版本，读哪个？**  
   读时间戳 10 的已提交版本，前提是副本能安全提供该快照。

10. **旧缓存时间一定会读到半个事务吗？**  
    不一定。正确 MVCC 可以返回完整旧快照；问题可能是不够新鲜。

11. **付款成功后刷新还看到 UNPAID，违反哪项要求？**  
    在没有后续覆盖写入的例子里，违反尊重真实时间先后的外部一致性；单凭可串行化不能排除它。

12. **`TT.now()=[100,120]`，能断言时间戳 110 已经过去吗？**  
    不能。真实时间可能仍为 105，也可能已经为 115。

13. **选择 `cts=120` 后，新区间 `[119,129]` 能结束等待吗？**  
    不能；下界尚未大于 120。新区间 `[121,131]` 则满足条件。

14. **为什么不能一边等待一边把 cts 改成当前 U？**  
    事务时间戳必须固定；不断把目标移到新的上界会改变已经约定的版本时间，也可能永远追不上目标。

15. **Commit wait 的核心证明链是什么？**  
    `写 cts < 写对外完成时刻 < 后来读的取时刻 ≤ 读 sts`。

16. **为什么直接使用普通机器时钟不够？**  
    不同机器可能有偏移和漂移，后来事务的本地读数可能反而更小。

17. **使用原子钟就不需要误差区间了吗？**  
    不是。时间源到普通机器的通信、同步间隔和本地漂移仍引入不确定性。

18. **30 秒、200 微秒／秒，对应多大的新增误差？**  
    单侧 6 ms，若只计这一项，对称区间全宽 12 ms。

19. **无漂移时，同步 RPC 推导出的区间宽度是多少？**  
    `t_end - t_begin`，即 RTT；不必假设去程与回程等长。

20. **`t_srv-t_begin` 为什么不能直接当单向延迟？**  
    它跨越两个时钟，未知偏移也在差值中。同一客户端时钟上的 RTT 才可直接测量。

21. **TrueTime 每次调用都要联系远端时间服务器吗？**  
    本讲设计不需要。后台同步维护区间，事务读取本机估计。

22. **误差区间变宽会怎样？**  
    只要界仍有效，主要影响可能是等待变长；不能直接推出数据一致性已经被破坏。

23. **有正确的 sts，为什么还要检查副本就绪？**  
    落后副本可能尚未应用某个 `cts≤sts` 的写入，直接取本地旧版本会遗漏事务。

24. **成功提交是否要求所有副本同时应用完？**  
    不要求，但尚未追上的副本不能随意回答会遗漏已提交效果的读取。

25. **TrueTime 能替代 Paxos 或 2PC 吗？**  
    不能。时间区间不决定提交结果，也不复制数据；这些机制必须共同作用。
