## 1. 本讲主线

对应讲义页 1–5，PDF 第 2–9 页。

**RPC（Remote Procedure Call）让程序通过类似本地函数调用的接口，调用另一个地址空间中的过程。它隐藏通信细节，但无法完全隐藏远程故障。**

接着上一讲的文件系统，可以把文件放在远端服务器上：应用仍然调用 `Read()`、`Write()`，RPC 负责把操作送到文件服务器，再返回结果。这是构建分布式文件系统的一种基础机制。

本讲围绕三个问题展开：

1. **如何调用？** 用 stub（桩代码）把函数调用转换为请求与响应。
2. **如何传数据？** 用统一编码与 schema 处理机器、语言和版本差异。
3. **失败后怎么办？** 用超时、重试、请求标识与去重定义调用语义。

```text
本地调用接口
    ↓ stub 封装
请求消息：调用哪个过程、参数是什么、属于哪次调用
    ↓ 编码与网络传输
远端解码、分派、执行
    ↓ 返回响应
客户端取得结果，或面对结果未知的故障
```

课件提到 Sun RPC 曾广泛用于 UNIX，并作为 NFS 的基础；Thrift、gRPC 是其他 RPC 框架例子。RMI（Remote Method Invocation）可以理解为面向对象的方法远程调用形式。

## 2. 从 socket 到 stub：一次 RPC 如何完成？

对应讲义页 4、6–15，PDF 第 8、10–26 页。

### 2.1 为什么不直接用 socket？

socket 提供 `read()`、`write()`、`sendmsg()` 等通信接口。直接使用时，每个应用都需要处理连接、消息构造、参数转换、收发与结果解析。

课件用客户端向时间服务器查询时间作为例子：

```text
procedure SYNC_CLOCK():
    t ← GET_TIME(SECONDS)
    SET_CLOCK(t)
```

若手写网络通信，`GET_TIME()` 大致会展开为：

```text
连接 TimeServiceAddr
发送 {过程名: "Get time", 参数: 编码后的 SECONDS}
接收响应
检查响应状态
解码时间并返回
```

RPC 把这些共用工作放进框架，让应用代码继续围绕业务函数组织。

**补充理解：**查询远端时间只是调用流程示例。网络传输存在延迟，直接把返回值设成本地时间，并不是精确时钟同步算法。

### 2.2 客户端与服务端 stub 的职责

| 组件 | 主要工作 |
| --- | --- |
| Client stub | 打包参数，发送请求，等待响应，检查状态，解包结果 |
| Server / service stub | 接收并解包请求，调用真实服务函数，打包并返回结果 |
| 真实服务函数 | 执行业务逻辑，例如读取时钟、转换时间单位 |

一次成功调用的顺序：

```text
客户端应用       Client stub          Server stub        真实服务
    | GET_TIME()     |                     |                 |
    |--------------->|                     |                 |
    |                | 编码参数、发送请求  |                 |
    |                |-------------------->|                 |
    |                |                     | GET_TIME(units) |
    |                |                     |---------------->|
    |                |                     |<----------------|
    |                |<--------------------| 编码结果        |
    |<---------------| 解码并返回时间      |                 |
```

应用调用的是**本地 client stub**；真正的业务过程在服务端执行。所谓「像本地调用」，主要是接口形式和代码组织相似。

## 3. RPC 消息与 xid：如何把响应交给正确调用？

对应讲义页 16–19，PDF 第 27–42 页。

### 3.1 请求和响应包含什么？

课件展示的是 Sun / ONC RPC 风格的消息布局，不是所有 RPC 框架都具有完全相同的字段。

| 请求字段 | 含义 |
| --- | --- |
| `xid` | 本次调用的标识，用于匹配响应 |
| `call/reply` | 区分请求与响应 |
| RPC version | RPC 协议版本 |
| program number、program version | 目标服务及其版本 |
| procedure number | 目标过程 |
| authentication 信息 | 身份认证相关数据 |
| arguments | 编码后的参数 |

响应携带相同 `xid`，以及接受状态、认证信息、执行状态和结果。例如，RPC 版本错误、认证失败、过程不存在，都可能产生错误响应。

**区分三件事：消息被收到、RPC 被接受、业务操作成功，含义并不相同。**

### 3.2 为什么不能按请求顺序取响应？

客户端多个线程可能共享一条连接，服务端也可能并行执行请求：

```text
线程 1：Read(page.html)，xid = 1，执行较慢
线程 2：Read(logo.png)， xid = 2，执行较快

响应到达顺序：#2 logo.png → #1 page.html
```

如果谁先读到消息就拿走，线程 1 可能误拿 `logo.png`。框架需要根据 `xid` 找到对应的等待线程或 callback。

**补充理解：**TCP 保证连接内字节按发送顺序交付，不保证服务端按照请求到达顺序完成业务。因此使用 TCP 仍然需要调用与响应的关联机制。

`xid` 在本讲中有两个相关用途：

- **响应匹配：**响应属于哪次调用？
- **重复检测：**重发的是同一次逻辑调用，还是新的调用？

第二个用途还需要服务端记录和去重逻辑；消息中有一个 ID 本身并不提供去重保证。

## 4. 参数传递：为什么不能直接发送内存？

对应讲义页 20–25，PDF 第 44–49 页。

### 4.1 按值传递与按引用传递

按值传递可以把值编码后复制到消息中。普通内存指针则只在所属进程的地址空间中有意义：客户端的 `0x1234` 并不代表服务端同一对象。

对于包含指针的数据结构，课件给出的思路是：

```text
客户端对象
    → 不依赖本地指针的表示
    → 网络传输
    → 服务端重建对象及本地指针
```

**补充理解：**重建出来的是远端对象表示，不是自动共享原内存。若需要表达远程对象引用，应定义对象 ID / handle 及相应操作；若需要修改客户端对象，也必须约定如何传回修改结果。

### 4.2 机器之间的数据表示不同

以 `0x89ABCDEF` 为例，按地址递增排列：

| 字节序 | 内存字节 |
| --- | --- |
| Big endian，大端序 | `89 AB CD EF` |
| Little endian，小端序 | `EF CD AB 89` |

除此以外，还可能有整数宽度、浮点表示、字符编码、对齐和填充差异。课件举例：`中` 的 GBK 编码是 `D6 D0`，UTF-8 编码是 `E4 B8 AD`。

所以跨机器通信需要约定 **wire format（线上传输格式）**，不能把某种语言的结构体内存布局直接当成通用协议。

### 4.3 软件升级也会造成差异

```text
旧版本：Msg { id }
新版本：Msg { id, priority }
```

| 兼容方向 | 定义 | 课件示例 |
| --- | --- | --- |
| Backward compatibility，向后兼容 | 新代码能读取旧代码写的数据 | 新 reader 读到 `{id: 7}`，为缺失的 priority 使用约定值 |
| Forward compatibility，向前兼容 | 旧代码能读取新代码写的数据 | 旧 reader 读到 `{id: 7, priority: 1}`，忽略不认识的 priority |

记忆方法：**先看 reader 是新还是旧。** 缺失字段如何处理取决于 schema 与应用约定，不能假设所有新增字段都会自动取零。

### 4.4 编解码的三个目标

- **正确性：**能从字节还原出约定的数据含义。
- **兼容性 / 可演进性：**跨语言、跨机器、跨版本通信。
- **效率：**控制消息大小、编码和解码成本。

Encoding / decoding，也常称 serialization / deserialization；在 RPC 中常用 marshal / unmarshal（编组 / 解组）。

语言自带的对象序列化机制可能绑定语言或对象实现。课件以 Java 序列化和 Python pickle 为例提醒这一问题；不能把「有序列化功能」直接等同于「已有跨语言、跨版本协议」。

## 5. 文本格式、二进制格式与 schema

对应讲义页 26–28，PDF 第 50–54 页。

### 5.1 格式选择的权衡

| 方式 | 优点 | 需要考虑的问题 |
| --- | --- | --- |
| JSON、XML 等文本格式 | 可读、方便调试、跨语言工具多 | 数值类型与精度的约定、二进制数据表示、字段名和标记的空间开销 |
| Thrift、Protobuf 等二进制编码 | 字段编号和紧凑数值表示可以减少字节数 | 需要协议/schema 配合，直接阅读字节较困难 |

例如，JSON 中传任意二进制数据时，应用常需要约定 Base64 等表示方式。二进制格式通常能减少这类额外转换，但是否更快仍取决于具体编码和工作负载。

### 5.2 Schema 用编号描述字段

课件的 Thrift 示例：

```thrift
struct Person {
  1: required string userName,
  2: optional i64 favoriteNumber,
  3: optional list<string> interests
}
```

对应的对象：

```json
{"userName":"Martin","favoriteNumber":1337,"interests":["daydreaming","hacking"]}
```

schema 规定字段编号、类型和约束，线上数据便可发送编号 `1`，省去反复发送字符串 `userName`。

注意区分：

- **字段编号（field tag / field number）：**识别对象中的哪个字段。
- **调用编号（xid / call ID）：**识别哪次 RPC。

课件中的 Protobuf schema 使用 `required`，属于 proto2 风格示例；学习重点是字段编号与类型约定。

## 6. 编码实例：81 B → 59 B → 34 B

对应讲义页 27–30、52，PDF 第 53–68、116 页。

以下大小只计算示例 `Person` 的编码数据，不包含完整 RPC 消息头和网络协议开销。

### 6.1 Thrift BinaryProtocol：59 B

普通字段头由 `类型（1 B）+ 字段编号（2 B）` 构成；字符串和列表还需要长度或元素类型等信息。这里的整数使用固定宽度和大端序。

| 部分 | 大小计算 | 字节数 |
| --- | --- | --- |
| `userName = "Martin"` | 字段头 3 + 字符串长度 4 + 内容 6 | 13 |
| `favoriteNumber = 1337` | 字段头 3 + i64 值 8 | 11 |
| `interests` | 字段头 3 + 元素类型 1 + 元素数 4 + `(4+11)` + `(4+7)` | 34 |
| 结构结束标记 | STOP | 1 |
| **总计** | `13 + 11 + 34 + 1` | **59** |

去掉空白后的 JSON 是 81 B。主要节省来自不重复发送字段名，但固定宽度整数和长度字段仍有开销。

### 6.2 Thrift CompactProtocol：34 B

课件展示两种压缩思路：

1. **字段编号用差值表示，并与类型合并。** 本例编号依次为 1、2、3，相邻差值都是 1，字段头各占 1 B。
2. **整数采用变长表示。** 每个字节最高位表示是否还有后续字节，其余 7 位保存数据。

列表长度和字符串长度在这个例子中也能更紧凑地表示：

| 部分 | 大小计算 | 字节数 |
| --- | --- | --- |
| `userName` | 字段头 1 + 长度 1 + 内容 6 | 8 |
| `favoriteNumber` | 字段头 1 + 编码后的整数 2 | 3 |
| `interests` | 字段头 1 + 列表头 1 + `(1+11)` + `(1+7)` | 22 |
| 结构结束标记 | STOP | 1 |
| **总计** | `8 + 3 + 22 + 1` | **34** |

**补充推导：为什么课件把 1337 编成 `F2 14`？**

Thrift CompactProtocol 对 `i64` 先做 ZigZag，再做 varint：正数 1337 映射为 2674。按 7 位分组：

```text
2674 = 114 + 20 × 128
114 = 0x72，加上“还有后续字节”的高位 → 0xF2
20  = 0x14，最后一个字节的高位为 0   → 0x14
结果：F2 14
```

ZigZag 将 `0, -1, 1, -2, 2, ...` 映射到 `0, 1, 2, 3, 4, ...`，使绝对值小的负数也能紧凑编码。字段头只有在编号差值合适时才能缩成 1 B，并非所有字段头恒为 1 B。参见 [Apache Thrift Compact Protocol 规范](https://github.com/apache/thrift/blob/master/doc/specs/thrift-compact-protocol.md)。

### 6.3 Protobuf 的同一个数字为什么是 `B9 0A`？

课件末尾的例子是字段编号为 2 的 `int64 favorite_number = 1337`：

```text
10 | B9 0A
字段标记 | 数值
```

**补充推导：**Protobuf 的 `int64` 正数直接使用 varint，本例没有先做 ZigZag：

```text
1337 = 57 + 10 × 128
57 = 0x39，加续位 → 0xB9
10 = 0x0A        → 0x0A

字段标记 = (field_number << 3) | wire_type
         = (2 << 3) | 0 = 16 = 0x10
```

因此整个字段占 3 B，其中整数占 2 B。Protobuf 的 `sint64` 才采用 ZigZag；不要把所有 varint 编码都当成同一种有符号整数映射。参见 [Protobuf 编码文档](https://protobuf.dev/programming-guides/encoding/)。

## 7. Schema 演进、自动生成与性能

对应讲义页 31–36，PDF 第 69–77 页。

### 7.1 如何支持新旧版本共存？

课件以给 `Person` 增加字段 3 `interests` 为例：

- 新 reader 读取旧数据：仍识别字段 1、2；字段 3 保持未设置，或按约定使用默认值。
- 旧 reader 读取新数据：识别字段 1、2；利用类型和长度等编码信息跳过未知字段 3。

**补充理解：**编号、类型和字段含义需要保持兼容；「能解码」还不等于「业务含义兼容」。例如，把原先表示金额的字段改成数量，即使底层都是整数也会出错。新增字段若要求所有旧数据必须包含它，同样会破坏兼容。

### 7.2 自动生成 stub

```text
接口定义：过程、参数类型、返回类型
                  ↓ RPC compiler / stub generator
客户端 stub + 服务端 stub + 编解码代码
```

自动生成可以减少重复工作和手写错误，并使双方对参数类型、过程标识等约定保持一致。

### 7.3 RPC 与传输协议是不同层次

RPC 框架可以封装 TCP、UDP 等传输方式，也可以适配新的网络能力。具体支持什么取决于框架，不能据此推断每个框架都支持所有协议。

**补充理解：**即使用 TCP，服务端仍可能在执行请求后、返回响应前崩溃。可靠字节传输不等于业务操作具备持久化或恰好一次语义。

### 7.4 二进制编码一定使 RPC 更快吗？

课件提出：网络变快之后，减少消息字节数是否仍是主要收益？

**补充分析：**可用下面的简化模型理解一次调用的耗时：

$$
T_{\text{RPC}}\approx T_{\text{编解码}}+T_{\text{网络往返}}+
\frac{S_{\text{请求}}+S_{\text{响应}}}{B}+T_{\text{排队}}+T_{\text{服务执行}}
$$

其中 $B$ 是有效传输带宽，网络往返项不重复计算上式单列的传输时间。这只是分析模型，实际还可能有复制、连接建立、重试等成本。

减小消息能降低传输时间，但当网络很快、消息很小或编解码很贵时，CPU 成本、排队和服务执行可能更重要。应比较端到端延迟与吞吐量，不能只比较编码后的字节数。

## 8. 部分故障：超时究竟说明什么？

对应讲义页 37–39，PDF 第 79–88 页。

分布式系统可能发生 **partial failure（部分故障）**：客户端仍在运行，但网络或服务端出了问题。

课件列出六种「客户端没有收到回复」的情况：

| 可能原因 | 服务端执行情况 |
| --- | --- |
| 请求丢失 | 这份请求没有到达服务端 |
| 请求延迟、仍在排队 | 可能稍后到达并执行 |
| 服务端崩溃 | 取决于崩溃时点，可能尚未执行或已经执行 |
| 服务端暂时暂停，例如长时间 GC | 可能恢复后继续执行 |
| 已执行，但响应丢失 | 操作已经产生效果 |
| 已执行，但响应延迟 | 操作已经产生效果，回复可能稍后到达 |

**超时只表示在约定时间内没有拿到结果，不能证明请求没有执行。**

这也是 RPC 的透明性被打破的地方。应用需要处理错误状态，并考虑结果未知的情况。课件中的 gRPC 调用通过检查 `Status` 决定使用结果还是处理错误。

**补充理解：**超时也不自动撤销远端已经发生的效果。即使客户端放弃等待，服务端可能继续执行。

## 9. 三种调用语义：至少一次、至多一次、恰好一次

对应讲义页 39–43、46–49，PDF 第 88–97、109–112 页。

### 9.1 先明确讨论单位

这里讨论的是**一次逻辑调用**。为完成它而发送的原请求和重试请求，应被视为同一操作，而不是多个独立业务请求。

| 语义 | 执行或生效次数 | 主要机制与限制 |
| --- | --- | --- |
| At-least-once，至少一次 | 成功完成时可能为 1 次或多次 | 超时重试，可能重复执行 |
| At-most-once，至多一次 | 0 次或 1 次 | 识别重复请求，避免再次执行；失败时可能不知道是否执行 |
| Exactly-once，恰好一次 | 在约定条件下最终生效 1 次 | 需要重试、持久去重和正确恢复共同配合 |

**补充理解：**至少一次的最终执行保证依赖故障最终恢复、重试持续进行等条件。若只尝试三次就停止，或者服务永久不可用，操作仍可能执行零次。

### 9.2 简单重试为什么可能重复执行？

```text
客户端                         服务端
  |---- Transfer(+100) --------->| 余额 0 → 100
  |           响应丢失 <--------|
  |                             |
  |---- 超时，重发同一操作 ------>| 余额 100 → 200
  |<---------------------- OK ---|
```

客户端只想执行一次，服务端却执行了两次。收到 `OK` 并不能在简单重试方案中证明「总共只执行了一次」。

### 9.3 Birrell 的至多一次语义

课件总结 Birrell RPC 的约定：

- 返回 `OK`：执行了一次。
- 报告 `CRASH`：可能执行零次，也可能执行一次，调用者无法仅凭该状态确定。

机制是为调用分配 call ID，重发沿用原 ID，服务端记住调用状态：

| 情况 | 处理方式 |
| --- | --- |
| 请求丢失 | 客户端重发，服务端首次收到后执行 |
| 同一调用重复到达 | 识别重复，不再次执行 |
| 原调用完成、回复丢失 | 返回保存的回复 |
| 服务端崩溃、无法确定结果 | 向应用报告不确定性，由应用进一步处理 |

其价值是把不确定性限制在故障情况：正常收到 `OK` 时不会因为重试多转一笔钱。

**补充理解：**`CRASH` 是课件使用的故障结果标签，不表示崩溃的服务端还能主动发消息，也不表示普通超时能准确区分崩溃与暂时变慢。

课件用「记住每个客户端的最后一个 call ID」描述基本思路。若允许同一客户端并发存在多个未完成调用，就需要按相应调用上下文维护状态，不能机械地只留一个编号。

## 10. 幂等性：哪些操作适合重试？

对应讲义页 43–46、48，PDF 第 97–109、111 页。

### 10.1 幂等关注重复后的效果

对同一状态变换 $f$，幂等可写为：

$$
f(f(s))=f(s)
$$

即在约定条件下，重复执行与执行一次产生相同效果。

| 操作 | 重复效果 | 判断 |
| --- | --- | --- |
| `i = 1` | 再执行仍然为 1 | 幂等 |
| `i++` | 每次都增加 | 非幂等 |
| `Deposit(+100)` | 每次多加 100 | 非幂等 |
| `ReadTime()` | 不修改本例的业务状态，但时间值可能不同 | 本例中可以安全重试的只读操作 |
| `Like()` 实现为 `counter++` | 重发也增加计数 | 非幂等 |

**概念澄清：**课件用「有副作用」解释非幂等操作，但有副作用不必然非幂等，例如 `i = 1` 会写状态却仍幂等。反过来，可以安全重试的读取也不意味着每次返回值完全相同。

### 10.2 ReadTime 与 Like 的区别

两个客户端各调用一次：

- `ReadTime()`：其中一次回复丢失后重试，服务端读了三次时间；如果应用接受重试时获取的新时间，仍满足需要。
- `Like()`：其中一次回复丢失后重试，计数从预期的 2 变成 3，业务结果错误。

### 10.3 用业务请求 ID 去重

课件展示的改进思路是为 `Like` 传入 xid，见过的请求不再增加计数：

```text
Like(request_id):
    若此 request_id 已完成：
        返回之前的结果
    否则：
        counter += 1
        记录 request_id 和结果
        返回结果
```

这段代码只表达逻辑，尚未解决并发和崩溃恢复。

**补充理解：**请求身份必须在约定范围内唯一。课件中的 `C0:#1` 和 `C1:#1` 是不同客户端的不同请求，不能只按数字 `1` 把两者合并。同一逻辑操作重试应复用身份；新的独立操作应使用新的身份。

## 11. 恰好一次为什么困难？

对应讲义页 47–49，PDF 第 110–112 页。

课件给出两个要求和一个关键假设：

1. 服务端记住已见请求与已执行请求的回复，**重启后仍能恢复这些信息**。
2. 请求有唯一 ID，以识别重复调用。
3. 假设故障最终修复，客户端持续重试。

### 11.1 只持久保存一个 seen 集合还不够

**补充推导：**假设 `counter` 和去重记录都需要持久保存：

| 更新顺序 | 中间崩溃会怎样？ |
| --- | --- |
| 先保存 `counter++`，再记录 request ID | 增量已生效但 ID 未保存；重试可能再次加一 |
| 先记录 request ID，再保存 `counter++` | ID 已保存但增量未生效；重试被跳过，操作丢失 |

因此，**业务状态变更与去重结果记录需要作为一个可原子提交、可恢复的整体处理。** 两个重复请求同时到达时，也要防止它们都通过「尚未见过」的检查。

一个理想化的事务结构是：

```text
在支持相应隔离与持久性的事务内：
    查询 request_id 是否已有结果
    若已有：读取保存的结果
    否则：
        执行业务状态变更
        保存 request_id 与返回结果
提交后回复
```

若业务效果发生在事务范围以外，例如另一个独立服务，还需要额外协调；仅把本地 `seen` 写入数据库并不能覆盖外部效果。

### 11.2 执行一次与生效一次

实际系统通常更关心「一次逻辑请求只提交一次业务效果」。重试、解析、查询去重记录等代码可以运行多次；不能把恰好一次解释成整个处理函数的每条指令只运行一次。

如果故障永久不恢复，就无法保证最终成功完成。本讲把完整恢复机制留给后续课程。

## 12. 实现案例：reply cache 与 gRPC retry

对应讲义页 51–53，PDF 第 115–117 页。Protobuf 编码例子见第 6 节。

### 12.1 Sun RPC：回复缓存有保护范围

课件的简化逻辑：

```text
若 reply_cache 命中请求身份：
    重发缓存回复
    返回，不再调用 handler
否则：
    执行 handler
```

只要相应回复仍在缓存中，重复请求就可以直接得到旧回复，避免再次执行 `counter++`。

课件特别注明：

- 缓存需要启用。
- 实际缓存键包含调用者和方法身份等信息，不只是裸 xid。
- 缓存淘汰或重启丢失记录后，重试可能再次执行。

所以应说明去重覆盖的时间与故障范围，不能把有限回复缓存当成跨重启的永久保证。ONC RPC 协议也不会单凭消息格式就赋予所有实现同一种执行语义。参见 [RFC 5531 第 5 节](https://www.rfc-editor.org/rfc/rfc5531#section-5)。

### 12.2 gRPC：重试策略解决再次尝试的问题

课件为 `ReadTime` 展示的 service config 片段：

```json
{
  "retryPolicy": {
    "maxAttempts": 3,
    "initialBackoff": "0.1s",
    "maxBackoff": "1s",
    "backoffMultiplier": 2,
    "retryableStatusCodes": ["UNAVAILABLE"]
  }
}
```

- `maxAttempts = 3` 包含首次尝试，即最多两次策略重试。
- 初始退避基准为 0.1 秒，之后按倍数增长，上限 1 秒。
- 配置指定哪些状态可以触发重试。
- 仍受调用 deadline 等条件限制。

**补充理解：**gRPC 的实际退避包含随机抖动；收到响应头后，调用被视为 committed，不再进行这类自动重试。这里的 committed 是重试机制的状态，不等于业务数据库事务提交。参见 [gRPC Retry 文档](https://grpc.io/docs/guides/retry/)。

重试给暂时失败的调用另一次机会，但不会自动使 `Like()` 幂等，也不会自动添加持久业务去重。

## 13. 把整个 RPC 系统串起来

对应讲义页 50，PDF 第 113–114 页。

| 组件 | 回答的问题 |
| --- | --- |
| Wire format 标准 | 消息和数据类型如何表示成字节？ |
| 编解码库 | 如何在本地对象和字节之间转换？ |
| Stub generator / RPC compiler | 如何从接口定义生成调用与分派代码？ |
| Server framework | 如何分派请求，并按语义要求记录调用状态？ |
| Client framework | 如何匹配回复、唤醒等待者、处理超时与重试？ |
| Binding / 服务定位机制 | 客户端如何找到正确的服务端？ |

从文件系统的 `Read()` 回看整条链路：

```text
找到文件服务
  → 调用本地 Read stub
  → 编码请求身份、过程与参数
  → 网络发送
  → 服务端解码、检查调用状态、分派
  → 执行真实 Read
  → 编码并返回结果
  → 客户端按调用身份匹配响应
  → 返回数据，或向应用报告错误 / 结果未知
```

## 14. 复习自测

1. **RPC 隐藏了什么，什么无法完全隐藏？**  
   隐藏消息构造、参数转换和网络收发等细节；远程延迟、部分故障以及结果不确定性仍需处理。

2. **为什么用 TCP 仍需要 xid 或类似机制？**  
   并行服务的响应可能按不同于请求的顺序发送，需要把每个响应交给正确调用。

3. **为什么不能把指针直接传给远端？**  
   普通指针属于本地地址空间。需要传对象内容或定义远程对象标识。

4. **向后兼容和向前兼容如何区分？**  
   新 reader 读旧数据是向后兼容；旧 reader 读新数据是向前兼容。

5. **Schema 如何同时改善大小与兼容性？**  
   用编号代替字段名；配合类型和长度信息识别已知字段、跳过未知字段，并约定缺失字段的处理方式。

6. **本例 JSON、Thrift Binary、Thrift Compact 分别多大？**  
   81 B、59 B、34 B；均未计入完整 RPC 和网络消息头。

7. **同样的 1337，为什么出现 `F2 14` 和 `B9 0A`？**  
   前者是 Thrift Compact 的 ZigZag 加 varint；后者是 Protobuf `int64` 的直接 varint。

8. **超时后能否断定操作没有执行？**  
   不能。请求可能未到达，也可能已经完成但回复丢失。

9. **至多一次是否保证一定成功？**  
   否，它允许零次；故障时调用者还可能不知道操作是否发生。

10. **幂等是否等于没有副作用或每次返回相同值？**  
    都不等同。`i = 1` 有写入效果但幂等；可安全重试的 `ReadTime()` 可能返回不同时间。

11. **为什么只在内存中记住 xid 不够？**  
    重启后记录丢失，重试可能再次执行。即使持久保存，还要解决去重记录与业务更新的原子性。

12. **为什么自动重试不等于恰好一次？**  
    重试解决再次尝试，恰好一次还要求稳定的请求身份、去重、持久恢复和业务效果协调。

**整讲核心：RPC 简化远程调用的写法；编码协议决定双方能否理解数据，失败语义决定重试之后业务结果是否仍然正确。**
