## 1. 本讲主线

对应课件第 1–14 页。

**文件系统通过逐层映射，把用户使用的路径名转换为磁盘上的数据块。**

大型网站依赖分布式文件系统、数据库和缓存，而这些服务又建立在单节点组件之上。本讲先理解单机文件系统，重点是命名、数据组织和元数据管理。

```text
用户提供路径 /programs/pong.c
        ↓ 选择根目录，逐级查找目录项
文件的 inode number
        ↓ 查询 inode table
inode：文件大小、类型、数据块索引等
        ↓ 将文件内偏移转换为磁盘块号
磁盘数据块
        ↓ 找到块内位置
需要读取的字节
```

贯穿本讲的区别：

| 概念 | 表示什么 | 例子 |
| --- | --- | --- |
| 文件名 | 某个目录中的名字 | `pong.c` |
| 路径名 | 从某个起点寻找文件的路线 | `/programs/pong.c` |
| inode number | 文件系统内部标识 inode 的编号 | `9` |
| 文件内块索引 | 该文件的第几个逻辑块，从 0 开始 | `0, 1, 2` |
| 磁盘块号 | 数据块在设备上的位置编号 | `61, 44, 15` |

**文件名保存在目录项中，不是 inode 的组成部分。**

## 2. 文件抽象与磁盘抽象

对应课件第 6–12 页。

### 2.1 文件提供什么？

文件是具有名字、能够持久保存的数据对象，可以把普通文件看作一个长度可变的线性字节数组。

应用希望使用如下抽象接口：

```text
READ(name, offset, size) -> bytes
WRITE(name, offset, size, bytes)
```

文件可以大于一个磁盘块，也可以随写入增长。文件系统负责把这些请求转换成设备操作。

**补充理解：**这里是概念接口。实际 UNIX 程序通常先 `open()` 获得文件描述符，再通过文件描述符执行读写；文件具有持久存储能力，也不代表每次 `write()` 返回后数据都已完成持久化。

### 2.2 磁盘提供什么？

课件把磁盘驱动接口简化为：

```text
Read(block_idx) -> Sector
Write(block_idx, data: Sector)
```

硬件按扇区（sector）组织和访问数据，例如 512 B 或 4 KiB。文件系统则需要支持任意位置、不同长度的文件访问，两者存在抽象上的差距。

```text
应用程序：open / read / write
              ↓
内核文件系统：名字解析、偏移映射、空间管理
              ↓
磁盘驱动：设备读写请求
              ↓
磁盘：扇区
```

### 2.3 朴素方案为什么不够？

设每个文件占据一段连续扇区，用起始扇区号作为名字。

| 问题 | 原因或后果 |
| --- | --- |
| 空闲空间难找 | 缺少专门记录空闲状态的元数据 |
| 文件增长代价大 | 后方空间被占用时，可能需要搬迁整个文件 |
| 名字不友好 | 用户需要记住扇区编号，且搬迁会影响地址 |
| 权限难管理 | 缺少统一保存所有者、权限等信息的位置 |

因此需要独立的空间分配、文件索引和命名机制。

### 2.4 UNIX 文件系统接口概览

| 功能 | 课件列举的接口 |
| --- | --- |
| 内容访问与位置管理 | `OPEN, READ, WRITE, APPEND, SEEK, CLOSE` |
| 持久化同步 | `FSYNC` |
| 元数据与权限 | `STAT, CHMOD, CHOWN` |
| 命名与链接 | `RENAME, LINK, UNLINK, SYMLINK` |
| 目录与路径上下文 | `MKDIR, CHDIR, CHROOT` |
| 文件系统接入 | `MOUNT, UNMOUNT` |

这是一份功能清单，并不表示每项在实际 UNIX 中都对应同名的独立系统调用。

## 3. 七层结构总览

对应课件第 13–14 页。

| 层 | 名称 | 核心映射或作用 |
| --- | --- | --- |
| L1 | Block Layer，块层 | 磁盘块号 → 块数据 |
| L2 | File Layer，文件层 | inode + 文件内块索引 → 磁盘块号 |
| L3 | inode Number Layer，inode 编号层 | inode number → inode |
| L4 | File Name Layer，文件名层 | 目录 + 文件名 → inode number |
| L5 | Path Name Layer，路径名层 | 起始目录 + 多级路径 → inode number |
| L6 | Absolute Path Name Layer，绝对路径层 | 用根目录 `/` 提供统一的命名起点 |
| L7 | Symbolic Link Layer，符号链接层 | 将链接中保存的路径作为新的解析目标 |

底层使用适合机器处理的数字标识，上层使用适合用户理解的名字。每层都隐藏下一层的一部分细节。

## 4. L1：块与空闲空间管理

对应课件第 15–19 页。

### 4.1 Block 与 Sector

**块（block）是文件系统管理数据的基本单位；扇区是设备层的单位。** 在课件模型中，块大小不小于扇区大小，一个块可以覆盖多个连续扇区。

课件例子：若扇区为 1 KiB，文件系统块为 4 KiB，则每个块覆盖 4 个扇区。针对同样的数据量，需要记录的分配单位数量约缩小到原来的四分之一。

块大小存在权衡：

- 块较大：需要管理的块数更少，块索引等元数据可能更少，但小文件的内部碎片可能更多。
- 块较小：空间使用更精细，但需要管理更多分配单位。

**补充理解：**若块大小为 4 KiB，采用整块分配且没有内联存储等优化，一个 1 KiB 文件仍占用一个数据块，剩余 3 KiB 属于内部碎片。

### 4.2 Superblock：描述整个文件系统

内核挂载文件系统时读取 superblock（超级块），取得解释磁盘布局所需的信息。课件列出：

- 块大小。
- 空闲块数量与空闲块列表。
- inode 等其他文件系统元数据。

课件采用一个逻辑 superblock 的模型；具体实现可能保留备份，并把实际的空闲空间记录放在其他元数据块中。

### 4.3 Bitmap：记录哪些块空闲

位图为每个块保存一位状态，以区分已占用和空闲；`0`、`1` 的具体约定由实现决定。

若总块数为 $N$，位图大小为：

$$
\left\lceil\frac{N}{8}\right\rceil\text{ bytes}
$$

**补充计算：**若容量为 4 TiB、块大小为 4 KiB：

$$
N=\frac{2^{42}}{2^{12}}=2^{30},\qquad
\text{bitmap size}=2^{27}\text{ B}=128\text{ MiB}
$$

课件第 7 页写作 `4TB = 2^30 × 4KB`，这里用 TiB、KiB 明确其二进制单位含义。

位图仍可能需要扫描，但扫描紧凑的元数据比读取所有数据块来推测空闲状态更合理。

## 5. L2：inode 如何组织文件数据

对应课件第 20–22 页。

### 5.1 inode 保存文件元数据

inode（index node，索引节点）记录文件的数据块位置与文件属性。最简单的模型是：

```c
struct inode {
    integer block_nums[N];
    integer size;
};
```

文件的逻辑顺序由索引决定，实际数据块可以分散在磁盘各处。例如：

```text
文件内块索引：  0    1    2
磁盘块号：     61   44   15
```

这样扩展文件时可以分配新的空闲块，再修改索引，无需保证整个文件物理连续。

### 5.2 文件偏移如何转换为磁盘位置？

设字节偏移为 $x$，块大小为 $B$：

$$
q=\left\lfloor\frac{x}{B}\right\rfloor,\qquad r=x\bmod B
$$

- $q$：文件内块索引。
- $r$：块内字节偏移。
- 通过 inode 将 $q$ 映射为磁盘块号，再访问该块的第 $r$ 个字节。

**补充例子：**块大小为 4096 B，读取偏移 5000：

```text
文件内块索引 = 1
块内偏移     = 904
若 block_nums[1] = 44，则访问磁盘块 44 的偏移 904
```

若读取区间跨越块边界，需要分别查找并读取相关块。课件伪代码只展示块定位，省略了块内偏移、越界检查等细节。

### 5.3 大文件：多级间接索引

inode 本身需要占用存储空间，无法用一个固定大小的 inode 直接列出任意多的数据块。因此课件引入：

```text
直接指针：inode → 数据块
一级间接：inode → 间接索引块 → 数据块
二级间接：inode → 二级索引块 → 一级索引块 → 数据块
三级间接：inode → 三级索引块 → 二级索引块 → 一级索引块 → 数据块
```

间接索引块保存的是块号，也会占用磁盘空间。更多层级可以寻址更大的文件，但在索引未缓存时也会增加查找 I/O。

**补充推导：**设块大小为 $B$ 字节，块指针为 $P$ 字节，一个间接索引块可存放 $K=\lfloor B/P\rfloor$ 个指针。若 inode 有 $D$ 个直接指针，以及一级、二级、三级间接指针各一个，则理论上可寻址的数据容量为：

$$
S_{\max}=B(D+K+K^2+K^3)
$$

该式只计算数据容量，不计索引块开销，也未考虑文件大小字段等其他限制。课件没有指定 $D$、$P$，不能据此直接给出本课模型的固定最大文件大小。

## 6. L3：inode number 与 inode table

对应课件第 23–24 页。

inode 还需要一个稳定、简短的标识，即 inode number。在课件的简化布局中：

```text
inode number → inode_table[number] → inode
```

inode table 位于磁盘上的已知位置；系统还要记录哪些 inode 已使用，课件举例使用空闲链表或 inode 内字段。

到这里，已经可以完成：

```text
(inode number, 文件内偏移)
    → inode
    → 文件内块索引
    → 磁盘块号
    → 数据块
```

inode number 足以供系统定位文件，但不适合用户记忆，因此还需要文件名层。

**补充理解：**inode number 的作用域是所属文件系统，不能把不同文件系统上的同号 inode 当成同一个文件。

## 7. L4 与 L5：目录、文件名和多级路径

对应课件第 25–28 页。

### 7.1 目录也是一种文件

目录保存「文件名 → inode number」的映射。课件示例：

| 文件名 | inode number |
| --- | --- |
| `helloworld.txt` | 12 |
| `cse2021.md` | 73 |

目录具有自己的 inode，其类型字段表明这是一个目录；目录的数据块存放目录项。

```c
struct inode {
    integer block_nums[N];
    integer size;
    integer type;
};
```

需要区分：**目录的 inode 描述目录自身；目录的数据块记录其子项的名字及 inode 编号。** 文件内容仍通过各个子项对应的 inode 查找。

### 7.2 单个名字的解析需要上下文

`notes.md` 这个名字只有结合所在目录才有意义。默认上下文通常是当前工作目录（cwd）。

统一写成如下概念接口：

```text
LOOKUP(directory_inode_number, filename) -> inode_number
```

课件的简单查找过程：读取目录 inode，检查类型，遍历目录的数据块，比较目录项中的名字，找到后返回 inode number。

顺序扫描的代价会随目录项数量增加。课件随后通过多级目录组织名字；分层有助于管理名字，但不会自动让每个目录内部的线性查找变成常数时间。

**课件文字校正：**第 26–27 页写 `LOOKUP("cse2021", dir)` 返回 73，但表中的名字是 `cse2021.md`。按精确字符串匹配，应查找 `cse2021.md`。

课件还指出 UNIX V6 的文件名上限为 14 字节。字节数不等于任意编码下的字符数，这也不是所有现代文件系统的通用限制。

### 7.3 多级路径是反复执行 LOOKUP

解析相对路径 `projects/paper`：

1. 从当前目录查找 `projects`，得到其 inode number。
2. 确认它可作为目录继续遍历。
3. 以该目录为新上下文，查找 `paper`。

```text
起始目录 → LOOKUP("projects") → 新目录 → LOOKUP("paper") → 目标 inode
```

中间任何名字不存在，或中间分量不是目录，都无法按这条路径继续查找。

## 8. 硬链接、引用计数与目录环

对应课件第 29–32 页。

### 8.1 硬链接增加一个名字绑定

课件例子：

```text
LINK("Mail/inbox/new-assignment", "assignment")
```

执行后，两个目录项保存同一个 inode number：

```text
Mail/inbox/new-assignment ─┐
                          ├→ 同一个 inode → 同一份文件数据
assignment ───────────────┘
```

硬链接不复制文件内容，也没有「原始名字更重要」的区别。两个名字地位相同，通过任何一个名字访问的都是同一个文件对象。

### 8.2 UNLINK 删除的是名字绑定

课件使用引用计数记录指向 inode 的名字绑定数量：

- `LINK` 增加绑定，计数加一。
- `UNLINK` 删除绑定，计数减一。
- 在课件简化模型中，计数为零时回收 inode 和数据块。

**补充理解：**实际 UNIX 中还要考虑打开文件的引用。删除最后一个名字后，已经打开该文件的进程仍可继续访问；不能把硬链接计数为零直接等同于数据立即被回收。

### 8.3 为什么禁止用户随意给目录建立硬链接？

若允许一个目录内部的路径再指回祖先目录，就可能形成环。删除外部入口后：

```text
根目录   （已无法到达这组目录）

目录 A → 目录 B
  ↑        ↓
  └────────┘
```

环内对象彼此引用，计数仍大于零，却已无法从根目录到达，单纯引用计数无法回收它们。

课件用「禁止普通用户创建目录硬链接」避免这类问题；`.` 和 `..` 是系统管理的特殊关系。

删除目录通常要求它先为空，也能避免直接移除目录入口后遗留仍有内容的子树。`.`、`..` 的维护由目录操作专门处理。

## 9. 重命名与崩溃一致性

对应课件第 33–34 页。

### 9.1 先删除目标名字的风险

课件用编辑器先写临时文件、再替换目标文件的场景说明问题。若把重命名简单实现为：

```text
1. UNLINK(to_name)
2. LINK(from_name, to_name)
3. UNLINK(from_name)
```

在步骤 1 和 2 之间崩溃，原有目标名字已经消失，新绑定还未建立，用户无法通过 `to_name` 找到文件。

### 9.2 先更新目标绑定可以提供较弱保证

课件讨论另一个顺序：

1. 把 `to_name` 的目录项改为指向 `from_name` 的 inode。
2. 删除 `from_name` 的目录项。

若在两步之间失败，可能留下两个名字指向同一个 inode，恢复时还需修正引用计数。相较于先删目标，这个顺序旨在避免中间阶段目标名字完全消失。

**理解边界：**课件第 34 页的 `LINK` 是教学示意，不能直接当成可覆盖现有目标的普通 `link()` 调用。该两步方案也没有独立解决所有元数据更新、写入顺序与持久化问题。

本节引出的核心问题是：**一个名字操作会修改多个相关状态，崩溃时如何保证它们仍然一致？** 完整原子性与恢复机制留待后续课程展开。

## 10. L6：绝对路径与完整查找示例

对应课件第 35–45 页。

### 10.1 根目录提供统一起点

相对路径从当前工作目录开始，绝对路径从根目录 `/` 开始。用户的 HOME 通常是登录后的初始工作目录，但不是绝对路径解析的根。

```text
/programs/pong.c  → 从 / 开始
programs/pong.c   → 从 cwd 开始
```

课件模型中根 inode number 为 `1`，`/.` 与 `/..` 都指向根。编号 `1` 是本例设定，不是所有文件系统的固定根 inode 编号。

### 10.2 查找 /programs/pong.c

课件图中给出的映射如下：

| 对象 | inode number | inode 中记录的数据块号 |
| --- | --- | --- |
| 根目录 `/` | 1 | 14、37、16 |
| 目录 `/programs` | 7 | 23、28、55、51 |
| 文件 `/programs/pong.c` | 9 | 61、44、15 |

本例的目标目录项分别位于根目录的块 14 和 `programs` 的块 23：

1. 已知根 inode 为 1，在 inode table 中找到它。
2. 根据根 inode 的索引读取目录块 14。
3. 找到目录项 `programs → 7`。
4. 读取 inode 7，再读取它的目录块 23。
5. 找到目录项 `pong.c → 9`。
6. 读取 inode 9，得到文件的数据块号 `61、44、15`。
7. 根据需要访问这些块，拼成文件的逻辑字节序列。

```text
/ [inode 1]
  → 目录块 14：programs → inode 7
      → 目录块 23：pong.c → inode 9
          → 文件数据块 61、44、15
```

**补充理解：**这里展示的是逻辑依赖链，不能直接据此断言实际需要固定次数的磁盘 I/O。inode 可能位于同一块，目录或数据可能已被缓存，还可能涉及间接索引块。

## 11. 从十六进制数据理解目录项

对应课件第 46–47 页。

课件通过 `ls -ai` 查看 inode 编号，再用 `debugfs` 导出目录数据、用 `xxd` 展示字节内容，说明目录确实保存着可解释的数据结构。

其中 `.` 对应的 12 字节为：

```text
0d 01 73 00 | 0c 00 | 01 | 02 | 2e 00 00 00
inode      | 长度  |名长|类型| 名字及填充
```

按小端序解读：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| inode | `0x0073010d = 7536909` | 当前目录的 inode number |
| 目录项长度 | `0x000c = 12` | 本条记录占 12 字节 |
| 文件名长度 | `1` | 有效名字为 1 字节 |
| 文件类型 | `0x02` | 目录 |
| 文件名 | `0x2e` | ASCII 字符 `.` |

**课件校正：**第 47 页把这一条记录的类型解说写成 `01 / regular file`，但实际字节为 `02`，对应目录。带独立类型字段的布局对应 ext4 的 `ext4_dir_entry_2`；目录项长度包含头部、名字和填充，不能等同于文件名长度。参见 [Linux 内核 ext4 目录项文档](https://www.kernel.org/doc/html/v6.17/filesystems/ext4/directory.html)。

本节的重点是理解目录项编码，课件中的 `/dev/sda1` 等设备路径只适用于其演示环境。

## 12. L7：符号链接

对应课件第 48–50 页。

### 12.1 符号链接保存目标路径

硬链接通过 inode number 绑定同一个文件。不同文件系统有各自的 inode 编号空间，因此课件引入按路径间接引用目标的符号链接（soft link / symbolic link）。

```text
硬链接：目录项 → 目标文件 inode
软链接：目录项 → 链接自身的 inode → 保存的路径 → 解析目标
```

符号链接有自己的 inode 类型，可以指向当前命名空间中的其他文件系统内的路径。

**补充理解：**挂载负责把其他文件系统接入目录命名空间；符号链接负责引用路径。创建符号链接本身不会完成磁盘挂载。

### 12.2 课件示例：悬空链接

```sh
ln -s "/tmp/abc" s-link
readlink s-link
# /tmp/abc
```

即使 `/tmp/abc` 不存在，链接仍可创建，但读取目标会失败。目标文件随后出现时，同一个链接就可以访问它。

课件显示链接大小为 `8`，因为 `/tmp/abc` 这个路径字符串占 8 字节；它不是目标文件内容的大小。

### 12.3 硬链接与符号链接对照

| 项目 | 硬链接 | 符号链接 |
| --- | --- | --- |
| 引用方式 | 指向同一个 inode | 保存目标路径 |
| 是否有独立 inode | 新名字与已有名字共用 inode | 链接自身有 inode |
| 是否复制目标内容 | 否 | 否 |
| 跨文件系统 | 通常不支持 | 可以引用已接入命名空间的目标路径 |
| 指向目录 | 通常禁止用户创建 | 可以 |
| 目标暂时不存在 | 建立链接时需要已有目标 | 可形成悬空链接 |
| 删除目标的另一个名字 | 仍可通过此硬链接访问 | 若所保存路径失效，则无法访问目标 |
| 目标硬链接计数 | 增加 | 不因创建软链接而增加 |

**补充理解：**相对符号链接的目标路径以链接所在目录为解析基准。符号链接也可能形成循环，因此路径解析还需要限制链接跟随次数等机制。

## 13. Bash 中的逻辑路径与物理路径

对应课件第 51–52 页。

设存在：

```text
/CSE-web → /Scholarly/programs/www
```

Bash 默认的逻辑模式保留用户使用的路径。在该模式下：

```sh
cd /CSE-web
pwd -L
# /CSE-web
pwd -P
# /Scholarly/programs/www
cd ..
pwd -L
# /
```

若重新进入链接后按物理结构取父目录：

```sh
cd /CSE-web
cd -P ..
pwd -P
# /Scholarly/programs
```

**课件解释修正：**关键是 Bash 维护逻辑路径并按 `-L` / `-P` 选择解析方式。不能把 `cd ..` 解释为总是返回 `$OLDPWD`；返回上次工作目录的是 `cd -`。参见 [Bash 官方手册：cd](https://www.gnu.org/s/bash/manual/html_node/Bourne-Shell-Builtins.html)。

这个例子再次说明：名字的意义取决于解析它的上下文，shell 的逻辑路径处理与文件系统的实际目录结构可能不同。

## 14. 复习要点与自测

对应课件第 53 页及全讲总结。

### 14.1 必须掌握的结论

- **文件名不在 inode 中。** 名字属于目录项，是目录的数据，也是文件系统的元数据。
- **同一个 inode 可以拥有多个名字。** 硬链接之间地位相同。
- **目录保存映射。** 目录大小不等于子文件内容大小之和，但大量目录项仍会让目录自身变大。
- **文件内块索引与磁盘块号不同。** inode 负责两者之间的映射。
- **路径解析是带上下文的逐级查找。** 相对路径从 cwd 开始，绝对路径从根开始。
- **空间管理需要元数据。** 数据块和 inode 都要跟踪分配状态。
- **名字操作也涉及一致性。** 目录项、inode 引用计数与空间分配信息可能需要协调更新。

### 14.2 自测题

1. 为什么文件可以由不连续的磁盘块组成？  
   inode 保存逻辑块到磁盘块的映射，逻辑顺序无需等于物理顺序。

2. 给定块大小 4096 B，偏移 9000 位于哪里？  
   文件内块索引为 2，块内偏移为 808；实际磁盘块号还需查 inode。

3. 两个文件名的 inode number 相同，就一定是同一个文件吗？  
   还要确认它们属于同一个文件系统；不同文件系统的编号可以重复。

4. 删除一个硬链接为什么不一定删除文件数据？  
   可能仍有其他名字绑定该 inode；实际系统中还可能有打开文件的引用。

5. 为什么引用计数难以回收目录环？  
   环内引用使计数不归零，即使从根目录已无法到达这些对象。

6. 为什么软链接可以指向不存在的文件？  
   它保存路径字符串，目标是否存在是在后续解析时判断的。

7. 为什么先 `unlink(to_name)` 再创建新绑定有风险？  
   中途崩溃会留下目标名字不存在的状态。

8. 从 `/programs/pong.c` 找到数据必须经过哪些对象？  
   根 inode → 根目录项 → `programs` inode → `pong.c` 目录项 → 文件 inode → 数据块。
