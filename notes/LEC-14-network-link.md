## 1. 本讲主线：网络怎样把数据送到另一台机器？

对应课件页 2–4、13–14。

此前讨论 RPC、复制和分布式事务时，我们把网络看成能够发送消息的基础设施。本讲打开这个黑盒：**从一条链路上的比特传输出发，逐步构造帧、分组，以及跨多个中间节点的数据传递。**

```text
应用产生数据
    ↓ 应用协议定义内容和交互
端到端通信：把数据交给目标主机上的相应应用
    ↓ TCP / UDP 等传输层协议
跨网络传递：根据目的地址选择下一跳
    ↓ IP 与路由、转发
相邻节点通信：复用链路、划分帧、检测差错
    ↓ 链路协议与物理传输
电信号、光信号或无线信号
```

本讲最关键的区分：**链路层解决一跳，网络层组织多跳，传输层提供端到端服务。**

### 1.1 三种分层视角

| 视角               | 从高到低的层次                               | 本讲如何使用                            |
| ------------------ | -------------------------------------------- | --------------------------------------- |
| OSI 七层模型       | 应用、表示、会话、传输、网络、数据链路、物理 | 理解不同功能可以进一步拆分              |
| TCP/IP 四层模型    | 应用、传输、互联网、网络接口                 | 对应常见协议栈                          |
| 课件的三层网络抽象 | End-to-end、Network、Link                    | 应用位于其上；Link 同时讨论物理传输和帧 |

不同模型的层数不一样，不代表同一件事必须严格拆成同样数量的软件模块。课件页 2 单独列出应用；页 3 的示意图又把应用与传输放在较宽泛的端到端部分。阅读时应以**功能和作用范围**为准。

### 1.2 各层关心什么？

| 层次     | 主要问题                                   | 标识或分用依据                        | 课件中的例子          |
| -------- | ------------------------------------------ | ------------------------------------- | --------------------- |
| 应用层   | 数据表示什么，双方如何交互？               | URL 等应用命名，具体取决于协议        | HTTP、FTP、POP3、SMTP |
| 传输层   | 数据交给哪个应用，是否需要可靠、有序交付？ | 端口号；连接识别还结合 IP 等信息      | TCP、UDP              |
| 网络层   | 目的地在哪里，下一跳走哪条链路？           | IP 地址、IP 协议字段                  | IP、ICMP、路由器      |
| 链路层   | 怎样把帧送到相邻节点？                     | 链路协议字段；某些链路还使用 MAC 地址 | Ethernet、PPP         |
| 物理传输 | 怎样发送和识别比特？                       | 信号电平、编码、时钟                  | 导线、光纤、无线介质  |

**表述边界：**端口号不能单独标识整个互联网中的一个连接；URL 也不是所有应用协议共同的命名方式。课件页 9 将 bridge 列在网络实体中，但通常的二层 bridge 按链路层地址转发。ICMP 属于互联网层，不能因页 4 示意图把它画在 TCP、UDP 旁边，就当作传输层协议。

### 1.3 Internet 的沙漏结构

```text
        Web、Email、文件传输、语音等应用
                  TCP、UDP 等
                     IP
            Ethernet、PPP 等链路协议
               多种物理传输介质
```

IP 是中间较窄、统一的接口：上层应用不必为每种底层链路各写一套通信逻辑，新的链路技术也可以承载现有 IP 应用。这就是课件中 “Everything over IP, and IP over everything” 的含义。

统一接口促进互联，但接口越复杂，所有参与者共同实现和扩展它的成本也越高。课件借此讨论标准化与灵活性，以及把复杂功能放在端点还是网络内部的取舍。

课件的「个人价值约为 `N`、社会价值约为 `N²`」是网络效应的直观模型。**补充理解：**`N` 个节点的潜在无向连接对有 `N(N−1)/2` 个；这说明连接机会随规模快速增加，并不证明实际经济价值必然等于某个平方函数。

## 2. 封装、分用与跨路由器传输

对应课件页 5–12。

### 2.1 每层把上层数据当作自己的载荷

```text
应用：                       [Application data]
传输层：          [TCP/UDP H | Application data]
网络层：    [IP H | TCP/UDP H | Application data]
链路层：[Link H | IP H | TCP/UDP H | Application data | Link trailer]
```

发送端向下封装，接收端向上解析并移除相应头部／尾部。常见叫法如下：

| 层次 | 数据单元                        |
| ---- | ------------------------------- |
| 应用 | Message，消息                   |
| TCP  | Segment，报文段                 |
| UDP  | Datagram，数据报                |
| IP   | Packet / datagram，分组／数据报 |
| 链路 | Frame，帧                       |

课件有时宽泛地使用 packet。做题时应先说明讨论的是哪一层，避免把 IP 包、TCP 段和链路帧的长度混在一起。

### 2.2 协议头不只是增加开销，也提供分用依据

接收端逐层回答不同问题：

```text
链路协议字段 → 载荷交给 IP 还是其他协议？
IP Protocol 字段 → 载荷交给 TCP 还是 UDP？
TCP/UDP 端口 → 交给哪个应用端点？
应用协议 → 这条消息表示什么操作？
```

这就是 multiplexing / demultiplexing：多个上层使用同一个下层服务，下层必须保留足够的信息，在接收时把数据分回正确的上层。

### 2.3 TCP、UDP 和 IPv4 头部的阅读重点

| 协议 | 课件图中的关键字段                        | 用途                                     |
| ---- | ----------------------------------------- | ---------------------------------------- |
| TCP  | Source/Destination Port                   | 标识发送与接收应用端点                   |
| TCP  | Sequence/Acknowledgment Number            | 支持字节排序、确认与重传                 |
| TCP  | Data Offset、Flags、Window                | 确定头部长度、控制连接状态、通告接收窗口 |
| UDP  | Source/Destination Port、Length、Checksum | 提供端口分用、长度和差错检测信息         |
| IPv4 | Source/Destination Address                | 标识网络层源地址与目的地址               |
| IPv4 | TTL、Protocol                             | 限制包在网络中持续转发；标识上层协议     |
| IPv4 | IHL、Total Length                         | 确定头部与整个 IP 包的长度               |
| IPv4 | Identification、Flags、Fragment Offset    | 支持 IPv4 分片相关处理                   |
| IPv4 | Header Checksum                           | 检测 IPv4 头部差错                       |

TCP 无选项时的头部为 20 B，UDP 头部为 8 B，IPv4 无选项时的头部为 20 B。课件页 5 的两个 `20 Bytes` 不能推广到所有传输协议或所有带选项的报文。

**课件校正：**页 7 的 “UDP: nothing” 指 UDP 不提供 TCP 式的可靠交付与重传，不能理解为 UDP 没有头部或任何功能。UDP 仍然提供数据报接口和端口分用等机制。

**补充理解：** TCP 提供字节流；一次应用写入不一定对应一个 TCP 段或一个链路帧。分段与重组也有具体协议条件，不能把页 12 的 “may split up” 理解为每层必然切分数据。

### 2.4 中间路由器主要处理到网络层

```text
主机 A                    路由器                    主机 B
应用                                                 应用
TCP                                                  TCP
IP                         IP                         IP
链路 1  ←──────────────→  链路 1 / 链路 2  ←──────→  链路 2
```

普通 IP 转发时，路由器接收一跳的链路帧，取出 IP 包，按目的地址查表，再用下一条链路的格式重新封装。因此：

- 链路帧及其链路层头部通常逐跳变化。
- TCP 通信的端点仍是两端主机，普通转发不要求路由器执行应用逻辑。
- IP 头也不是逐字节不变，例如 TTL 会更新；这里暂不讨论 NAT、隧道等额外机制。

### 2.5 长度题先确定统计范围

**补充理解：**普通、无 VLAN 标签的 Ethernet II 可以按以下范围区分：

| 项目                           | 长度      |
| ------------------------------ | ---------:|
| MAC 头：目的地址、源地址、类型 | 14 B      |
| 数据字段，包含必要填充         | 46–1500 B |
| FCS                            | 4 B       |
| 从目的 MAC 地址到 FCS 的帧长   | 64–1518 B |

数据字段的长度和承载 IP 的方式可对照 [RFC 894](https://www.rfc-editor.org/rfc/rfc894.html)。前导码与帧起始定界符另占 8 B；若把它们与 14 B MAC 头合计，才会得到 22 B。**对课件页 5 的 `22 Bytes` 可以作这样的解释，但图中没有明确写出统计口径。**

页 5 的 `64 to 1500 Bytes` 不宜作为一个通用长度范围背诵：64 B 通常是上述完整帧的最小值，1500 B 通常是数据字段上限。两者统计的对象不同。

## 3. 链路层需要完成哪些工作？

对应课件页 13–14。

链路层负责从一个节点到物理相邻节点的传递。课件列出五项工作：

| 工作                           | 要解决的问题                           |
| ------------------------------ | -------------------------------------- |
| Physical transmission          | 怎样把比特变成信号，再恢复为比特？     |
| Multiplexing the link          | 多个通信流怎样共用一条链路？           |
| Framing bits and bit sequences | 何时采样一个比特，如何识别一帧的起止？ |
| Detecting transmission errors  | 怎样发现传输中的损坏？                 |
| Providing an interface         | 怎样向上层提供可使用的收发接口？       |

特别注意两个层次的边界识别：**bit framing 确定比特的采样时刻，frame framing 确定一段比特属于哪一帧。** 能正确采样比特，不代表已经知道消息在哪里结束。

## 4. 物理传输：共享时钟、握手与串行发送

对应课件页 15–18。

### 4.1 共享时钟：在下一个时钟边沿读取

同一芯片上的两个寄存器可以共用时钟：发送寄存器更新输出，信号沿导线传播，接收寄存器在下一时钟边沿读取。

前提是一个周期足以容纳输出稳定、信号传播以及接收采样所需的时间。距离变长、模块彼此独立时，就不能轻易假设所有设备拥有同一个可靠时钟。

### 4.2 无共享时钟：三线 ready/acknowledge 协议

```text
A ─────── data ───────→ B
A ─────── ready ──────→ B
A ←──── acknowledge ── B
```

一次传递的逻辑顺序：

1. A 将数据放在 data 线上，并使其稳定。
2. A 改变 ready 的值，通知 B 有新数据。
3. B 观察到 ready 变化，读取 data。
4. B 改变 acknowledge 的值，告诉 A 已读取。
5. A 观察到确认后，才可以为下一次传递改变数据。

`ready` 回答「B 什么时候读」，`acknowledge` 回答「A 什么时候可以不再保持旧值」。课件以信号变化描述握手，理解为双方约定的事件即可，不必假定每次都只是将某根线设置为 1。

### 4.3 每个比特都等确认，传播延迟会限制速率

设单向传播时间为 `Δt`。数据／通知前往 B、确认返回 A，至少消耗约 `2Δt`，还未计入电路处理和稳定时间。

$$
R_{\text{one wire}} \lesssim \frac{1}{2\Delta t}
$$

若有 `N` 根并行数据线，每轮发送 `N` 个比特，则理想上限为：

$$
R_{\text{parallel}} \lesssim \frac{N}{2\Delta t}
$$

**补充例题：**`Δt = 1 μs` 时，单数据线的理想上限约为 `0.5 Mb/s`；8 根数据线约为 `4 Mb/s`。这些是每轮等待往返确认的模型上限，不是所有串行或并行链路的通用公式。

### 4.4 串行发送：连续发送，不逐比特等待往返

发送端按一定速率连续送出比特流，接收端自行恢复比特与时钟。这样，多位数据可以同时处于传播途中，距离增加不再直接要求每个比特都等待一个 RTT。

课件以 USB、SATA 作为串行传输的例子。这里的关键优势来自连续传输与时钟恢复；**串行这一形式本身并不保证一定比所有并行方案快**，也不意味着完整协议永远不需要确认或流量控制。

## 5. 时钟恢复：PLL 与 Manchester 编码

对应课件页 19–21。

### 5.1 接收端为什么不能只看电压高低？

接收端没有发送端的时钟副本。实际信号经过线路后还会失真，所以必须同时知道：

- 电平代表 0 还是 1。
- 一个比特持续多久，应该在什么时刻采样。

例如，一段持续的低电平可能代表一个很长的 0，也可能代表连续多个 0；没有时间基准，无法区分。

### 5.2 VCO 与锁相环

VCO（Voltage-Controlled Oscillator，压控振荡器）的频率可由控制电压调整。课件用下面的反馈过程说明 PLL（Phase-Locked Loop，锁相环）：

```text
接收信号与本地振荡信号比较
    → 产生并滤波误差信号
    → 调整 VCO
    → 让本地时钟跟踪输入信号的频率和相位
```

锁定后，本地时钟成为接收端的采样基准。若比特流长时间没有电平跳变，接收端缺少持续校正的依据，时钟偏差会逐渐积累。

### 5.3 Manchester：在每个比特中间安排一次跳变

本讲采用：

```text
数据位 0 → 01
数据位 1 → 10

数据：     1  0  1  1  0
编码：    10 01 10 10 01
```

每个数据位被编码成两个半比特时隙，并且在中点发生跳变。因此连续的 0 或连续的 1 也能提供同步信息。

若线路每秒可承载 `S` 个这样的电平时隙，则数据率为：

$$
R_{\text{data}} = S/2
$$

课件的「最大数据率减半」应在相同可用电平时隙速率下理解。这里付出的冗余用于**同步**，不能据此认为 Manchester 自动具备 Hamming 码那样的单比特纠错能力。不同资料也可能采用相反的 0/1 跳变约定，做题以题目规定为准。

## 6. 共享链路：等时复用与分组复用

对应课件页 22–27。

### 6.1 电话网络：预先分配周期性时隙

Isochronous communication（等时通信）适合持续、规则的数据流。传统电话的课堂模型是：

1. 建立连接时，各交换机预先安排传输资源。
2. 每路通话定期获得固定时隙，形成一条逻辑上的 virtual link。
3. 通话结束后释放时隙。

时隙已满时，新呼叫可能得到「网络忙」。时分复用 TDM（Time-Division Multiplexing）共享的是一条物理链路上的时间。

### 6.2 例题：45 Mb/s 链路能承载多少路 64 kb/s 电话？

课件给出：每路电话每次发送 8 bit，每秒 8000 次。

$$
R_{\text{call}} = 8\times8000 = 64000\ \text{bit/s}
$$

每路样本的发送周期：

$$
T = 1/8000\ \text{s} = 125\ \mu s
$$

忽略额外协议开销，可承载的完整通话数：

$$
N = \left\lfloor\frac{45\times10^6}{64\times10^3}\right\rfloor = 703
$$

每个周期安排 703 个 8-bit 块，共占：

$$
703\times8 = 5624\ \text{bit times}
$$

**补充推导：**如果链路速率严格等于 `45,000,000 bit/s`，125 μs 内可传 5625 bit。课件的 5624 对应 703 路所占的位数，约占 124.978 μs；课件把它与 125 μs 并列，是忽略剩余容量与开销的近似。

第 704 路无法再分到一个完整固定时隙，在这个模型中只能拒绝或等待资源释放。

### 6.3 每隔 125 μs 才传一次，为什么声音仍然连续？

链路上交错传输的是数字样本。接收端按每秒 8000 个样本的节奏恢复播放，而不是「收到一小块才临时发出一小段声音」。只要样本按时到达，复用导致的发送间隔不会直接变成可听见的空白。

### 6.4 数据通信通常是突发的

网页请求、文件下载等流量可能一段时间很忙，随后长时间空闲。固定为每个流保留时隙，会让空闲流占着无法利用的容量。

异步分组传输允许帧在链路可用时发送，并在协议允许范围内采用不同长度：

```text
输入流 A ─┐
输入流 B ─┼→ 输出队列 → 共用链路 → 根据头部信息分用／转发
输入流 C ─┘
```

- **复用：**多个输入进入队列，输出链路依次发送，需要内存和缓冲。
- **分用：**读取分组头部中的目的地等信息，结合转发表决定去向。
- **代价：**等待时间变化；缓冲有限，突发过大时可能丢包。

| 比较项             | 固定时隙 TDM       | 异步分组复用           |
| ------------------ | ------------------ | ---------------------- |
| 资源安排           | 连接建立时预留     | 按实际到达的数据共享   |
| 空闲期间           | 预留容量可能闲置   | 容量可供其他流使用     |
| 高负载后果         | 新连接可能被拒绝   | 排队加长，缓冲满后丢包 |
| 接收时如何识别归属 | 约定的时隙位置     | 分组头部信息           |
| 适合说明的流量     | 持续、规则的语音流 | 突发数据流             |

**课件校正：**页 26 的 “Connectionless transmission: no state maintained” 应理解为不必预先建立并维护每条连接的专用电路状态。设备仍需要转发表、队列、接口状态等。异步分组传输也不排斥上层建立 TCP 连接。

课件还提到 segment and reassemble，以及 packet voice：较大的消息可以按协议切分、在接收侧重组；语音也可以使用分组传输，但需要处理时延变化。

## 7. 帧边界与位填充

对应课件页 28。

### 7.1 为什么要有帧分隔符？

即使已经恢复出 `010101…`，接收端仍需要知道哪里是一帧的开始和结束。一个简单办法是保留特定比特模式作为 frame separator。

课件的教学方案选用**连续七个 1**作为分隔符。问题在于：合法数据本身也可能出现连续七个 1，接收端会误把数据当边界。

### 7.2 Bit stuffing：让数据不产生保留模式

课件的规则是：发送端在帧内容中每遇到连续六个 1，就额外插入一个 0；接收端按对应规则去掉填充位。

```text
原始数据：1111111
发送内容：11111101
                ↑ 六个 1 后插入的 0

接收端去填充后：1111111
```

分隔符本身按协议直接发送，不按普通数据填充。位填充的意义是**让帧内容可以透明地承载任意数据，同时保留可识别的边界模式**。

**与后面的 PPP 区分：**这里是「七个 1 的分隔符、六个 1 后插 0」的教学规则。PPP 的实际 Flag 是 `01111110`，其位填充规则是连续五个 1 后插 0，见第 10 节。

## 8. 差错处理与 Hamming distance

对应课件页 29–31。

### 8.1 检测到损坏后，可以怎样处理？

| 方法                          | 核心机制                             | 成本或限制                               |
| ----------------------------- | ------------------------------------ | ---------------------------------------- |
| Error detection               | 加校验冗余，判断接收内容是否符合规则 | 只能在能力范围内检测，不能自动恢复原数据 |
| Forward error correction，FEC | 发送前编码，接收端根据冗余直接恢复   | 消耗额外带宽，纠错能力有限               |
| Retransmission                | 通过确认、超时等机制要求重新发送     | 发送端需保留数据，增加往返等待           |
| Discard                       | 丢弃损坏帧                           | 是否恢复交给上层或应用决定               |

这些方法可以组合，例如链路层检测并丢弃坏帧，端到端协议在之后重传。课件用磁盘等噪声特性较可控的场景说明纠错编码的价值。

### 8.2 Hamming distance：两个比特串有多少位不同？

对于等长比特串 A、B：

$$
d_H(A,B) = \operatorname{popcount}(A\oplus B)
$$

例如，课件的两个串 `100101` 与 `000111` 在两位上不同，距离为 2。

编码只允许部分比特串成为合法码字。定义任意两个不同合法码字之间的最小距离为 `d_min`。冗余位的作用是让合法码字彼此分开，使少量错误不至于无法辨认。

### 8.3 检错和纠错的距离条件

只做合法性检查时，保证检测所有至多 `e` 位翻转，需要：

$$
d_{\min} \ge e+1
$$

保证纠正所有至多 `t` 位翻转，需要：

$$
d_{\min} \ge 2t+1
$$

**补充推导：**若两个合法码字距离不超过 `2t`，可能存在一个收到的串，距离它们都不超过 `t`。此时接收端无法唯一判断发送的是哪一个。纠错要求每个合法码字周围半径为 `t` 的集合互不重叠。

| `d_min` | 仅检错时保证检测的位数 | 保证纠正的位数 |
| -------:| ----------------------:| --------------:|
| 2       | 1                      | 0              |
| 3       | 2                      | 1              |
| 4       | 3                      | 1              |

**课件表述边界：**页 30 的「距离 4，检测 2 位、纠正 1 位」可以理解为 SECDED：单比特错误纠正，双比特错误报告为不可纠正。若只检查是否为合法码字，距离 4 实际可检测任意三位错误。不能在解码器已经主动纠错时，仍直接套用纯检错的最高保证。

### 8.4 简单偶校验：能检出单错，但不能定位

课件把两个数据位编码为三个比特，使 1 的总数为偶数：

| 数据 | 合法码字 |
| ---- | -------- |
| `00` | `000`    |
| `01` | `011`    |
| `10` | `101`    |
| `11` | `110`    |

8 种三位模式中只有 4 种合法，最小距离为 2。任何一位翻转都会破坏偶校验，但接收端不知道究竟是哪一位错了。两位翻转可能得到另一个合法码字，例如 `000 → 110`，因而漏检。

## 9. Hamming(7,4)：用三位冗余定位单比特错误

对应课件页 32–33。

### 9.1 校验位放在 1、2、4 号位置

下面把码字从左到右编号为 1–7，沿用课件的 `P1…P7` 表示各位置。只有 `P1、P2、P4` 是校验位，其余是数据位。

| 位置             | 1       | 2       | 3    | 4       | 5    | 6    | 7    |
| ---------------- | ------- | ------- | ---- | ------- | ---- | ---- | ---- |
| 位置的二进制表示 | 001     | 010     | 011  | 100     | 101  | 110  | 111  |
| 存放内容         | 校验 P1 | 校验 P2 | 数据 | 校验 P4 | 数据 | 数据 | 数据 |

每个校验位覆盖「位置编号的相应二进制位为 1」的那些位置：

```text
P1 校验组：1、3、5、7
P2 校验组：2、3、6、7
P4 校验组：4、5、6、7
```

采用偶校验，得到：

$$
\begin{aligned}
P_1 &= P_3\oplus P_5\oplus P_7 \\
P_2 &= P_3\oplus P_6\oplus P_7 \\
P_4 &= P_5\oplus P_6\oplus P_7
\end{aligned}
$$

### 9.2 编码课件示例：`1101 → 1010101`

将数据 `1101` 依次放到位置 3、5、6、7：

```text
位置： 1 2 3 4 5 6 7
初始： ? ? 1 ? 1 0 1

P1 = 1 XOR 1 XOR 1 = 1
P2 = 1 XOR 0 XOR 1 = 0
P4 = 1 XOR 0 XOR 1 = 0

结果： 1 0 1 0 1 0 1
```

### 9.3 解码：失败的校验组直接组成错误位置

接收端对各校验组整体求 XOR：

$$
\begin{aligned}
s_1 &= P_1\oplus P_3\oplus P_5\oplus P_7 \\
s_2 &= P_2\oplus P_3\oplus P_6\oplus P_7 \\
s_4 &= P_4\oplus P_5\oplus P_6\oplus P_7
\end{aligned}
$$

`s=0` 表示该组校验通过，`s=1` 表示不匹配。在**至多发生一位错误**的前提下，综合症 syndrome 对应的错误位置为：

$$
j = s_1 + 2s_2 + 4s_4
$$

| 不匹配的校验组 | `s4 s2 s1` | 单比特错误位置 |
| -------------- | ---------- | --------------:|
| 无             | `000`      | 无错误         |
| P1             | `001`      | 1              |
| P2             | `010`      | 2              |
| P1、P2         | `011`      | 3              |
| P4             | `100`      | 4              |
| P1、P4         | `101`      | 5              |
| P2、P4         | `110`      | 6              |
| P1、P2、P4     | `111`      | 7              |

课件的两例：

- `1010101 → 1010001`：P1、P4 不匹配，`j=1+4=5`，翻转第 5 位恢复原码字。
- `1010101 → 1110101`：仅 P2 不匹配，`j=2`，翻转第 2 位恢复原码字。

**校验位本身也可能出错。** 三个校验位区分的是「无错」加「七个位置中的某一位出错」，共 8 种情况，所以需要 `2³=8` 种综合症。

### 9.4 如果有两位或三位错误呢？

Hamming(7,4) 的最小距离为 3，只保证纠正单比特错误。

**两位错误可能被误纠正。** 例如第 1、2 位同时翻转，综合症为 `1 XOR 2 = 3`。如果解码器坚持按「只有一位错」处理，就会错误地再翻转第 3 位。

**三位错误可能完全漏检。** 对课件码字翻转第 1、2、3 位：

```text
原码字：1010101
收到值：0100101
```

三个校验组仍全部通过，因为 `1 XOR 2 XOR 3 = 0`。接收端收到的是另一个合法码字，无法仅凭这个码判断损坏。

因此，`syndrome = 0` 只表示校验通过；超过错误模型的能力范围时，不能断言没有发生错误。三位错也不一定都漏检，具体结果取决于翻转位置。

### 9.5 冗余位数量与 SECDED

**补充推导：**若有 `m` 个数据位、`r` 个校验位，为区分无错和所有单比特错误位置，需满足：

$$
2^r \ge m+r+1
$$

`m=4、r=3` 时恰好有 `8=4+3+1`。对 56 个数据位，6 个 Hamming 校验位即可满足单错定位的数量要求：`64≥56+6+1`；再加一位整体奇偶校验，可构造单错纠正、双错检测的方案。课件括号里的「56 位加 7 位冗余」不应理解为单错纠正一定至少需要 7 位。

常见的扩展 Hamming 码在 Hamming(7,4) 上增加一位整体奇偶校验，得到最小距离为 4 的编码，用于 SECDED。它仍然不能保证纠正双比特错误。

## 10. PPP：把成帧、检错和链路管理组合起来

对应课件页 34–36。

PPP（Point-to-Point Protocol）是一组配合工作的协议，包含：

| 组成                               | 职责                                          |
| ---------------------------------- | --------------------------------------------- |
| Framing / encapsulation            | 界定帧边界并封装不同上层协议                  |
| LCP，Link Control Protocol         | 建立、配置、测试和关闭链路                    |
| NCP，Network Control Protocol 家族 | 配置各网络层协议如何使用链路，例如 IP 的 IPCP |

### 10.1 基本帧格式

未采用字段压缩时，可以按课件记为：

```text
Flag | Address | Control | Protocol | Payload | FCS | Flag
 1 B |   1 B   |   1 B   |   2 B    | 可变长  |2/4 B| 1 B
```

| 字段     | 典型值或作用                                       |
| -------- | -------------------------------------------------- |
| Flag     | `0x7E = 01111110`，标记帧边界                      |
| Address  | 通常为 `0xFF`，点到点链路不靠它选择多个接收站      |
| Control  | 通常为 `0x03`                                      |
| Protocol | 标识载荷协议，支持分用                             |
| Payload  | 上层数据，也可以是链路控制协议内容                 |
| FCS      | 默认 16-bit CRC，可协商使用 32-bit CRC，检测帧差错 |

**课件校正：**页 35 把 IPv4 的 PPP Protocol 写成 `0x0800`。正确的 PPP 值是 **`0x0021`**；`0x0800` 是 Ethernet 中承载 IPv4 的 EtherType。协议号属于各自的字段命名空间，不能直接互换。参见 [IANA PPP 协议号表](https://www.iana.org/assignments/ppp-numbers/ppp-numbers.xhtml) 和 [RFC 894 的 Ethernet 封装规定](https://www.rfc-editor.org/rfc/rfc894.html)。

基本帧格式与 FCS 规则可对照 [RFC 1662 §3.1](https://www.rfc-editor.org/rfc/rfc1662.html#section-3.1)。FCS 提供检错，PPP 的基本成帧机制不会因此自动获得可靠重传。

### 10.2 PPP 如何避免数据中的 Flag 被误认？

对于采用位填充的 PPP：

- 发送端先计算 FCS，再对两个 Flag 之间的帧内容做位填充。
- 每连续出现五个 1，就插入一个 0。
- 接收端去除填充，再检查 FCS。

这样帧内容不会伪装成 `01111110`。PPP 也定义了按字节转义的方式，不能把位填充规则套到所有 PPP 传输形式上。参见 [RFC 1662 §4–5](https://www.rfc-editor.org/rfc/rfc1662.html#section-4)。

### 10.3 LCP 协商：先商定如何通信

课件以最大接收长度和 CRC 长度为例，说明双方不能直接假定对方与自己能力相同。可把过程理解为：

```text
A 提交配置提议 → B 接受、建议修改，或拒绝不支持的选项
              → A 调整并重新提议 → 双方完成链路配置
```

这只是协商意图示例，实际双方各自完成配置状态机。完整过程还可能包含认证，并通过相应 NCP 使网络层协议就绪；LCP 打开不等于任何网络层数据立刻都可发送。MRU 指接收的信息字段及填充的上限，不包含 PPP 全部帧开销。参见 [RFC 1661 §2–3](https://www.rfc-editor.org/rfc/rfc1661.html#section-2)。

页 36 标题中的 “PPT Link Management” 是 “PPP Link Management” 的笔误。

## 11. 网络层：尽力而为、重复分组与地址

对应课件页 37–40。

### 11.1 IP 的 best-effort 服务

IP 尽力把分组送往目的地，但不承诺一定到达。中间设备无法继续转发、队列溢出或遇到其他问题时，可以丢包。

课件将它与更高层的 guaranteed-delivery 服务对比：后者可使用持久缓冲、逐消息跟踪、重试等机制，在规定的故障模型内努力保证交付。任何保证都有适用前提，不能解释为所有故障下永不丢失。

**课件校正：**页 38 把 guaranteed-delivery network 又称为 store-and-forward network，但「存储转发」本身只表示先接收并保存，再转发。普通分组交换设备也会存储转发，而且仍可能丢包。可靠交付还需要确认、重试、持久性等额外机制。

### 11.2 超时和重试为什么会产生重复？

```text
A → B：请求 #7
B：已经处理，但响应丢失或延迟
A：等待超时，再发请求 #7
B：再次收到同一个逻辑请求
```

超时只能说明发送方尚未及时获得响应，不能证明对方没有执行。是否必须抑制重复，取决于操作语义：读一个值可能允许重复，重复扣款通常不允许。

与 [LEC 4：RPC](LEC-4-Remote-procedure-call.md) 联系起来：请求 ID、去重记录、幂等操作和重试语义，都用于处理这一问题。

**补充理解：** TCP 可以处理其连接内部的重复字节段，但应用在超时后重新发起一笔业务请求，仍可能造成重复执行。链路检错、传输可靠性和业务去重解决不同范围的问题。

### 11.3 地址标识网络接入点

课件把网络地址与 network attachment point（网络接入点）关联起来。网络层需要知道源和目的接入点，才能向相应方向传递分组。

**补充理解：**不要把 IP 地址简单看作一台物理机器永远唯一的身份证。一台机器可以有多个接口和多个地址；这里强调的是网络中的寻址位置。

课件的抽象接口可以记为：

```text
NETWORK_SEND(segment_buffer, destination, network_protocol, end_layer_protocol)
NETWORK_HANDLE(packet, network_protocol)
```

它表达「向下提交数据和目的地址」与「处理收到的网络分组」的层间关系，并不是某个操作系统中可直接调用的标准 API。

## 12. 路由、转发，以及控制平面与数据平面

对应课件页 41–43。

### 12.1 Routing 和 forwarding 的区别

| 概念                 | 要完成的工作                                   | 触发场景                   |
| -------------------- | ---------------------------------------------- | -------------------------- |
| Routing，路由计算    | 计算路径，形成或更新转发规则                   | 拓扑、链路状态、策略等变化 |
| Forwarding，分组转发 | 根据已有规则，把当前包送到选定输出接口／下一跳 | 每个分组到达               |

课件页 42 用目的网络到输出接口的映射举例：

| 目的网络，沿用课件标签 | 输出接口 |
| ---------------------- | -------- |
| `10.1.2.0`             | `E0`     |
| `10.1.1.0`             | `T00`    |
| `10.8.4.0`             | `S0`     |

**表述边界：**该示意图没有写前缀长度。实际路由项需要明确匹配范围，不能仅凭地址尾部是 `.0` 就断定掩码；路由项也可能需要下一跳等信息。

### 12.2 静态路由与自适应路由

- **静态路由：**按配置使用路径，环境变化后通常需要修改配置。
- **自适应路由：**交换相关信息，计算并更新路径，以应对链路变化或故障。

课件也提到根据拥塞调整路径的可能性。具体协议使用哪些指标、如何避免更新不稳定，需要由协议设计决定，不能理解为所有路由协议都会自动按实时拥塞选路。

### 12.3 Control plane 与 data plane

```text
控制平面：收集信息、运行路由算法、形成规则
                         ↓ 下发或更新转发表
数据平面：收到包 → 查表 → 选输出接口 → 排队／发送
```

控制平面决定数据如何流动，数据平面按规则处理具体数据。数据平面位于逐包处理的关键路径，因此吞吐、查表速度与队列处理非常重要。

**补充理解：**两者是功能分工，不要求一定运行在两台不同机器上。普通路由器可以在同一设备中同时包含控制平面和数据平面。

## 13. 重点公式与易混概念

### 13.1 公式速查

| 问题                     | 公式                   | 使用条件                       |
| ------------------------ | ---------------------- | ------------------------------ |
| 逐比特握手的速率上限     | `R ≲ 1/(2Δt)`          | 每轮发送后等待往返确认         |
| N 根数据线的并行速率上限 | `R ≲ N/(2Δt)`          | 每轮同时发 N 位，忽略额外延迟  |
| Manchester 数据率        | `Rdata = S/2`          | S 是每秒可用的半比特电平时隙数 |
| TDM 可容纳连接数         | `floor(Rlink / Rcall)` | 固定速率、忽略额外开销         |
| 样本周期                 | `T = 1/f`              | f 为每秒样本数                 |
| Hamming distance         | `popcount(A XOR B)`    | A、B 等长                      |
| 保证检测 e 位错误        | `dmin ≥ e+1`           | 纯检错，不主动纠正             |
| 保证纠正 t 位错误        | `dmin ≥ 2t+1`          | 任意至多 t 位翻转              |
| 单错定位的校验位数量条件 | `2^r ≥ m+r+1`          | m 数据位、r 校验位             |
| Hamming(7,4) 错误位置    | `j=s1+2s2+4s4`         | 至多一位错误，沿用本讲编号     |

### 13.2 易混概念

| 容易混淆                           | 应当区分                                   |
| ---------------------------------- | ------------------------------------------ |
| 比特同步与帧同步                   | 采样时刻与整帧边界是两个问题               |
| Manchester 与 Hamming 编码         | 前者在本讲用于时钟恢复，后者用于检错／纠错 |
| 并行与串行                         | 数据线数量与是否逐次等待确认是不同维度     |
| 无连接与无状态                     | 不预留连接状态，不代表没有转发表和队列     |
| TCP 连接与固定时隙电路             | TCP 可以运行在无连接的 IP 网络上           |
| 检测差错与恢复数据                 | 检测到损坏后，还需纠错、重传或丢弃策略     |
| 校验通过与绝对正确                 | 校验只能在规定错误模型内提供保证           |
| 物理介质共享与端口分用             | 一个安排链路使用，一个把数据交给应用端点   |
| 存储转发与可靠交付                 | 缓冲后转发不自动保证不丢失                 |
| 路由与转发                         | 一个构造规则，一个逐包使用规则             |
| PPP Protocol 与 Ethernet EtherType | 都能标识载荷协议，但数值命名空间不同       |

## 14. 复习自测

1. **为什么主机之间可以跨 Ethernet 和其他链路通信？**  
   IP 提供共同的网络层接口，路由器在每一跳按相应链路格式重新封装。

2. **一台普通路由器必须处理 HTTP 内容才能转发包吗？**  
   不需要。普通 IP 转发主要依据网络层目的地址和转发表。

3. **ready 与 acknowledge 各自解决什么问题？**  
   ready 通知接收方可以读取；acknowledge 通知发送方可以结束对旧数据的保持。

4. **为什么逐比特握手在长距离下吞吐低？**  
   每发送一位都等待约一个往返传播时间，距离增大使等待增长。

5. **Manchester 为什么能缓解连续 0 导致的时钟恢复困难？**  
   每个数据位中间都有跳变，接收端持续获得同步依据。

6. **703 路电话中的某一路暂时静音，第 704 路就一定可以加入吗？**  
   不可以。在固定分配的课堂模型里，原通话的时隙仍然被预留。

7. **分组复用为什么需要缓冲？缓冲是否能无限吸收突发？**  
   多个输入可能同时竞争一个输出，必须排队。缓冲有限，持续超负荷最终会丢包。

8. **数据中出现帧分隔符怎么办？**  
   通过位填充或转义避免保留模式直接出现在帧内容中，接收端再恢复原数据。

9. **课件的位填充和 PPP 的位填充规则相同吗？**  
   不同。教学例子在六个连续 1 后插 0，PPP 位填充在五个连续 1 后插 0。

10. **`dmin=3` 能保证纠正两位错误吗？**  
    不能，只保证纠正一位；若纯做合法性检查，可以检测任意两位错误。

11. **Hamming(7,4) 中 P2、P4 校验失败，应纠正哪一位？**  
    在单错假设下是第 `2+4=6` 位。

12. **所有 Hamming 校验都通过，是否一定没有三位错误？**  
    不一定。例如位置 1、2、3 同时翻转，综合症仍为 0。

13. **PPP 中 Flag、Protocol、FCS 各管什么？**  
    分别管理边界识别、载荷协议分用和差错检测。

14. **PPP 承载 IPv4 的协议号是多少？**  
    `0x0021`。不要与 Ethernet 的 IPv4 EtherType `0x0800` 混淆。

15. **TCP 已经可靠，为什么 RPC 还需要请求 ID？**  
    传输层处理字节交付；应用超时后重发业务请求，仍需要识别是否属于同一次逻辑操作。

16. **某条链路断开后，谁负责改规则，谁负责执行新规则？**  
    控制平面计算并更新路由／转发表，数据平面按更新后的规则逐包转发。
