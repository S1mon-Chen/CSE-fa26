## 1. 本讲主线

对应课件第 1–3、14–15 页。

**文件系统 API 把路径解析、打开状态和磁盘数据组织连接起来，让应用通过文件描述符访问文件。**

上一讲解释了如何通过路径找到 inode 和数据块。本讲进一步回答：

- 为什么 `open()` 返回一个整数，而不是 inode 地址？
- 谁保存文件的当前读写位置？多个进程何时共享它？
- 一次 `open/read/write` 会访问哪些磁盘结构？
- 删除、关闭、重命名和持久化分别改变什么状态？
- 不使用 inode 的 FAT 文件系统如何提供类似接口？

```text
open(path)
    → 解析路径、检查权限
    → 建立打开文件记录
    → 返回进程内的 fd

read(fd, buf, n)
    → 进程的 fd_table
    → 系统的打开文件记录：访问模式、cursor 等
    → inode：大小、数据块索引等
    → 缓存或磁盘数据块
```

## 2. 复习：名字、inode 与符号链接

对应课件第 4–13 页。

### 2.1 七层抽象与名字绑定

| 层 | 作用 |
| --- | --- |
| L1：块层 | 用块号访问磁盘数据块 |
| L2：文件层 | 通过 inode 把文件内位置映射到数据块 |
| L3：inode 编号层 | 将 inode number 映射到 inode |
| L4：文件名层 | 在目录中查找「名字 → inode number」 |
| L5：路径名层 | 逐级解析多级目录 |
| L6：绝对路径层 | 从根目录 `/` 开始解析 |
| L7：符号链接层 | 读取链接保存的路径，继续解析目标 |

需要保留的结论：

1. 文件名存放在目录项中，不在 inode 中。
2. 一个 inode 可以有多个名字，它们都是地位相同的硬链接。
3. 目录保存子项的名字和 inode 编号，不包含所有子文件的内容。
4. inode 的多级间接索引用于寻址大文件。

课件再次使用 `/programs/pong.c`：从根目录找到 `programs`，再找到 `pong.c` 的 inode，最后访问数据块 `61、44、15`。

**理解边界：**第 13 页的「Directory size is small」强调目录保存映射而非子文件内容；目录项很多时，目录自身也可以很大。

### 2.2 硬链接与符号链接

```text
硬链接：名字 A ─┐
               ├→ 同一个 inode → 文件内容
        名字 B ─┘

符号链接：链接名 → 链接自身的 inode → 目标路径 → 目标文件
```

课件例子：

```sh
ln -s "/tmp/abc" s-link
readlink s-link
# /tmp/abc
```

链接保存的 `/tmp/abc` 占 8 字节，因此链接大小为 `8`。目标不存在时，链接仍然存在，但沿链接访问目标会失败。符号链接可以引用其他已挂载文件系统中的路径；挂载本身由 `mount` 等机制完成。

### 2.3 `cd ..` 的逻辑路径与物理路径

假设：

```text
/CSE-web → /Scholarly/programs/www
```

在 Bash 的默认逻辑模式下：

```sh
cd /CSE-web
pwd -L
# /CSE-web
pwd -P
# /Scholarly/programs/www
cd ..
pwd -L
# /
```

若重新进入该链接，再使用物理模式：

```sh
cd /CSE-web
cd -P ..
pwd -P
# /Scholarly/programs
```

**课件校正：**第 12 页将逻辑 `cd ..` 归因于 `$OLDPWD`，不够准确。Bash 根据逻辑路径处理 `..`，`OLDPWD` 则用于记录前一个工作目录，供 `cd -` 等使用。`cd -P` 按实际目录结构解析。参见 [Bash 的 `cd` 与 `pwd` 说明](https://www.gnu.org/software/bash/manual/html_node/Bourne-Shell-Builtins.html)。

## 3. API、系统调用与标准库

对应课件第 15–16 页。

### 3.1 文件系统 API 的分类

| 类别 | 课件列出的操作 | 主要作用 |
| --- | --- | --- |
| 目录上下文 | `CHDIR, MKDIR` | 改变当前目录、创建目录 |
| 文件与名字 | `CREAT, LINK, UNLINK, RENAME` | 创建文件、增删或修改名字绑定 |
| 符号链接 | `SYMLINK` | 创建保存目标路径的链接 |
| 挂载 | `MOUNT, UNMOUNT` | 将文件系统接入或移出命名空间 |
| 内容访问 | `OPEN, READ, WRITE, APPEND, CLOSE` | 管理打开状态与文件内容 |
| 同步 | `SYNC` | 将缓存中的修改提交到存储设备 |

这里使用概念操作名。实际接口不一定一一同名，例如追加通常使用带 `O_APPEND` 标志的 `open()` 配合 `write()`。

内核为不同文件系统提供各自的操作实现，课件用「多组函数指针」描述这种分派。路径进入某个挂载的文件系统后，内核调用对应实现。应用可以使用相同的文件 API，而不必自行解释 inode 或 FAT。

### 3.2 `open()` 与 `fopen()`

| 比较项 | `open()` | `fopen()` |
| --- | --- | --- |
| 所在接口层 | UNIX/POSIX 系统调用接口 | C 标准库的流接口 |
| 返回对象 | `int fd` | `FILE *` |
| 配套操作 | `read/write/close` | `fread/fwrite/fprintf/fclose` |
| 用户态缓冲 | 不提供 stdio 的流缓冲 | 通常提供流缓冲 |
| 可移植性 | 依赖相应 OS/POSIX 接口 | 标准 C 接口，Windows 和 Linux 均提供 |

stdio 可以把多次小写入合并成较少的底层调用，因此经常提高性能。但不能据此断言 `fopen()` 总比 `open()` 快，结果取决于访问大小、缓冲策略和负载。

**补充理解：**`FILE *` 是标准库管理的流对象指针，不能当作 fd 传给 `read()`。另外，使用 `open/read/write` 仍可能经过内核缓存，不能把「没有 stdio 缓冲」理解为「完全没有缓存」。

## 4. inode 中的权限和时间戳

对应课件第 17–18 页。

课件将 inode 扩展为：

```text
inode
├── block_nums[]       数据块索引
├── size、type         文件大小与类型
├── refcnt             本课模型中的硬链接计数
├── userid、groupid    所有者与所属组
├── mode               权限位等
└── atime、mtime、ctime
```

### 4.1 权限检查

基本权限按 owner、group、other 三类划分，每类都有 read、write、execute 权限。`open()` 按调用者身份和请求的访问方式检查是否允许打开文件。

**补充理解：**对目录而言，读权限对应列出目录项，执行权限对应搜索、穿过目录。创建或删除名字还涉及父目录权限，不能只看目标文件的读写权限。

### 4.2 三种时间戳

| 字段 | 含义 | 典型更新原因 |
| --- | --- | --- |
| `atime` | 最近访问时间 | 读取文件内容 |
| `mtime` | 最近内容修改时间 | 写入、截断文件 |
| `ctime` | 最近 inode 状态变更时间 | 权限、链接数等改变，或写入导致状态改变 |

**`ctime` 不是创建时间。** 内容修改通常也伴随 `ctime` 更新，不能把三种时间戳理解成互斥事件。

**课件校正：**第 18 页把更新时间戳列在 `OPEN` 中，但第 29 页的图在 `READ` 阶段才写回 `bar` inode。实际 Linux 中不能笼统认为只调用 `open()` 就会更新 `atime`，其更新还受 `noatime/relatime` 等策略影响。参见 [Linux inode 时间戳说明](https://man7.org/linux/man-pages/man7/inode.7.html)。

## 5. 文件描述符：进程使用的短名字

对应课件第 18–20 页。

### 5.1 fd 是进程内的整数编号

`open()` 成功后返回文件描述符（file descriptor，fd），后续 `read/write/close` 使用该编号访问已打开的对象。

| 常规 fd | 名称 | 默认用途 |
| --- | --- | --- |
| `0` | stdin | 标准输入 |
| `1` | stdout | 标准输出 |
| `2` | stderr | 标准错误 |

这些是进程通常继承的约定，可以被重定向或关闭。程序只需从 `0` 读、向 `1` 写，无需把键盘、终端或普通文件写死在程序中。

**每个进程有自己的 fd 命名空间。** 进程 A 的 `fd = 3` 和进程 B 的 `fd = 3`，既可能对应同一文件，也可能对应不同文件。

### 5.2 为什么不返回 inode 指针或全部块号？

课件强调两个理由：

- **安全性：**用户程序不能直接访问、修改内核数据结构。
- **不可绕过性 / complete mediation：**文件操作经过内核，由内核解释句柄并执行访问约束。

这种间接访问还隐藏了磁盘布局。文件增长、块分配或文件系统实现变化，不必暴露给应用。

**补充理解：**经过内核不等于每次 `read()` 都重新按路径查权限。普通文件在打开时确定访问模式，后续操作检查 fd 及其打开状态；名字改变也不会自动让已有 fd 改指向另一个文件。

## 6. `fd_table`、`file_table` 与共享 cursor

对应课件第 21–23 页。

### 6.1 三种状态分别放在哪里？

| 结构 | 范围 | 保存的主要信息 |
| --- | --- | --- |
| `fd_table` | 每个进程一份 | fd 到打开文件记录的映射 |
| `file_table` | 课件中的系统级表 | inode 引用、cursor、打开记录的引用计数 |
| inode | 文件对象 | 大小、块索引、权限、硬链接数等 |

cursor 是下一次读写的位置，可以由 seek 操作改变。**它属于一次打开所形成的状态，不属于 inode。** 否则所有打开同一文件的进程都会被迫使用同一位置。

实际系统通常称这种打开记录为 **open file description**。课件中的数组与下标用于说明关系，不要求内核真的用一个固定数组实现全部对象。

### 6.2 同一个 inode，可以对应不同 cursor

课件第 23 页的例子：

```text
进程 A：fd 3 → file_table[115] → inode 23，cursor = 128，refcnt = 1

进程 B：fd 3 ─┐
             ├→ file_table[116] → inode 23，cursor = 240，refcnt = 2
进程 C：fd 3 ─┘
```

- A 和 B 分别执行 `open()`，得到两条打开记录，cursor 独立。
- C 是 B 的子进程，通过 `fork()` 继承 fd，引用 B 的同一条打开记录，cursor 共享。
- 三个进程访问的是同一个文件对象，因此仍然共享文件内容。

**独立 cursor 不意味着内容隔离。** A 写入文件后，B 仍可能读到被修改的内容。

### 6.3 两个 `refcnt` 不能混淆

| 计数 | 记录什么 | 典型增加操作 | 典型减少操作 |
| --- | --- | --- | --- |
| inode 的硬链接计数 | 有多少目录项指向该文件 | `link()` | `unlink()` |
| 打开文件记录的引用计数 | 有多少引用仍持有该打开记录 | `fork()`、`dup()` 等 | `close()`、进程退出等 |

课件称后者为「打开进程的引用计数」，但同一进程也可通过 `dup()` 持有多个 fd 引用，因此不能严格等同于进程数。

**补充例子：**文件内容为 `abcdef`，假设下列调用按顺序完成且均成功：

| 操作序列 | 读到的内容 |
| --- | --- |
| B 打开文件，然后 `fork()` 出 C；B 读 2 字节，C 再读 2 字节 | B 得到 `ab`，C 得到 `cd` |
| A、B 各自打开文件，然后各读 2 字节 | A、B 都得到 `ab` |

若父子进程并发执行，哪一方先读不能仅凭代码书写位置确定。关于打开记录和共享偏移，参见 [Linux `open(2)`](https://man7.org/linux/man-pages/man2/open.2.html)。

## 7. `OPEN` 和 `READ` 的实现

对应课件第 24–25 页。

### 7.1 `OPEN`：从路径建立打开状态

课件伪代码可整理为：

```text
OPEN(path, flags, mode):
    解析路径，定位 inode
    若最后一个名字不存在，且允许创建：创建文件
    若路径解析或创建失败：返回错误
    检查请求的访问权限
    创建打开文件记录，初始化 cursor 等状态
    找到当前进程一个未使用的 fd
    将 fd 绑定到打开文件记录
    返回 fd
```

`open()` 主要建立访问文件的上下文，并不把整个文件读入内存。

**课件校正：**第 24 页写作 `flags = O_CREATE`。实际 POSIX 标志名为 `O_CREAT`，可以与其他标志按位组合，不能一般性地用相等判断代替检查某一标志。创建也只适用于合适的「目标不存在」情形，不能把权限错误等任意解析失败都当成可创建。

示例：

```c
int fd = open("notes.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
```

这表示以只写方式打开，不存在则创建，存在则截断。`0644` 是创建时请求的权限，通常还要受 `umask` 限制。实际程序需检查 `fd == -1`。

### 7.2 `READ`：根据 cursor 读取并推进位置

设文件大小为 $S$，当前 cursor 为 $c$，请求读取 $n$ 字节。在忽略并发修改和 I/O 错误的普通文件模型中：

$$
m=\min\bigl(n,\max(0,S-c)\bigr)
$$

读取完成后，cursor 增加实际读取的字节数。

课件伪代码省略了块内偏移、部分读取和失败处理。更清楚的教学版本如下，假设访问的块均可成功读取且文件没有稀疏洞：

```text
READ(fd, buf, n):
    验证 fd、读取权限和用户缓冲区
    opened = fd_table[fd] 对应的打开记录
    inode = opened 对应的 inode
    pos = opened.cursor
    remaining = min(n, max(0, inode.size - pos))
    copied = 0

    while remaining > 0:
        block_index = pos // BLOCKSIZE
        offset = pos % BLOCKSIZE
        chunk = min(remaining, BLOCKSIZE - offset)
        block = 按 inode 索引取得对应的数据块
        将 block[offset : offset + chunk] 复制到 buf[copied : ...]
        pos += chunk
        copied += chunk
        remaining -= chunk

    opened.cursor = pos
    按文件系统策略处理访问时间
    return copied
```

关键是每轮最多复制 `BLOCKSIZE - offset` 字节，不能总按完整块大小复制。

**补充计算：**块大小 4096 B，从偏移 4090 读取 20 B，且文件足够长：

- 从当前块末尾读取 6 B。
- 从下一块开头读取 14 B。
- 新 cursor 为 4110。

实际 `read()` 返回正数表示读取字节数，返回 `0` 表示 EOF（请求长度为零时也可能返回 `0`），返回 `-1` 表示错误。成功也可能只读到请求的一部分。参见 [Linux `read(2)`](https://man7.org/linux/man-pages/man2/read.2.html)。

## 8. 磁盘布局与 I/O 次数

对应课件第 26–30 页。

### 8.1 一个 64 块的简单文件系统

课件将块编号设为 `0–63`：

```text
块 0       块 1       块 2       块 3–7          块 8–63
superblock inode bitmap data bitmap inode table   data region
```

| 区域 | 内容 |
| --- | --- |
| Superblock | 文件系统参数、布局信息、用于识别文件系统类型的 magic number 等 |
| inode bitmap | 哪些 inode 已分配 |
| data bitmap | 哪些数据块已分配 |
| inode table | inode 记录，本例可容纳 80 个 |
| data region | 56 个块，用于普通文件内容、目录内容等 |

inode table 占 5 块，容纳 80 个 inode，因此本例平均每块容纳 16 个 inode。superblock 在挂载时用于解释后续布局。

### 8.2 `open("/foo/bar", O_RDONLY)` 的时序

课件第 29 页依次画出：

1. 读根目录 inode。
2. 读根目录数据，找到 `foo`。
3. 读 `foo` inode。
4. 读 `foo` 目录数据，找到 `bar`。
5. 读 `bar` inode，建立打开状态。

**按课件图逐项计数：5 次读，0 次写。**

随后三次 `read()` 分别读取 `bar` 的三个数据块，每次画出：

```text
读 bar inode → 读一个 bar 数据块 → 写 bar inode
```

每次是 **2 次读、1 次写**，写 inode 的原因是更新 `atime`。因此整幅图合计 **11 次读、3 次写**。

为什么后续 `read()` 不再写 `foo` inode？因为已经通过 fd 定位打开文件，读取的是 `bar` 的内容，无需重新解析 `/foo/bar`。课件图也没有计入目录查找可能涉及的目录时间戳处理。

### 8.3 创建 `/foo/bar` 的时序

第 30 页创建阶段的操作如下：

| 步骤 | 访问结构 | 图中操作 | 目的 |
| --- | --- | --- | --- |
| 1 | 根 inode、根数据、`foo` inode、`foo` 数据 | 4 次读 | 找到父目录及插入位置 |
| 2 | inode bitmap | 1 次读、1 次写 | 分配新 inode |
| 3 | `foo` 数据 | 1 次写 | 插入 `bar → 新 inode` 的目录项 |
| 4 | `bar` inode 所在块 | 1 次读、1 次写 | 初始化新 inode，保留同块其他记录 |
| 5 | `foo` inode | 1 次写 | 更新父目录元数据 |

**按图合计：6 次读、4 次写。** 此时新文件为空，图中还没有为文件内容分配数据块。

之后每次向新块写入，图中包含：

```text
读 bar inode
读、写 data bitmap
写新的 bar 数据块
写 bar inode
```

即每次 **2 次读、3 次写**。图中三次写入连同创建，总计 **12 次读、13 次写**。

### 8.4 这些数字何时成立？

以上数字是**对课件时序图中 read/write 标记的计数**，不是任意真实文件系统的固定磁盘 I/O 次数。图采用简化假设，例如目录查找只访问图示目录块、父目录已有可用空间、新文件写入逐次分配数据块。

真实磁盘访问还受以下因素影响：

- inode、目录和数据是否已缓存。
- 多个 inode 是否位于同一个磁盘块。
- 文件是否需要间接索引块。
- 目录是否扩容，写入是否需要读改写。
- 时间戳策略、日志写入与延迟回写。

做题时先写清缓存和布局假设，再列出访问对象，最后统计次数。

## 9. `WRITE`、`APPEND` 与崩溃一致性

对应课件第 31–32 页。

### 9.1 写入比读取多了哪些工作？

写入沿用 `fd → 打开记录 → inode → 数据块` 的查找过程，同时可能需要：

- 分配新块并更新 data bitmap。
- 修改数据块。
- 更新 inode 的大小、块指针和修改时间。
- 按实际写入字节数推进 cursor。

因此，一次写入可能修改多个互相依赖的磁盘结构。机器若在中途崩溃，磁盘上可能只保留部分修改。

### 9.2 `APPEND` 与先 seek 再 write

追加将本次写入位置设为文件末尾。多个进程各自执行「seek 到末尾，再 write」，可能都观察到同一个旧末尾，进而覆盖对方的内容。

**补充理解：**Linux 的 `O_APPEND` 将定位末尾与本次写入作为一个原子步骤处理，但这不代表跨多次 `write()` 的完整记录或事务也具有原子性，网络文件系统还可能有额外限制。参见 [Linux `open(2)` 的 `O_APPEND`](https://man7.org/linux/man-pages/man2/open.2.html)。

### 9.3 第 32 页：三种写入顺序如何比较？

设为文件追加一个新块，需要持久化三类修改：

```text
B：bitmap 将新块标记为已占用
D：将新内容写入该数据块
I：inode 更新大小和指针，引用新块
```

下表假设各步完整落盘，并且设备遵守给定顺序：

| 顺序 | 中途崩溃的主要风险 |
| --- | --- |
| `B → D → I` | inode 尚未引用新块时崩溃，可能留下已分配但不可达的块，需要回收 |
| `B → I → D` | inode 已暴露新块，但新数据未写入，读取可能得到旧内容或无效内容 |
| `I → B → D` | inode 引用的块仍显示为空闲，可能被再次分配，同时也有未初始化内容的风险 |

**在这个简化场景中，优先选择 `B → D → I`：先分配并准备数据，再让 inode 引用它。** 这使中间状态更偏向资源泄漏，而不是让文件指向仍空闲或尚未准备好的块。

但它仍不是完整的崩溃一致性方案。程序执行顺序未必等于持久化顺序，单步写入也可能失败，仍需日志、恢复流程或其他一致性机制。本讲在此提出问题，后续课程再展开。

## 10. 缓存与持久化同步

对应课件第 33 页。

### 10.1 为什么要延迟写回？

块缓存保存近期使用的数据：缓存命中时可直接读取，未命中时才访问设备。修改后的脏块可以暂留内存，将多次修改合并后写回，以减少 I/O。

代价是：**`write()` 返回成功，不必然表示数据已能在断电后保留。**

```text
应用的 stdio 缓冲（使用 FILE * 时）
    ↓ fflush / fclose 等
内核缓存
    ↓ 文件系统回写、fsync 等
存储设备
```

### 10.2 不同同步操作的边界

| 操作 | 主要作用 |
| --- | --- |
| `fflush(stream)` | 将用户态流缓冲提交到底层写操作 |
| `fsync(fd)` | 同步该文件的数据及相关元数据到存储设备 |
| `fdatasync(fd)` | 同步数据及正确读取这些数据所必需的元数据 |
| `sync()` | 请求同步整个系统的文件数据和元数据 |
| `close(fd)` | 释放 fd 引用，不能当作持久化保证 |

**课件校正：**第 33 页用 `SYNC` 泛指「确保一个文件的修改写入设备」。实际接口中，这一表述更接近 `fsync(fd)`，不能直接等同于全局 `sync()`。

**补充理解：**同步文件本身不必然同步它在父目录中的名字。若还要保证新建或重命名的目录项持久化，Linux 中通常需要对相关目录另行同步。参见 [`fflush(3)`](https://man7.org/linux/man-pages/man3/fflush.3.html)、[`fsync(2)`](https://man7.org/linux/man-pages/man2/fsync.2.html) 和 [`sync(2)`](https://man7.org/linux/man-pages/man2/sync.2.html)。

## 11. `CLOSE`、`UNLINK` 与文件生命期

对应课件第 31、34 页。

### 11.1 关闭一个 fd 的过程

1. 清除当前进程 `fd_table` 中的对应项。
2. 减少对应打开文件记录的引用计数。
3. 若该打开记录不再被引用，则释放它。
4. 若文件也已没有名字及其他存活引用，才可回收文件资源。

关闭 fd 不会自动删除文件名。共享同一打开记录时，一个进程的 `close()` 也不会使另一个进程的 fd 立即失效。

### 11.2 已打开文件被删除后会怎样？

```text
初始：目录项 report → inode X，进程 A 的 fd → 打开记录 → inode X

进程 B 执行 unlink("report")：
    目录项消失，硬链接计数降为 0
    A 的 fd 仍引用 inode X，仍可访问原文件

A 最后关闭它，且没有其他引用：
    文件资源可以回收
```

**删除名字和结束打开状态是两个独立操作。**

如果 `report` 随后被重新创建，这个名字指向新文件；A 的旧 fd 仍指向此前打开的对象，不会自动切换。

课件提到 Windows 可能禁止删除已打开文件。这里保留「可能」：是否允许取决于打开方式和共享删除设置，不能概括为所有 Windows 打开文件都无法删除。

## 12. `RENAME`：名字替换与原子性

对应课件第 35–38 页。

### 12.1 为什么不能简单先删目标？

编辑器可先写临时文件，再替换正式文件。若按课件的朴素方案：

```text
1. UNLINK(to_name)
2. LINK(from_name, to_name)
3. UNLINK(from_name)
```

在步骤 1 和 2 之间崩溃，目标名字已经不存在，新名字绑定却尚未建立。

### 12.2 先更新目标绑定的较弱方案

课件讨论先让目标目录项指向来源 inode，再删除来源目录项：

```text
1. to_name 改为指向 from_name 的 inode
2. 删除 from_name 的目录项
```

两步之间失败时，可能留下两个名字指向同一 inode。恢复过程还需要修正链接计数，并处理旧目标对象的资源。

**理解边界：**课件把第一步简写为 `LINK`，但普通 `link()` 不能直接覆盖一个已有的目标名字。这里讨论的是内部更新方案，不是可原样运行的两个系统调用。

### 12.3 跨目录不等于跨文件系统

课件第 37 页执行：

```sh
mv dir1/from.txt dir2/to.txt
```

目标最后保留来源的 inode 编号 `40978804`，说明这次操作改变的是目录中的名字绑定，无需复制来源文件内容。

**补充理解：**同一文件系统中的 `rename()` 可以跨目录，并对已有目标提供原子替换语义；跨文件系统通常不能直接 `rename()`，会返回 `EXDEV`。工具 `mv` 此时可能通过复制和删除完成移动，不能据此推断仍具有相同原子性。参见 [Linux `rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html)。

还要区分：原子替换关心其他观察者是否看到中间状态，持久化关心崩溃后哪些修改保留下来。一次 `rename()` 成功，不足以单独证明新文件内容及目录更新都已经持久化。

## 13. 不使用 inode 的选择：连续分配与 FAT

对应课件第 39–45 页。

### 13.1 连续块分配

把一个文件的数据放在连续区域，可以用起点和长度快速计算位置。但文件增长时，后方未必有足够空闲空间，可能需要重新分配并搬迁整个文件，也会遇到外部碎片问题。

### 13.2 FAT：通过分配表连接数据块

FAT（File Allocation Table）将文件组织成块链。课件按块解释，实际 FAT 通常以簇（cluster，一组扇区）为分配单位。

链的后继信息保存在 FAT 表中，表项与分配单位对应。可用如下概念示例理解：

```text
目录项：example.txt → 起始簇 31

FAT[31] = 7
FAT[7]  = 52
FAT[52] = EOF

文件逻辑顺序：簇 31 → 簇 7 → 簇 52
```

文件内偏移表示为 `<B, x>` 时，`B` 是文件中的逻辑块索引，`x` 是块内偏移。要找到逻辑块 `B`，从链首沿 FAT 后继关系前进相应步数。

**补充理解：**在没有额外索引或已知位置的基本链表模型中，随机定位第 $k$ 块需要沿链访问 $O(k)$ 个表项。缓存 FAT 可以减少设备访问，但不会自动消除链式定位关系。

### 13.3 追加数据与目录

向课件的 File 31 追加第 4 个逻辑块时，需要找一个空闲块，将旧链尾连接到新块，并标记新的链尾，同时更新文件大小等元数据。

FAT 文件系统把文件名、大小、起始簇等属性保存在目录项中，没有本课所讲的独立 inode table。目录本身存储一组目录项，也需要分配存储空间。

**课件校正：**第 44 页的「Root dir at sector 0」不能作为实际 FAT 布局规则。FAT12/16 的根目录位于 FAT 表之后的专用区域；FAT32 的根目录起始簇由引导参数中的 `BPB_RootClus` 指定。参见 [Microsoft FAT Specification](https://www.scs.stanford.edu/~zyedidia/docs/_other/fat.pdf)。课件中的 free list 也是概念表达，实际 FAT 用表项值表示空闲簇。

### 13.4 inode 与 FAT 对照

| 方面 | 本课 inode 模型 | 传统 FAT 模型 |
| --- | --- | --- |
| 文件数据定位 | inode 的直接、间接块索引 | 从起始簇沿 FAT 链查找 |
| 文件元数据 | 集中在 inode | 主要保存在目录项中 |
| 目录项作用 | 名字映射到 inode number | 保存名字、起始簇、大小等 |
| 随机访问 | 通过索引定位所需数据块 | 基本模型需要沿链定位 |
| 硬链接 | 多个目录项共享 inode 和链接计数 | 标准格式不原生提供 UNIX 式硬链接 |
| 符号链接 | 专门的文件类型保存目标路径 | 标准格式不原生提供 UNIX 式符号链接 |

为什么不能只在两个 FAT 目录项里写同一起始簇，就认为实现了硬链接？因为还需协调文件大小等重复元数据，并解决删除一个名字时谁负责释放簇链。共享数据地址并不等于完整的硬链接语义。

符号链接的路径间接思想本身不依赖 inode，但文件系统必须定义相应对象类型，系统也必须支持解析它。某些扩展或上层模拟不能直接视为传统 FAT 的原生能力。

### 13.5 vnode / VFS 的统一接口

课件最后预告 vnode：在内核中提供统一的文件对象与操作接口，使上层通过相同方式访问不同文件系统。

```text
应用的 open/read/write
          ↓
统一的文件系统抽象与操作分派
          ↓
具体文件系统实现：inode 索引、FAT 链等
```

因此，「应用使用文件描述符」和「磁盘上使用 inode」并不是必须绑定的选择。

## 14. 复习自测

1. **fd、inode number 和 cursor 分别是什么？**  
   fd 是进程内引用打开对象的编号；inode number 标识文件系统中的 inode；cursor 是打开记录中的当前读写位置。

2. **两个进程的 `fd = 3` 是否表示同一文件？**  
   不一定，fd 命名空间属于进程。

3. **两个 fd 指向同一 inode，是否一定共享 cursor？**  
   否。分别 `open()` 时通常独立；引用同一打开记录时才共享。

4. **`fork()` 后父子共享什么？**  
   各自持有 fd 表，但继承的 fd 引用同一打开记录，因此共享相应 cursor。

5. **打开文件记录的引用数是否等于硬链接数？**  
   否，前者描述打开状态的引用，后者描述目录名字绑定。

6. **读文件为什么可能引发写操作？**  
   因为可能更新 inode 的 `atime`；实际是否立即产生磁盘写入取决于策略与缓存。

7. **课件中打开 `/foo/bar` 需要多少次读写？**  
   按第 29 页图计数是 5 读、0 写；后续每次读一个数据块是 2 读、1 写。

8. **课件中新建 `/foo/bar` 需要多少次读写？**  
   按第 30 页创建阶段计数是 6 读、4 写；之后每次向新分配的数据块写入是 2 读、3 写。

9. **追加新块时，为什么倾向先 bitmap、再数据、最后 inode？**  
   让 inode 只引用已经分配并准备好的块，但中途仍可能泄漏空间，并非完整的一致性保证。

10. **`write()`、`fflush()`、`close()` 返回是否都表示已持久化？**  
    否。需要明确对应接口的同步保证，名字更新还涉及目录持久化。

11. **最后一个名字被删除，文件是否立即不可访问？**  
    不一定，已有 fd 仍可访问原对象，资源要等存活引用结束后才能回收。

12. **为什么 `ctime` 不能解释为创建时间？**  
    它记录 inode 状态变更时间，修改权限、链接数或内容等都可能使它改变。

13. **跨目录移动是否一定复制文件数据？**  
    否，同一文件系统内通常只需修改目录关系；跨文件系统则是另一种情况。

14. **FAT 为什么不直接提供 UNIX 式硬链接？**  
    它缺少本课 inode 模型中统一的文件元数据对象和链接计数，直接复制起始簇引用无法正确处理修改与释放。
